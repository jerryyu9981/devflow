## 一、背景与目标

### 1.1 问题定义

在现有 DevFlow 五步开发流程中，Step 2（架构与设计阶段）虽有"UI/UX 与原型"和"API 接口设计"等类别，但存在以下缺口：

**前端设计缺口**：
- **页面遗漏风险**：无法系统性地确认"所有该有原型的页面是否都有了原型"。
- **状态覆盖不全**：原型往往只覆盖"正常态"，忽略空态、错误态、加载态、边界态。
- **流程断点未知**：单页面原型完整，但页面间跳转逻辑可能在真实用户路径中出现断点。
- **需求-原型脱节**：需求文档中的用户故事与原型文件之间缺乏双向可追溯的映射关系。

**后端设计缺口**：
- **API 契约不完整**：API 文档缺少异常响应、边界条件、版本兼容性和降级策略。
- **数据模型与前端脱节**：数据库设计与前端展示需求未对齐，导致联调阶段频繁返工。
- **状态机缺失**：后端业务状态流转缺乏可视化文档，开发和测试难以理解完整生命周期。
- **安全与权限设计遗漏**：鉴权粒度、数据权限、敏感字段处理在设计阶段未系统化梳理。
- **性能与容量设计浮于表面**：缺乏具体的性能基线、瓶颈路径分析和容量预算。

**共性缺口**：
- **测试视角缺失**：设计阶段未预埋测试关注点，导致测试阶段频繁发现设计遗漏。
- **前后端协作断点**：前端与后端的设计文档缺乏交叉验证机制，接口契约在联调时才暴露不一致。

### 1.2 核心目标

建立一套**可执行、可检查、可审计**的**前后端设计工程化规范**，确保：

**前端目标**：
1. **无遗漏**：所有 P0/P1 需求涉及的前端页面均有原型覆盖。
2. **状态完整**：每个页面的关键交互状态均在原型中体现。
3. **流程贯通**：核心用户路径通过原型走查验证，无断点。
4. **双向追溯**：需求 ↔ 页面 ↔ 原型 ↔ 测试用例 形成完整追溯链。

**后端目标**：
5. **API 契约完整**：每个 API 的异常响应、边界条件、版本兼容性和降级策略均有设计。
6. **数据模型对齐**：数据库设计与前端展示需求、API 契约三者一致。
7. **状态机可视化**：核心业务状态流转有可视化文档，覆盖所有异常分支。
8. **安全设计系统化**：鉴权粒度、数据权限、敏感字段处理在设计阶段已梳理。

**前后端协作目标**：
9. **API 契约对齐**：前端页面清单与后端 API 设计交叉验证，接口契约在设计阶段锁定。
10. **设计即测试**：设计阶段预埋测试关注点（前端 UI 测试 + 后端接口测试），减少下游返工。

### 1.3 方案定位

本方案是 `design-stage-execution` 技能的**专项增强补充**，不是替代。所有增强内容必须在 Step 2 设计阶段和 Step 3 编码阶段执行，并遵循 `project-document-management` 技能的文档命名与存储规范。

**`prototype-coverage` 技能是本方案前端部分的执行载体**，封装了完整的七步覆盖检查流程（页面清单建立 → 状态覆盖检查 → 原型走查 → 用例场景演练 → 元素级交互标注 → 设计-测试预映射 → 覆盖检查报告）。

**后端设计覆盖检查**由 `design-stage-execution` 的设计规范矩阵直接管控，本方案通过新增"后端设计覆盖检查"类别和"前后端 API 契约对齐"检查点来增强现有矩阵。

**编码阶段前后端规范**由 `coding-stage-execution` 管控，本方案通过新增"前后端编码规范区分"和"API 契约一致性检查"来增强编码阶段的输入要求和自测标准。

## 二、核心方案：前后端设计覆盖保障体系

### 2.1 体系架构

```text
前后端设计覆盖保障体系
├── 前端部分（由 prototype-coverage 技能执行）
│   ├── 1. 前端页面清单（Page Inventory）
│   │   └── 建立"需求 → 页面 → 原型"的完整映射
│   ├── 2. 前端状态覆盖检查
│   │   └── 每个页面必须覆盖空态、加载态、错误态、成功态、边界态
│   ├── 3. 原型走查（Prototype Walkthrough）
│   │   └── 按用户角色和核心路径模拟操作，暴露流程断点
│   ├── 4. 用例场景演练（Scenario-Based Validation）
│   │   └── 基于用例规约，在原型中完整演练基本流程 + 异常分支
│   ├── 5. 元素级交互标注
│   │   └── 每个可交互元素标注触发事件、条件判断、成功路径、错误处理
│   └── 6. 前端设计-测试预映射
│       └── 设计阶段预埋前端 UI 测试关注点
│
├── 后端部分（由 design-stage-execution 矩阵管控）
│   ├── 7. API 契约覆盖检查
│   │   └── 检查 API 的异常响应、边界条件、版本兼容、降级策略
│   ├── 8. 数据模型对齐检查
│   │   └── 验证数据库设计与前端需求、API 契约三者一致
│   ├── 9. 业务状态机覆盖检查
│   │   └── 核心业务状态流转可视化，覆盖所有异常分支
│   ├── 10. 安全与权限设计检查
│   │   └── 鉴权粒度、数据权限、敏感字段处理系统化梳理
│   └── 11. 后端设计-测试预映射
│       └── 设计阶段预埋后端接口测试关注点
│
└── 前后端协作部分
    ├── 12. API 契约对齐检查
    │   └── 前端页面清单与后端 API 设计交叉验证
    ├── 13. 数据流追溯检查
    │   └── 前端展示数据 ↔ API 响应 ↔ 数据库字段 三者映射一致
    └── 14. 编码阶段规范区分
        └── 前端编码规范 vs 后端编码规范，API 契约一致性检查
```

**技能调用关系**：
- **前端原型创建**：`frontend-design` / `prototyping` / `ui-ux-pro-max` / `figma` → 产出 HTML 原型文件
- **前端原型验证**：`prototype-coverage` → 执行六步前端覆盖检查流程 → 输出前端覆盖检查报告
- **后端设计验证**：`design-stage-execution` 矩阵 → 执行五步后端覆盖检查 → 输出后端设计评审结论
- **前后端协作对齐**：`api-design` + `api-contract-management` → 验证 API 契约一致性 → 输出对齐确认书
- **编码阶段**：`coding-stage-execution` → 执行前后端编码规范 → 输出 DevLogReport
- 整体形成**设计 → 对齐 → 编码 → 联调**的闭环

### 2.2 与现有 DevFlow 的集成关系

| 现有技能/规范 | 本方案的增强点 |
|---|---|
| `design-stage-execution` | 在设计规范矩阵中新增"前端原型覆盖检查"、"原型走查"、"用例场景演练"三行 |
| `project-document-management` | 新增三种文档类型：前端页面清单、原型走查记录、用例场景演练报告 |
| 需求-设计追溯矩阵 | 增加"涉及页面"、"原型状态"、"测试关注点"三列 |
| 强制规则 | 新增三条前端原型专项规则 |
| 输出要求 | 增加"前端页面清单"、"原型走查记录"、"用例场景演练报告"三项强制产出 |

    └── 通过后进入前后端对齐阶段

### 3.3 前后端对齐流程

```text
前后端协作对齐阶段（Step 2 内）
├── 1. API 契约对齐检查
│   ├── 前端页面清单 ↔ 后端 API 设计 交叉验证
│   ├── 检查: 每个前端数据展示是否都有对应 API
│   ├── 检查: 每个 API 响应字段是否被前端使用
│   └── 产出: {项目名}-API契约对齐确认书-v{x}.md
│
├── 2. 数据流追溯检查
│   ├── 前端展示字段 ↔ API 响应字段 ↔ 数据库字段 三者映射
│   ├── 检查: 字段类型、格式、枚举值是否一致
│   ├── 检查: 必填/可选规则是否一致
│   └── 产出: {项目名}-数据流追溯检查表-v{x}.md
│
└── 3. 对齐确认
    ├── 准入条件: API 契约对齐 + 数据流追溯 全部通过
    ├── 确认产出: {项目名}-前后端对齐确认书-v{x}.md
    └── 确认后前后端设计锁定，进入 Step 3 编码阶段
```

### 闭环规则

- **不通过即返回**：任何一步检查不通过，必须返回对应设计阶段修复，修复后重新执行对应步骤，不得跳过。
- **创建与验证分离**：
  - 前端：原型创建由 `frontend-design` / `prototyping` 负责，原型验证由 `prototype-coverage` 负责
  - 后端：设计创建由 `api-design` / `sql-database` 负责，设计验证由 `design-stage-execution` 矩阵管控
- **前后端对齐为强制门禁**：未通过 API 契约对齐和数据流追溯检查，不得进入编码阶段。
- **自动化触发**：
  - `prototype-coverage` 在"原型设计说明"产出后自动触发
  - 后端覆盖检查在"API 接口设计文档"产出后自动触发
  - 前后端对齐检查在前端和后端设计评审均通过后自动触发

## 四、具体实施规范

> 本章节分为**前端部分**（4.1-4.6）和**后端部分**（4.7-4.11）。前端部分由 `prototype-coverage` 技能执行，后端部分由 `design-stage-execution` 矩阵管控。

### 4.1 前端页面清单（Page Inventory）

#### 4.1.1 定义

前端页面清单是从需求文档中系统提取的**所有前端页面（含弹窗、抽屉、浮层）的汇总表**，是检查原型覆盖率的基准。

#### 4.1.2 清单结构

```markdown

### 统计概览
- 总页面数: 23
- P0 页面数: 12
- P1 页面数: 8
- P2 页面数: 3
- 已原型覆盖: 20 (87%)
- 未原型覆盖: 3

### 页面明细

| 页面ID | 页面名称 | 路由/URL | 用户角色 | 对应需求ID | 优先级 | 原型文件 | 原型状态 | 评审状态 |
|---|---|---|---|---|---|---|---|---|
| PG-001 | 登录页 | /login | 所有用户 | REQ-001 | P0 | prototype/login.html | 已设计 | 已通过 |
| PG-002 | 忘记密码页 | /forgot-password | 所有用户 | REQ-001 | P0 | prototype/forgot.html | 已设计 | 已通过 |

| ... | ... | ... | ... | ... | ... | ... | ... | ... |

### 入口-出口关系图

```text
登录页 (PG-001)
  → 成功 → 仪表盘首页 (PG-003)
  → 忘记密码 → 忘记密码页 (PG-002)

仪表盘首页 (PG-003)
  → 导出报表 → 导出确认弹窗 (PG-004)
  → 查看详情 → 报表详情页 (PG-005)
  → 退出登录 → 登录页 (PG-001)
```

### 未覆盖页面跟踪

| 页面ID | 页面名称 | 优先级 | 未覆盖原因 | 预计完成时间 | 责任人 |
|---|---|---|---|---|---|
| PG-004 | 导出确认弹窗 | P1 | 需求刚变更，新增页面 | 2026-07-02 | 张三 |
```

#### 4.1.3 生成规则

1. **从需求文档提取**：每个涉及用户界面的用户故事（User Story）必须映射到至少一个页面或弹窗。
2. **统一编号**：页面ID格式为 `PG-{三位数字}`，弹窗为 `MD-{三位数字}`，抽屉为 `DW-{三位数字}`。
3. **入口-出口必填**：每个页面必须列出所有可能的入口来源和出口去向。
4. **优先级继承**：页面优先级不低于其对应需求的优先级。

#### 4.1.4 通过标准

- P0 页面：原型覆盖率 100%
- P1 页面：原型覆盖率 >= 80%
- P2 页面：原型覆盖率 >= 50%，或记录"不适用"理由
- 任何"未覆盖"项必须有明确的完成计划和责任人

### 4.2 需求-设计追溯矩阵增强

#### 4.2.1 在现有矩阵基础上增加三列

| 新增列 | 说明 | 填写规则 |
|---|---|---|
| **涉及页面** | 该需求涉及的所有页面ID（引用页面清单） | 多个页面用逗号分隔 |
| **原型状态** | 涉及页面的原型整体状态 | 全部已设计 / 部分待设计 / 全部待设计 / 不适用 |
| **测试关注点** | 从设计角度预埋的测试重点 | 如"边界值：最多支持100条记录"、"并发：多标签页状态同步" |

#### 4.2.2 增强后矩阵示例

| 需求ID | 用户故事 | 涉及页面 | 原型状态 | 测试关注点 | 交互状态 | 评审状态 |
|---|---|---|---|---|---|---|

### 4.3 交互状态覆盖检查

#### 4.3.1 每个页面必须覆盖的状态

| 状态类型 | 定义 | 示例 | 强制要求 |
|---|---|---|---|
| **空态（Empty State）** | 页面/列表无数据时的展示 | 空列表提示"暂无数据，点击添加" | P0 页面强制 |
| **加载态（Loading State）** | 数据正在加载时的展示 | Skeleton 骨架屏、Loading  spinner | P0 页面强制 |
| **错误态（Error State）** | 加载失败或操作失败时的展示 | 网络错误提示、权限不足提示 | P0 页面强制 |
| **成功态（Success State）** | 操作成功后的展示 | 保存成功 Toast、提交成功跳转 | P0 页面强制 |
| **边界态（Edge Case）** | 极端数据量或极端条件下的展示 | 表格横向滚动、超长文本截断 | P0/P1 建议 |
| **权限态（Permission State）** | 无权限时的展示 | "您无权查看此页面"、按钮禁用 | 涉及权限时强制 |

```markdown

| 页面ID | 页面名称 | 空态 | 加载态 | 错误态 | 成功态 | 边界态 | 权限态 | 检查结论 |
|---|---|---|---|---|---|---|---|---|
| PG-001 | 登录页 | ✓ | ✓ | ✓ | ✓ | ✓ | N/A | 通过 |
| PG-003 | 仪表盘首页 | ✓ | ✓ | ✗ | ✓ | ✗ | ✓ | 不通过：缺少错误态、边界态 |
```

#### 4.3.3 通过标准

- P0 页面：空态、加载态、错误态、成功态 四种状态必须全部覆盖。
- P1 页面：至少覆盖空态、错误态 两种状态。
- 涉及权限的页面：必须覆盖权限态。

### 4.4 原型走查（Prototype Walkthrough）

#### 4.4.1 定义

原型走查是**以用户角色视角，按真实业务场景在原型中模拟操作**，目的是暴露页面间的流程断点、逻辑漏洞和交互矛盾。

#### 4.4.2 走查规则

1. **按角色分组**：每个主要用户角色（如管理员、普通用户、访客）独立走查。
2. **选择核心路径**：每个角色选择 3-5 条最高频的核心用户路径。
3. **完整模拟**：从入口页面开始，一步一步点击/操作，记录每一步的预期结果和实际原型表现。

### 4.5 用例场景演练（Scenario-Based Validation）

#### 4.5.1 定义

用例场景演练是**基于需求文档中的用例规约，在原型中逐条验证基本流程和所有异常分支**，确保原型与需求的一致性。

#### 4.5.2 演练规则

1. **覆盖所有 P0 用例**：每个 P0 用例必须在原型中完整演练一遍。
2. **基本流程 + 异常分支**：不仅验证"正常怎么走"，还要验证"异常怎么办"。
3. **前置条件验证**：演练开始前确认前置条件是否满足（如"已登录"、"购物车有商品"）。
4. **后置状态确认**：演练结束后确认系统状态是否符合预期（如"订单状态=已支付"、"库存-1"）。

### 4.6 元素级交互标注

#### 4.6.1 定义

元素级交互标注是对**页面中每个可交互元素**（按钮、链接、输入框、下拉框等）的详细行为说明，确保前端开发时不遗漏交互细节。

#### 4.6.2 标注规范

每个可交互元素必须标注以下信息：

| 属性 | 说明 | 示例 |
|---|---|---|
| **触发事件** | 用户如何触发（click / hover / focus / blur / change / submit） | click |
| **前置条件** | 什么情况下元素可用/不可用 | 已登录且拥有编辑权限 |

### 4.9 数据模型对齐检查

#### 4.9.1 定义

数据模型对齐检查是验证数据库设计与前端展示需求、API 契约三者之间的一致性，防止联调阶段因字段不一致导致返工。

#### 4.9.2 对齐维度

| 对齐对象 | 检查内容 | 示例 |
|---|---|---|
| **数据库 ↔ API 响应** | 数据库字段名、类型、约束是否与 API 响应一致 | 数据库 `user_name` vs API `username`（不一致） |

### 4.10 业务状态机覆盖检查

#### 4.10.1 定义

#### 4.10.2 必须覆盖的内容

#### 4.10.3 状态机文档格式

```markdown
## 订单状态机

### 状态定义
- 待支付 (pending)
- 已支付 (paid)
- 已发货 (shipped)
- 已签收 (delivered)
- 已完成 (completed)
- 已取消 (cancelled)
- 退款中 (refunding)
- 已退款 (refunded)

### 状态转换规则

| 当前状态 | 触发事件 | 目标状态 | 前置条件 | 后置动作 | 异常处理 |
|---|---|---|---|---|---|
| pending | 支付成功 | paid | 支付金额 = 订单金额 | 扣减库存 | 库存不足 → cancelled |
| pending | 超时未支付 | cancelled | 创建时间 > 30分钟 | 释放库存 | — |
| paid | 发货 | shipped | 库存已扣减 | 记录物流单号 | 物流接口异常 → 重试3次 |
| shipped | 签收 | delivered | 物流状态 = 已签收 | 触发评价提醒 | — |
| delivered | 确认完成 | completed | 签收后 > 7天 或 用户手动确认 | 发放积分 | — |
| paid | 用户申请退款 | refunding | 未发货 或 签收后 < 7天 | 冻结订单 | — |
| refunding | 退款成功 | refunded | 管理员审批通过 | 返还库存、退款 | 退款失败 → 人工处理 |

### 异常分支
- **并发下单超卖**：库存扣减时加乐观锁，失败则返回"库存不足"
- **支付回调延迟**：支付状态以支付网关回调为准，最多容忍 5 分钟延迟
- **重复支付**：同一订单允许多次支付尝试，但只有第一次成功有效
```

#### 4.10.4 通过标准

- P0 业务实体：所有状态转换路径 100% 覆盖，异常分支 >= 80%

## 七、设计规范矩阵增强

### 7.1 新增设计类别

在现有 `design-stage-execution` 设计规范矩阵中新增以下行：

| 设计类别 | 执行技能 | 必须执行内容 | 通过标准 | 强制产出 |
|---|---|---|---|---|
| **前端页面清单建立** | `prototype-coverage` | 1. 从需求文档提取所有涉及界面的需求项；2. 建立"页面清单"，包含页面ID、名称、路由、角色、对应需求、优先级；3. 建立页面间的入口-出口关系图 | 所有 P0/P1 涉及界面的需求项均有对应页面记录；无孤立页面 | 前端页面清单 |
| **前端原型覆盖检查** | `prototype-coverage` | 1. 从页面清单提取所有 P0/P1 页面；2. 检查每个页面是否有对应原型文件；3. 检查每个页面的关键交互状态（空态、加载态、错误态、成功态）是否有原型覆盖 | 所有 P0 页面 100% 原型覆盖且四种状态齐全；P1 页面 >= 80% 覆盖 | 前端原型覆盖检查表 |
| **原型走查** | `prototype-coverage` | 1. 按用户角色分组；2. 每个角色选择 3-5 条核心用户路径；3. 用原型模拟完整操作，记录断点 | 所有 P0 用户路径无严重断点；P1 路径断点有修复计划 | 原型走查记录 |
| **用例场景演练** | `prototype-coverage` | 1. 从需求文档提取所有用例规约；2. 每个 P0 用例在原型中完整演练基本流程 + 所有异常分支；3. 验证前置条件和后置状态 | P0 用例基本流程 100% 通过，异常分支覆盖率 >= 80% | 用例场景演练报告 |
| **元素级交互标注** | `prototype-coverage` | 1. 识别 P0 页面中所有可交互元素；2. 对每个主操作按钮和表单输入框标注触发事件、条件判断、成功路径、错误处理、边界限制 | P0 页面主操作按钮和表单输入框 100% 标注；P1 涉及安全/资金的操作 100% 标注 | 元素级交互标注 |
| **设计-测试预映射** | `prototype-coverage` | 1. 从页面清单、状态检查表、走查记录、场景演练报告中提取测试关注点；2. 按功能/性能/安全/兼容/并发等分类；3. 标注优先级和预估测试方法 | 所有 P0 需求项均有至少一个测试关注点；测试代表在设计评审时确认 | 设计-测试预映射表 |
| **API 契约覆盖检查** | `design-stage-execution` + `api-design` | 1. 检查每个 API 的路径、方法、请求参数、响应结构、异常响应、边界条件、版本兼容、降级策略、鉴权方式；2. 建立 API 契约覆盖检查表 | P0 API 所有检查项 100% 覆盖；P1 API 核心检查项覆盖 | API 契约覆盖检查表 |
| **数据模型对齐检查** | `design-stage-execution` + `sql-database` / `mongodb` | 1. 对比数据库字段与 API 响应字段的一致性；2. 对比 API 响应字段与前端展示字段的一致性；3. 检查枚举值、必填规则、数据格式的一致性 | P0 数据流三者映射 100% 一致；P1 核心字段一致 | 数据模型对齐检查表 |
| **业务状态机覆盖检查** | `design-stage-execution` | 1. 定义核心业务实体的所有状态、初始状态、终止状态；2. 列出所有正常转换和异常转换；3. 覆盖超时处理和并发冲突场景 | P0 实体所有转换路径 100% 覆盖，异常分支 >= 80% | 业务状态机文档 |
| **安全与权限设计检查** | `design-stage-execution` + `security-best-practices` | 1. 梳理鉴权方式、权限粒度、数据权限；2. 识别敏感字段并制定处理策略；3. 规划输入校验、审计日志、加密策略 | 所有强制检查项 100% 通过 | 安全设计检查表 |
| **前后端 API 契约对齐检查** | `api-contract-management` | 1. 交叉验证前端页面清单与后端 API 列表；2. 验证字段名、类型、格式、分页策略、错误处理的一致性；3. 前后端负责人签字确认 | P0 页面所需 API 100% 对齐；字段不一致有统一方案 | 前后端 API 契约对齐确认书 |

### 7.2 新增强制规则

在现有 7 条强制规则后增加：

**8. 不得遗漏 P0/P1 前端页面原型**：任何涉及用户界面的 P0/P1 需求，如果没有对应页面清单记录和原型覆盖，设计阶段不得完成。

**9. 原型必须覆盖关键交互状态**：每个有原型的 P0 页面，必须至少覆盖空态、加载态、错误态、成功态四种状态；涉及权限的页面必须覆盖权限态。

**10. 原型走查不得跳过核心路径**：所有 P0 用户路径必须通过原型走查验证，走查不通过不得进入设计评审。

**11. 用例场景演练必须覆盖异常分支**：每个 P0 用例的场景演练必须覆盖所有异常分支，异常分支覆盖率低于 80% 不得进入设计评审。

**12. 设计-测试预映射必须在设计评审前完成**：设计-测试预映射表必须在设计评审会议前提交给测试代表审阅，测试代表签字确认后方可进行设计评审。

**13. API 契约必须覆盖异常响应和边界条件**：每个 P0 API 必须定义完整的异常响应、边界条件和降级策略，缺少任一项不得进入后端设计评审。

**14. 数据模型必须三方对齐**：数据库设计、API 契约、前端展示三者必须在设计阶段对齐，任何不一致必须记录修复方案，未对齐不得进入编码阶段。

**15. 业务状态机必须覆盖异常分支**：核心业务实体的状态机必须覆盖所有异常转换路径，异常分支覆盖率低于 80% 不得进入后端设计评审。

**16. 安全设计不通过不得编码**：安全与权限设计检查不通过，不得进入编码阶段。

**17. 前后端未对齐不得编码**：未通过 API 契约对齐检查和数据流追溯检查，不得进入编码阶段。

**18. API 契约偏差必须记录和批准**：编码阶段任何 API 契约变更必须更新设计文档并重新走对齐流程，擅自修改契约必须返工。

## 十、附录

### 10.1 术语表

| 术语 | 定义 |
|---|---|
| 页面清单（Page Inventory） | 项目中所有前端页面（含弹窗、抽屉）的汇总表，是原型覆盖检查的基准 |
| 原型走查（Prototype Walkthrough） | 以用户角色视角，在原型中模拟真实操作，暴露流程断点 |
| 用例场景演练（Scenario-Based Validation） | 基于用例规约，在原型中验证基本流程和异常分支 |
| 元素级交互标注 | 对页面中每个可交互元素的触发事件、条件判断、成功路径、错误处理等详细说明 |
| 设计-测试预映射 | 在设计阶段从设计文档中提取测试关注点，为测试用例设计提供输入 |
| 空态（Empty State） | 页面/列表无数据时的展示状态 |
| 加载态（Loading State） | 数据正在加载时的展示状态 |
| 错误态（Error State） | 加载失败或操作失败时的展示状态 |
| 成功态（Success State） | 操作成功后的展示状态 |
| 边界态（Edge Case） | 极端数据量或极端条件下的展示状态 |
| 权限态（Permission State） | 无权限时的展示状态 |
| API 契约（API Contract） | 前后端约定的接口规范，包括路径、参数、响应、错误码等 |
| 数据模型对齐（Data Model Alignment） | 验证数据库设计、API 契约、前端展示三者的一致性 |
| 业务状态机（Business State Machine） | 核心业务实体的状态定义、转换规则和异常分支的可视化文档 |
| 安全设计检查（Security Design Review） | 对鉴权、权限、敏感字段、输入校验、审计日志、加密策略的系统化梳理 |
| API 契约对齐（API Contract Alignment） | 前端页面清单与后端 API 设计的交叉验证，确保接口契约在编码前锁定 |
