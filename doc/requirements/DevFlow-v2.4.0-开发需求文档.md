## 1. 文档概述

### 1.1 文档目的

本文档是 DevFlow v2.4.0 版本的**开发需求文档**（Development Requirements Document），是 Step 1 需求分析阶段的主文档。本文档从开发视角将用户需求转化为可实施的功能需求、非功能需求、数据需求、权限安全需求和接口集成需求，并明确范围边界、验收标准和优先级，为后续设计（Step 2）和编码（Step 3）提供完整的开发输入。

### 1.2 读者对象

| 角色 | 阅读目的 |
|---|---|
| 项目负责人 / 架构师 | 确认需求分解的完整性和可行性 |
| 内容架构师 | 基于功能需求设计技能体系结构变更 |
| 开发负责人 | 基于功能需求制定技术方案和开发计划 |
| 质量负责人 | 基于验收标准制定测试策略和测试计划 |
| 测试负责人 | 基于功能需求和验收标准编写测试用例 |
| 文档负责人 | 基于功能描述编写用户手册和 API 文档 |

### 1.3 术语定义

| 术语 | 定义 |

| 平台 | 支持 DevFlow 运行的 AI 编程助手，包括 TRAE IDE、Claude Code、Cursor、Codex CLI |

## 3. 功能需求

### 3.1 VR-001 交互式安装向导

| 属性 | 值 |
|---|---|
| **需求 ID** | VR-001 |
| **需求名称** | 交互式安装向导 |
| **优先级** | P0（阻塞发布） |
| **痛点类别** | 上手体验 |
| **关联技术债务** | TD-006（安装脚本跨平台差异） |
| **预估工时** | 5 人天 |

#### 3.1.1 功能描述

开发交互式安装向导脚本，作为 DevFlow 安装的主入口。安装向导自动检测用户环境，通过交互式问答引导用户完成项目配置，一键安装全部技能文件、模板文件和配置文件到目标位置，并提供全过程的进度反馈和错误恢复能力。

**核心功能模块**：

1. **环境自动检测**
   - 检测操作系统类型和版本（Windows 10/11、macOS 12+、Ubuntu 20.04+/CentOS 7+）
   - 检测 Git 是否安装及版本号
   - 检测 Node.js 是否安装及版本号
   - 检测网络连通性（GitHub/GitLab 远程仓库可达性）
   - 检测已有 DevFlow 安装版本（读取 `version.json`）

2. **交互式引导配置**
   - 远程仓库地址输入（支持 GitHub、GitLab、Gitee 等）
   - 分支策略选择（git-flow / feature-branch / trunk-based），每种策略附带简要说明
   - 项目基本信息输入（项目名称、项目描述）
   - 团队规模选择（个人 / 小队 / 大团队）

3. **一键安装**
   - 复制全部技能文件到 TRAE skills 目录（按 L1/L2/L3/Orchestrator 分层存放）
   - 复制全部模板文件到 `.devflow/templates/`
   - 生成 `.devflow/config.json`（基于用户输入的配置信息）
   - 生成 `.devflow/state.json`（初始状态：Step 0 完成）
   - 初始化 Git 本地仓库（如尚未初始化）

4. **进度反馈**
   - 步骤级进度条（如 `[3/7] 正在安装技能文件...`）
   - 百分比进度显示
   - 当前操作的详细描述文本
   - 预计剩余时间估算

5. **错误恢复**
   - 检测失败：跳过可选组件（如 Node.js 不可用时跳过相关验证），提示用户
   - 网络失败：回退到本地已有文件，提示用户后续可手动更新
   - 已存在覆盖：自动备份已有版本后再覆盖，备份目录为 `.devflow/backup/{timestamp}/`

#### 3.1.2 输入 / 输出

| 类型 | 内容 |
|---|---|
| **输入** | 用户通过终端输入的配置信息（仓库地址、分支策略、项目信息等）；环境检测结果 |
| **输出** | 安装到目标目录的技能文件、模板文件、配置文件；安装日志；安装结果摘要 |

#### 3.1.3 处理逻辑要点

1. 按顺序执行环境检测，检测结果缓存供后续步骤使用
2. 交互式问答采用合理默认值，用户可直接回车使用默认选项
3. 安装步骤串行执行，每个步骤完成后输出进度更新
4. 关键步骤（文件复制、配置生成）执行前进行前置条件校验
5. 每个步骤的成功/失败状态记录到安装日志
6. 安装完成后输出结果摘要（安装路径、安装版本、技能数量、模板数量）

#### 3.1.4 状态与转换

```
[启动] → [环境检测] → [交互配置] → [安装执行] → [安装验证] → [完成]
                    ↓                ↓              ↓
                  [跳过可选]      [错误恢复]    [输出报告]
```

| 状态 | 触发条件 | 后续动作 |
|---|---|---|
| 环境检测 | 安装向导启动 | 检测 OS、Git、Node.js、网络、已有版本 |
| 交互配置 | 环境检测完成 | 引导用户输入配置信息 |
| 安装执行 | 用户确认配置 | 执行文件复制和配置生成 |
| 安装验证 | 安装执行完成 | 调用安装验证脚本（VR-005）检查完整性 |
| 完成 | 验证通过 | 输出结果摘要，退出 |
| 错误恢复 | 任一步骤失败 | 根据错误类型执行恢复策略 |

#### 3.1.5 错误处理

| 错误场景 | 错误级别 | 处理策略 |
|---|---|---|
| Git 未安装 | 致命 | 终止安装，提示用户安装 Git 后重试 |
| 目标目录无写权限 | 致命 | 终止安装，提示用户检查权限 |
| 远程仓库不可达 | 警告 | 跳过远程操作，使用本地文件完成安装 |
| 已有 DevFlow 版本 | 信息 | 备份已有版本，继续安装 |
| 技能文件复制失败 | 警告 | 记录失败文件，继续安装其余文件，最终报告列出失败项 |
| Node.js 未安装 | 警告 | 跳过 Node.js 相关功能，继续安装 |
| 配置文件生成失败 | 致命 | 终止安装，提示用户检查磁盘空间 |

#### 3.1.6 约束条件

| 约束项 | 约束内容 |
|---|---|
| 安装时间 | 全流程 <= 10 分钟（含环境检测、用户交互、文件安装、验证） |
| 平台支持 | Windows 10/11（PowerShell 5+）、macOS 12+（zsh/bash）、Linux（bash） |
| 权限要求 | 不需要 root/管理员权限，仅需用户目录写权限 |
| 文件编码 | 安装脚本统一使用 UTF-8 编码（no BOM） |
| 网络要求 | 支持离线安装（远程仓库不可达时回退到本地文件） |

### 3.2 VR-002 项目初始化向导增强

| 属性 | 值 |
|---|---|
| **需求 ID** | VR-002 |
| **需求名称** | 项目初始化向导增强 |
| **优先级** | P0（阻塞发布） |
| **痛点类别** | 上手体验 |
| **关联技术债务** | TD-007（Orchestrator 错误处理不完善） |
| **预估工时** | 3 人天 |

#### 3.2.1 功能描述

增强项目初始化向导（devflow-init），在现有基础上增加交互式问答、项目阶段自动推断和配置自动生成能力。向导通过交互式问答收集项目信息，结合环境检测自动推断项目所处阶段，并根据问答结果自动生成合理的项目配置文件。

**核心功能模块**：

1. **交互式问答**
   - 项目类型选择：Web 应用 / 移动应用 / 后端服务 / 工具库 / CLI 工具
   - 开发模式选择：敏捷 / 瀑布 / 混合（附带每种模式的简要说明）
   - 团队规模选择：个人 / 小队（2-5 人）/ 大团队（5 人以上）
   - 编程语言选择（可选）：从常见语言列表中选择

2. **项目阶段自动推断**
   - 检测已有文档目录结构（如存在 `doc/requirements/` 则推断已进入需求阶段）
   - 检测 Git 分支名（如存在 `feature/` 前缀则推断已进入设计或编码阶段）
   - 检测已有配置文件（如存在 `.devflow/config.json` 则推断已完成初始化）
   - 检测已有源代码目录结构（如存在 `src/` 则推断已进入编码阶段）
   - 综合推断当前项目所处阶段，并提示用户确认或修正

3. **配置自动生成**
   - 生成 `.devflow/config.json`：项目名称、项目类型、开发模式、团队规模、分支策略、编程语言等
   - 生成 `.devflow/state.json`：当前阶段、已完成阶段列表、阶段切换记录
   - 配置内容基于用户回答和推断结果自动填充

4. **合理默认值**
   - 个人项目：默认 agile + feature-branch + 小团队
   - 小队项目：默认 agile + git-flow + 小队
   - 大团队项目：默认 agile + git-flow + 大团队
   - 用户可随时修改默认值

#### 3.2.2 输入 / 输出

| 类型 | 内容 |
|---|---|
| **输入** | 用户交互输入（项目类型、开发模式、团队规模等）；环境检测结果（已有文档、Git 分支、配置文件） |
| **输出** | `.devflow/config.json` 配置文件；`.devflow/state.json` 状态文件；推断结果和确认信息 |

#### 3.2.3 处理逻辑要点

1. 首先执行环境推断，收集项目上下文信息
2. 根据推断结果预设默认值，减少用户输入
3. 交互问答按顺序进行，每步提供合理默认选项
4. 推断结果与用户输入冲突时，以用户输入为准
5. 配置生成采用模板填充方式，确保格式一致性
6. 生成的配置文件需要通过 JSON 语法验证

#### 3.2.4 状态与转换

```
[启动] → [环境推断] → [交互问答] → [确认推断] → [配置生成] → [完成]
                     ↓                 ↓
                   [无历史]          [用户修正]
```

| 状态 | 触发条件 | 后续动作 |
|---|---|---|
| 环境推断 | 初始化向导启动 | 扫描项目目录结构和 Git 状态 |
| 交互问答 | 环境推断完成 | 逐项收集项目信息 |
| 确认推断 | 问答完成 | 展示综合推断结果，等待用户确认 |
| 配置生成 | 用户确认 | 生成 config.json 和 state.json |
| 完成 | 配置生成成功 | 输出结果摘要 |

#### 3.2.5 错误处理

| 错误场景 | 错误级别 | 处理策略 |
|---|---|---|
| Git 仓库未初始化 | 警告 | 提示用户先初始化 Git 仓库，或跳过 Git 相关检测 |
| `.devflow/` 目录已存在 | 信息 | 读取已有配置作为默认值，询问用户是否覆盖 |
| 配置文件 JSON 生成失败 | 致命 | 终止，提示错误信息 |
| 用户中断交互 | 信息 | 保存已收集的信息，提示用户可再次运行完成初始化 |

#### 3.2.6 约束条件

| 约束项 | 约束内容 |
|---|---|
| 执行时间 | 全流程 <= 2 分钟（含环境检测、用户交互、配置生成） |
| 兼容性 | 支持 Windows/macOS/Linux 三平台 |
| 配置格式 | config.json 和 state.json 严格遵循 JSON 规范 |
| 向后兼容 | 新版配置文件兼容 v2.3.2 已有配置结构 |

### 3.3 VR-011 技能文件质量审查和统一

| 属性 | 值 |
|---|---|
| **需求 ID** | VR-011 |
| **需求名称** | 技能文件质量审查和统一 |
| **优先级** | P0（阻塞发布） |
| **痛点类别** | 内容质量 |
| **关联技术债务** | TD-001（技能文件格式不统一）、TD-004（部分模板内容过时） |
| **预估工时** | 4 人天 |

#### 3.3.1 功能描述

对 DevFlow 当前全部 22 个技能文件（3 L1 + 6 L2 + 10 L3 + 3 Orchestrator）进行系统性的质量审查，消除格式不一致、内容重复、内容矛盾等问题，确保全部技能文件达到统一的编写规范标准。

**审查维度**：

1. **格式一致性审查**
   - 标题层级结构是否符合层级规范（一级标题为技能名称，二级标题为章节名）
   - 表格格式是否统一（对齐方式、列名规范）
   - 代码块标注是否正确（语言标识符是否准确）
   - 列表缩进是否一致
   - 文件编码是否统一（UTF-8，no BOM）

2. **术语统一性审查**
   - 同一概念是否在所有技能中使用统一术语
   - 阶段名称是否统一（版本规划 / 需求分析 / 设计 / 编码 / 测试 / 部署）
   - 技能层级名称是否统一（L1/L2/L3/Orchestrator）

3. **交叉引用准确性审查**
   - 引用的其他技能名称是否正确
   - 引用的文档路径是否有效
   - 引用的模板名称是否存在

4. **示例代码正确性审查**
   - 示例命令是否可执行
   - 示例文件路径是否存在
   - 示例代码语法是否正确

5. **内容重复检测**
   - 不同技能中是否存在大段重复内容（>= 80% 相似度视为重复）
   - 重复内容是否合理（如速查表引用允许重复）或需要抽取为共享内容

6. **内容矛盾检测**
   - 不同技能对同一问题的描述是否矛盾
   - L2 技能的描述与被引用的 L3 技能内容是否一致

**审查对象**：22 个现有技能文件

- L1（3 个）：project-development-workflow、project-document-management、project-role-management
- L2（6 个）：version-planning-stage-execution、requirements-stage-execution、design-stage-execution、coding-stage-execution、testing-stage-execution、operations-stage-execution
- L3（10 个）：cicd-pipeline-management、code-logic-review、code-static-quality-check、code-version-backup-management、observability-standards、project-coding-conventions、project-document-templates
- Orchestrator（3 个）：devflow-init、devflow-phase-manager、devflow-project-config

#### 3.3.2 输入 / 输出

| 类型 | 内容 |
|---|---|
| **输入** | 22 个技能文件（SKILL.md）；SKILL.md 编写规范（VR-012 产出） |
| **输出** | 审查报告（Markdown 格式）：问题列表、严重级别（P0/P1/P2）、修复建议；修复后的技能文件 |

#### 3.3.3 处理逻辑要点

1. 按审查维度逐项扫描全部技能文件
2. 每个发现的问题记录严重级别：
   - **P0（致命）**：内容矛盾导致 AI 助手行为异常
   - **P1（严重）**：格式严重不一致或引用断裂
   - **P2（一般）**：轻微格式差异或术语不统一
3. 对每个问题给出具体修复建议
4. 修复后重新审查，确保问题已解决且未引入新问题
