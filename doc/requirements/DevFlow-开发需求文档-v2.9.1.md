## 4. 业务流程

### 4.1 首次安装流程 (F-04)

```
用户运行 install.ps1
  → 检测本地副本是否存在
    → 不存在 → download-devflow 克隆源码
    → 已存在 → 提示用户选择（更新 / 跳过 / 取消）
  → setup.ps1 安装技能到 IDE 系统目录
  → 复制 devflow-config.json 到 IDE 系统目录
  → 安装完成提示
```

### 4.2 增量更新流程 (F-05)

```
用户运行 update.ps1
  → 读取本地副本 devflow-config.json 版本
  → 读取 IDE 系统目录 devflow-config.json 版本
  → 版本相同 → 提示已是最新，退出
  → 版本不同 / 有技能文件变更
    → 卸载旧技能
    → 安装新技能
    → 更新 IDE devflow-config.json
    → 输出更新摘要
```

### 4.3 旧配置迁移流程 (F-03)

```
devflow-init / update.ps1 启动
  → 检测新路径配置文件是否存在
    → 存在 → 正常使用，跳过迁移
    → 不存在 → 检测旧路径配置文件
      → 旧文件也不存在 → 首次初始化，创建新配置
      → 旧文件存在 → 执行迁移
        → 重命名 / 复制到新路径
        → 验证新文件完整性
        → 备份旧文件（加 .bak 后缀）
        → 输出迁移成功提示
```

### 4.4 阶段产出物验证流程 (F-07)

```
阶段任务完成（Step X 结束前）
  → 生成本阶段产出物清单（从技能文档的"必出文档"列表）
  → 使用 LS / Glob 工具列出目标目录中的所有文件
  → 逐一核对清单中的文件是否实际存在
    → 全部存在 → 验证通过，阶段可关闭
    → 有缺失 → 验证不通过
      → 列出缺失文件清单
      → 必须补齐所有缺失文件
      → 重新执行验证
  → 验证结果（含工具实际输出）作为阶段完成的强制证据
```

### 4.5 全阶段产出物盘点流程 (F-09)

```
Step 5 全流程闭环审计
  → 汇总 6 个阶段（Step 0~5）的所有产出物清单
  → 生成全阶段产出物盘点总表
  → 使用 Glob / LS 工具逐一验证每个文件的存在性
  → 统计：
    - 应产出文件总数
    - 实际存在文件数
    - 缺失文件数
    - 空输出率 = 缺失 / 应产出
  → 空输出率 = 0% → 盘点通过，允许发布
  → 空输出率 > 0% → 盘点不通过
    → 列出所有缺失文件及其所属阶段
    → 回退到对应阶段补齐
    → 补齐后重新盘点
```

## 5. 功能需求

### F-01：devflow-config.json 框架配置文件

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-01 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-001 |
| **来源** | SRC-01 |

**描述**：
DevFlow 框架的权威配置文件（source of truth），存放框架自身的元数据。作为所有 DevFlow 版本信息和技能清单的唯一可信来源。

**功能点**：

1. `devflow-plugin/devflow-config.json` 为源码中的权威配置文件（source of truth）
2. IDE 系统目录 `devflow-config.json` 为运行时副本，由 setup/update 脚本从源码复制
3. 文件内容包含：
   - 基本信息：name, devflowVersion, description, author, license, homepage, repository
   - 技能层级：layers (L1/L2/L3/orchestrator)
   - 技能清单：skills 数组（合并原 devflow-manifest.json）
   - 元数据：_meta.sourceOfTruth = true, _meta.generatedAt, _meta.minTraeVersion
4. 所有脚本和技能文档读取框架版本时，统一从 IDE 系统目录 `devflow-config.json` 读取
5. `devflow-manifest.json` 合并后删除

### F-02：project-config.json 项目配置文件

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-02 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-001 |
| **来源** | SRC-01 |

**描述**：
每个项目独立的配置文件，存放项目自身的元数据和 DevFlow 使用配置。

**功能点**：

1. `.devflow/project-config.json` 为项目配置文件唯一位置
2. 原 `.devflow/config.json` 重命名为 `.devflow/project-config.json`
3. 原项目根 `version.json` 的关键字段（name, devflowVersion）合并进 project-config.json
4. 文件内容包含：
   - 项目信息：project, projectVersion
   - 分支策略：branchStrategy
   - 远程仓库：remote.origin, remote.backup
   - 备份配置：backup.type, backup.environments, backup.schedule
5. `devflow-project-config` 技能全部引用更新为 `project-config.json`
6. `devflow-init` 创建项目配置时，直接创建 `project-config.json`
7. 项目根 `version.json` 合并后删除
8. `.devflow/version.json` （如存在）合并后删除

### F-03：旧路径自动迁移（向后兼容）

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-03 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-001 |
| **来源** | SRC-01 |

**描述**：
确保 v2.9.0 及更早版本的用户升级到 v2.9.1 后，配置文件自动迁移，无需手动修改。

**功能点**：

1. devflow-init 启动时检测：
   - 新路径 `.devflow/project-config.json` 不存在
   - 旧路径 `.devflow/config.json` 存在
   → 自动执行迁移
2. 迁移步骤：
   - 读取旧文件内容
   - 合并项目根 `version.json` 字段（如有）
   - 写入新路径 `project-config.json`
   - 旧文件加 `.bak` 后缀备份
   - 输出迁移成功日志
3. update.ps1 启动时检测 IDE 系统目录：
   - 新路径 `devflow-config.json` 不存在
   - 旧路径 `devflow-plugin-config/version.json` 存在
   → 自动执行迁移
4. 迁移失败时保留旧文件，输出错误信息，不破坏用户数据
5. 新旧文件同时存在时，以新文件为准，跳过迁移

### F-05：update.ps1 增量更新入口

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-05 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-002 |
| **来源** | SRC-02 |

**描述**：
已安装用户更新 DevFlow 的统一入口，支持版本更新和本地修改同步两种场景。

**功能点**：

1. `update.ps1` 为更新的唯一入口
2. 合并原 `sync-skills.ps1` 的全部功能
3. 支持两种模式：
   - **版本更新模式**：从云端拉取最新版，更新本地副本 + IDE 系统目录
   - **本地同步模式**：本地副本有修改，同步到 IDE 系统目录（开发者常用）
4. 更新流程：
   - 读取本地副本 devflow-config.json 版本
   - 读取 IDE 系统目录 devflow-config.json 版本
   - 比较差异（版本号 + 技能文件哈希）
   - 有差异 → 执行更新
   - 无差异 → 提示已是最新
5. 更新内容：
   - 卸载旧版本技能文件
   - 安装新版本技能文件
   - 更新 IDE devflow-config.json
   - 执行 BOM 修复
6. 支持 DryRun 模式，预览变更
7. `sync-skills.ps1` 合并后删除

### F-07：阶段产出物存在性验证门禁

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-07 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-003 |
| **来源** | SRC-03 |

**描述**：
在 6 个阶段（Step 0~5）的完成标准中新增"产出物存在性验证"强制规则，作为阶段关闭的门禁。阶段完成前必须通过 LS/Glob 工具列出目标目录，确认所有产出文件实际存在，杜绝"声称完成但文件未实际创建"的空输出问题。

**功能点**：

1. **6 个阶段全覆盖**：version-planning / requirements / design / coding / testing / operations 六个 L2 阶段执行技能文档全部新增产出物验证门禁
2. **标准化验证模板**：制定统一的"产出物存在性验证"模板，包含：
   - 本阶段必出文档清单
   - 验证工具（LS / Glob）
   - 验证步骤
   - 验证结果记录格式
   - 不通过处置规则
3. **验证时机**：每个阶段完成前、审计前必须执行
4. **证据要求**：验证结果必须包含 LS/Glob 的实际输出列表作为证据，不得仅靠文字描述
5. **不通过处置**：
   - 有缺失文件 → 阶段不得关闭
   - 必须补齐所有缺失文件
   - 重新验证通过后方可进入下一阶段
6. **各阶段必出文档清单**（随技能文档同步更新）：
   - Step 0：单版本规划、Backlog、Phase 计划、评审记录
   - Step 1：需求来源、PRD、追溯矩阵、评审记录、基线说明、评估报告
   - Step 2：系统设计、详细设计、ADR、设计评审
   - Step 3：DevLogReport、代码提交记录、自测报告
   - Step 4：测试计划、测试用例、测试报告、缺陷清单
   - Step 5：Release Note、Changelog、闭环审计报告

### F-08：审计环节产出物存在性核查

| 属性 | 内容 |
|:-----|:-----|
| **需求 ID** | F-08 |
| **优先级** | P1 |
| **对应 Backlog** | BL-291-003 |
| **来源** | SRC-03 |

**描述**：
各阶段的审计检查清单中新增"产出物存在性核查"检查项，作为审计通过的必要条件之一。审计师必须逐一核查所有产出物的实际存在性，确保阶段交付物的真实性。

**功能点**：

1. **6 个阶段审计全覆盖**：每个阶段的审计检查清单均新增"产出物存在性核查"项
2. **核查内容**：
   - 本阶段所有应产出文件是否实际存在
   - 文件路径是否与规范一致
   - 文件内容是否非空（有实际内容，不是空白文件）
3. **核查方法**：
   - 使用 LS/Glob 工具列出目标目录
   - 逐一核对文件名
   - 抽样检查文件大小/内容
4. **核查结论**：
   - 全部存在 → 通过
   - 有缺失 → 不通过，退回补齐
5. **核查记录**：审计报告中必须包含产出物核查结果章节

| **来源** | SRC-03 |

**描述**：
Step 5 全流程闭环审计中新增"全阶段产出物盘点"章节，汇总 6 个阶段的所有产出物，逐一验证存在性，作为版本发布的最终门禁。只有空输出率为 0% 时，才允许版本发布。

**功能点**：

1. **盘点范围**：6 个阶段（Step 0~5）的全部产出物，约 40 份文档
2. **盘点内容**：
   - 生成全阶段产出物总清单（按阶段分组）
   - 逐一验证每个文件的实际存在性
   - 统计应产出数、实存数、缺失数、空输出率
3. **盘点方法**：
   - 使用 Glob 工具按目录模式匹配所有产出文件
   - 与各阶段必出文档清单对比
   - 生成盘点结果表
4. **发布门禁**：
   - 空输出率 = 0% → 盘点通过，允许发布
   - 空输出率 > 0% → 盘点不通过，不得发布
5. **不通过处置**：
   - 列出所有缺失文件及其所属阶段
   - 回退到对应阶段补齐
   - 补齐后重新执行全阶段盘点
6. **盘点报告**：闭环审计报告中必须包含完整的全阶段产出物盘点章节

## 8. 约束与排除项

### 8.1 约束

1. **必须向后兼容**：旧版本用户升级后必须能自动迁移，不得要求手动改配置
2. **source of truth 不变**：框架版本的权威来源仍是源码里的配置文件，IDE 系统目录只是副本
3. **不得影响现有功能**：所有现有功能必须保留，只做重命名和合并，不改业务逻辑
4. **脚本语义不变**：install.ps1 和 update.ps1 的核心语义（首次安装 / 增量更新）与用户预期一致

### 8.2 排除项（不做什么）

1. ❌ 不改变任何业务流程（如 Step 0~5 的执行逻辑）
2. ❌ 不新增功能需求（只做架构精简和重命名）
3. ❌ 不修改 release.ps1（它是 DevFlow 自己发版用的，不是用户安装脚本）
4. ❌ 不改变 state.json 的结构和位置
5. ❌ 不改变文档目录结构和命名规则
