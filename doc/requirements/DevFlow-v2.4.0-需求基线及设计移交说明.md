## 3. 基线变更规则

### 3.1 变更触发条件

进入 Step 2 后，以下情况触发基线变更流程：

1. **需求变更**：新增、删除或修改已批准的需求项（包括功能范围、验收标准的调整）
2. **优先级调整**：P0/P1 优先级的升降级
3. **技术债务变更**：技术债务的增减或优先级调整
4. **依赖/风险变更**：关键依赖关系变化或新增高风险项
5. **范围蔓延**：任何可能导致版本范围扩大的新增需求

### 3.2 变更审批要求

| 变更类型 | 审批级别 | 审批人 |
| --- | --- | --- |
| P0 需求变更 | L3 — 版本 Owner + 需求负责人 + 设计负责人 | jerry.yu |
| P1 需求变更 | L2 — 需求负责人 + 设计负责人 | jerry.yu |
| P2 需求变更 | L1 — 需求负责人 | jerry.yu |
| 技术债务变更 | L2 — 需求负责人 + 设计负责人 | jerry.yu |
| 优先级调整 | L3 — 版本 Owner + 需求负责人 | jerry.yu |
| 依赖/风险变更 | L1 — 需求负责人 | jerry.yu |
| 文档修正（错别字、表述优化） | L0 — 自行修正，记录日志 | — |

### 3.3 变更影响评估要求

每次变更必须包含以下评估内容：

1. **范围影响**：变更是否导致版本范围扩大或缩小
2. **进度影响**：变更是否影响 Phase 迭代计划的里程碑日期
3. **资源影响**：变更是否需要额外的人力或工具投入
4. **质量影响**：变更是否影响已定义的验收标准或成功指标
5. **依赖影响**：变更是否引入新的依赖关系或破坏现有依赖

### 3.4 变更记录要求

所有变更必须：

1. 填写[第 6 节 变更记录](#6-变更记录)表格
2. 同步更新受影响的基线文档（版本号递增）
3. 通知所有干系人（需求负责人、设计负责人、开发负责人）
4. 重新评估变更后的基线完整性

### 4.2 设计阶段关注要点

以下需求项在设计阶段需要特别关注，涉及较复杂的架构设计或技术决策：

#### 4.2.1 VR-001 安装向导（P0）

需要设计以下核心模块：

- **环境检测模块**：自动识别操作系统、Node.js 版本、包管理器、Git 配置等开发环境信息
- **交互式 CLI 框架**：基于 Inquirer.js 或类似库设计友好的命令行交互流程，包括多步骤引导、进度展示、默认值推断
- **错误恢复机制**：处理安装中断、环境不满足、权限不足等异常场景，支持断点续装和回滚

#### 4.2.2 VR-002 初始化增强（P0）

需要设计以下核心逻辑：

- **阶段推断算法**：根据项目目录结构、已有配置文件、Git 历史等信号，智能推断项目当前所处开发阶段
- **配置生成逻辑**：基于推断结果和用户选择，自动生成 `.devflow/` 目录结构及初始配置文件

#### 4.2.3 VR-013 交叉引用检查（P1）

需要设计以下核心数据结构和算法：

- **引用关系数据结构**：定义需求-设计-代码-测试之间的引用关系模型，支持双向查询
- **检查算法**：设计高效的交叉引用完整性检查算法，识别悬挂引用、循环引用、缺失引用等问题

#### 4.2.4 VR-006/007/009 新技能开发（P1）

以下新技能需要按照 VR-012 技能内容规范进行设计：

- **VR-006** coding-stage-execution（编码阶段执行）
- **VR-007** testing-stage-execution（测试阶段执行）
- **VR-009** operations-stage-execution（运维阶段执行）

设计要求：遵循 3 层技能架构（引导层 / 规范层 / 模板块），保持与其他阶段技能的一致性。

#### 4.2.5 VR-015/016/017 兼容性适配（P1）

以下兼容性需求需要设计各平台适配层：

- **VR-015** Node.js 版本兼容性适配
- **VR-016** 操作系统兼容性适配
- **VR-017** 包管理器兼容性适配

设计要求：抽象统一的适配层接口，各平台实现插件化，便于后续扩展新平台。

### 4.3 设计阶段输入约束

设计阶段须遵守以下约束条件：

1. **范围约束**：设计方案不得超出 Step 0 版本规划定义的范围，不得引入未纳入 Backlog 的功能
2. **优先级约束**：不得修改已批准的 P0/P1 优先级排序；P2 项仅在资源有余力时纳入设计
3. **问题管理约束**：设计过程中新发现的问题（如需求遗漏、技术不可行等）须先记录到风险清单，经评估后再决定是否纳入变更
4. **架构一致性约束**：设计方案须与现有 3 层技能架构保持一致（引导层 / 规范层 / 模板块），不得引入破坏性的架构变更
