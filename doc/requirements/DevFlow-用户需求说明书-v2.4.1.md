### 2.2 USC-2.4.1-001: 开发者在 PS5.1 环境运行 validate-install.ps1 失败

| 字段 | 内容 |
|---|---|
| **场景 ID** | USC-2.4.1-001 |
| **场景名称** | 开发者在 PS5.1 环境运行 validate-install.ps1 失败 |
| **用户角色** | 主要用户（TRAE IDE 用户 / 开发者） |
| **关联需求** | VR-2.4.1-001（validate-install.ps1 PS5.1 兼容性修复） |
| **前置条件** | 用户使用 Windows 7/10/Server 2016 等仅预装 PowerShell 5.1 的系统；用户已安装 DevFlow 并尝试运行安装验证脚本 |

**场景描述（步骤流程）**：

1. 开发者在 Windows 系统上安装了 DevFlow
2. 开发者运行 `validate-install.ps1` 进行安装验证
3. 脚本执行到第 133 行时抛出语法错误，脚本中断
4. 开发者看到错误信息，但因缺乏 PS 版本兼容性知识无法自行定位问题
5. 开发者尝试在 PS7.x 环境下运行脚本，发现可正常执行
6. 开发者确认是 PS5.1 兼容性问题，但在实际部署环境中只有 PS5.1 可用
7. 开发者无法完成安装验证，DevFlow 安装状态不明确

**预期结果（修复后）**：
- 脚本在 PS5.1 环境下正常运行并完成全部验证检查
- 验证报告准确输出，无语法报错
- 开发者无需关心 PS 版本差异，安装验证在所有环境下一致

**异常场景**：

| 异常编号 | 异常描述 | 系统行为 |
|---|---|---|
| E-001-01 | 修复后脚本在 PS5.1 下仍有其他不兼容语法 | 需进行全文件 PS5.1 兼容性扫描并修复所有不兼容点 |
| E-001-02 | 修复导致 PS7.x 环境行为变化 | 需在 PS5.1 和 PS7.x 双环境下进行回归验证 |

### 2.3 USC-2.4.1-002: AI Agent 编码后声明完成但无验证证据

| 字段 | 内容 |
|---|---|
| **场景 ID** | USC-2.4.1-002 |
| **场景名称** | AI Agent 编码后声明完成但无验证证据 |
| **用户角色** | 主要用户（项目负责人 / 质量负责人） |
| **关联需求** | VR-2.4.1-002（coding-stage-execution 验证证据强制化） |
| **前置条件** | AI Agent 正在执行 Step 3 编码阶段的开发任务；coding-stage-execution 技能已激活 |

**场景描述（步骤流程）**：

1. AI Agent 完成一项编码任务（如实现某个 API 接口）
2. AI Agent 在 DevLog 中声明"任务已完成，单元测试通过"
3. 质量负责人审查 DevLog 时发现仅有文字声明，没有实际的运行命令输出
4. 质量负责人无法确认代码是否真正通过测试，也无法追溯验证过程
5. 质量负责人要求 AI Agent 重新提供验证证据，但此时上下文可能已切换
6. 开发审计流程因证据不足而受阻

**预期结果（增强后）**：
- AI Agent 在每项编码任务完成时必须附带实际运行命令（如 `pytest tests/`）和命令输出
- 验证证据包含完整的命令、输出内容和执行时间戳
- 质量负责人可直接在 DevLog 中查看验证证据，确认代码质量
- 缺失验证证据的任务被自动阻断，不进入下一流程

**异常场景**：

| 异常编号 | 异常描述 | 系统行为 |
|---|---|---|
| E-002-01 | AI Agent 提供的验证证据格式不规范 | 根据 coding-stage-execution 中的示例格式要求重新提供 |
| E-002-02 | 验证命令执行失败但 AI Agent 未如实报告 | 阻断机制触发，要求 AI Agent 如实报告失败并修复后重新验证 |

### 2.4 USC-2.4.1-003: 代码审查遗漏性能/安全问题

| 字段 | 内容 |
|---|---|
| **场景 ID** | USC-2.4.1-003 |
| **场景名称** | 代码审查遗漏性能/安全问题 |
| **用户角色** | 主要用户（开发者 / 质量负责人） |
| **关联需求** | VR-2.4.1-003（code-logic-review 偏执级检查新增） |
| **前置条件** | AI Agent 正在执行代码逻辑审查；被审查的代码涉及数据库操作或用户输入处理 |

**场景描述（步骤流程）**：

1. 开发者完成一段涉及数据库查询的代码
2. code-logic-review 技能对代码进行常规审查（需求对齐、数据流、边界条件等）
3. 审查通过后，代码被提交到测试阶段
4. 测试阶段执行性能测试时发现严重的 N+1 查询问题
5. 经追溯发现，code-logic-review 在编码阶段的常规审查未覆盖 N+1 查询模式检测
6. 同样，涉及用户输入的代码在审查时未检测到潜在的 SQL 注入风险
7. 开发者需要返回编码阶段修复这些问题，导致返工和延迟

**预期结果（增强后）**：
- code-logic-review 自动检测循环内部的数据库/API 调用，识别 N+1 查询模式
- code-logic-review 自动检测共享状态读写和并发访问无保护的情况，识别竞态条件
- code-logic-review 自动检测未经验证的用户输入用于敏感操作的模式，识别信任边界违规
- 审查报告包含偏执级检查结果，含严重级别、问题描述和修复建议
- 偏执级检查仅在相关技术栈场景下触发，避免噪音

**异常场景**：

| 异常编号 | 异常描述 | 系统行为 |
|---|---|---|
| E-003-01 | 偏执级检查对不相关代码产生误报 | 调整触发条件，仅在涉及相应技术栈时触发 |
| E-003-02 | 偏执级检查遗漏实际存在的问题 | 分析遗漏模式，优化检查规则 |

### 2.5 USC-2.4.1-004: 测试阶段无法追溯 TDD 合规性

| 字段 | 内容 |
|---|---|
| **场景 ID** | USC-2.4.1-004 |
| **场景名称** | 测试阶段无法追溯 TDD 合规性 |
| **用户角色** | 主要用户（质量负责人 / 测试负责人） |
| **关联需求** | VR-2.4.1-004（testing-stage-execution TDD 证据链检查） |
| **前置条件** | 编码阶段已完成，进入测试阶段；项目要求遵循 TDD 流程 |

**场景描述（步骤流程）**：

1. 项目编码阶段完成，AI Agent 提交了多个 feat/fix 的 Git 提交
2. 进入测试阶段（Step 4），testing-stage-execution 技能被激活
3. 测试负责人希望确认每个编码提交是否遵循 TDD 流程（先测试后编码）
4. 当前 testing-stage-execution 不包含 TDD 证据链检查项，无法提供此类信息
5. 测试负责人只能手动检查每个 Git 提交的文件变更历史来判断 TDD 合规性
6. 对于包含多个文件的大型提交，手动判断耗时且容易出错
7. 最终无法得到准确的 TDD 合规率统计，TDD 执行质量无法量化

**预期结果（增强后）**：
- testing-stage-execution 自动检查每个 feat/fix 提交的 Git 历史
- 识别测试文件提交时间是否早于生产代码提交时间
- 输出 TDD 合规状态（合规/部分合规/不合规）和合规率统计
- 不合规项清单明确列出需补充测试的提交
- 合规率低于 90% 阈值时在报告中标注警告

**异常场景**：

| 异常编号 | 异常描述 | 系统行为 |
|---|---|---|
| E-004-01 | Git 历史中无法区分测试文件和生产文件 | 基于文件命名约定和目录结构进行分类 |
| E-004-02 | 提交历史被 squash 合并，无法追溯原始顺序 | 将 squash 提交标记为"部分合规"，不影响整体合规率计算 |

### 2.6 USC-2.4.1-005: 旧版技能文件格式不统一导致维护困难

| 字段 | 内容 |
|---|---|
| **场景 ID** | USC-2.4.1-005 |
| **场景名称** | 旧版技能文件格式不统一导致维护困难 |
| **用户角色** | 主要用户（开发者 / 技能维护者） |
| **关联需求** | VR-2.4.1-005（22 个旧版技能文件格式标准化）、VR-2.4.1-006（check-skill-format.ps1 自动填充能力） |
| **前置条件** | 22 个 v2.4.0 之前的技能文件格式存在不一致；skill-md-writing-standards 规范已制定 |

**场景描述（步骤流程）**：

1. 开发者需要修改某个旧版技能文件的内容
2. 打开文件后发现其格式与 skill-md-writing-standards 规范不一致（如章节顺序不同、元数据字段缺失）
3. 开发者手动修改格式以对齐规范，但不确定是否遗漏了某些标准章节
4. 开发者运行 check-skill-format.ps1 检查，脚本报告多个格式问题
5. 开发者需要逐一手动修复每个问题，过程耗时且容易出错
6. 对于 22 个文件的批量标准化，手动操作的工作量不可接受

**预期结果（增强后）**：
- 开发者运行 `check-skill-format.ps1 --fix` 自动填充缺失的标准章节
- 脚本执行前输出修改预览，开发者确认后自动执行
- 22 个文件可批量执行标准化，无需手动逐个修改
- 多次执行幂等，不会产生重复内容
- 标准化后的文件自动通过格式检查

**异常场景**：

| 异常编号 | 异常描述 | 系统行为 |
|---|---|---|
| E-005-01 | 自动填充后部分章节内容需要人工调整 | 自动填充使用占位符模板，标记 `[待补充]`，开发者后续手动完善具体内容 |
| E-005-02 | 批量标准化后交叉引用关系断裂 | 运行交叉引用检查脚本验证并修复断裂引用 |

### 4.4 BPF-2.4.1-003: 偏执级审查流程

#### 4.4.1 流程目标

| S1 | 代码分析 | AI Agent | 分析待审查代码，识别涉及的技术栈（数据库操作、并发编程、用户输入处理等） | 生产代码 | 技术栈分析结果 |
| S2 | 触发判断 | AI Agent | 根据技术栈分析结果判断是否触发偏执级检查 | 技术栈分析结果 | 触发/不触发 |
| S3 | N+1 查询检测 | AI Agent | 如涉及数据库操作，检测循环内部的 DB/网络/API 调用模式 | 触发 + 代码 | N+1 查询检查结果 |

| S6 | 结果汇总 | AI Agent | 将偏执级检查结果纳入审查报告，包含严重级别和修复建议 | 各项检查结果 | 偏执级审查报告 |
