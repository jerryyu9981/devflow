## 2. 业务目标

v2.8.4 为质量保障基础版（patch），核心业务目标：

1. **建立可执行证据底线**：从"文档说完成了"升级为"实际运行验证通过"，解决 Step 3 "假完成"问题
2. **遏制技术债务增长**：建立债务增长率红线，防止债务越积越多
3. **建立全局债务台账**：结束历史债务分散无汇总的状态，为跨版本还债打基础
4. **强化证据真实性**：通过交叉验证和新鲜度要求，减少 LLM 编造测试结果的风险

### 2.1 版本成功指标

| 指标 | 目标值 | 衡量方法 |
|-----|:------:|---------|
| 技术债务增长率 | ≤ 5%/版本 | 对比 v2.8.3 tag 与 v2.8.4 tag 的 TODO 数、高复杂度函数数、重复代码量 |
| Step 3 完成标准可执行性 | 100% | coding-stage-execution 中必须包含"实际运行验证"章节 |
| 历史债务底数清晰度 | 100% | 全局技术债务总表已建立，至少录入 10 条已知债务 |
| 证据交叉验证率 | 100% | DevLogReport 中静态检查、自测、审查三者有交叉印证 |
| 向后兼容 | 100% | 所有修改为增量添加，不删除原有章节，不破坏现有流程 |

## 3. 需求定义

### 3.1 V284-001：技术债务增长率红线

#### 3.1.1 需求描述

在 coding-stage-execution 中新增技术债务增长率门禁，每个版本新增的 TODO 数、高复杂度函数数、代码重复率不得超过阈值，超过则阻塞 Step 3 完成，必须在本版本内解决或申请豁免。

#### 3.1.2 用户故事

As a DevFlow 使用者,
I want 每个版本结束时自动对比技术债务指标的增长情况,
so that 防止债务越积越多，确保质量不退化。

#### 3.1.3 功能需求

| FR-ID | 需求项 | 输入 | 处理 | 输出 |
|:-----:|--------|------|------|------|
| FR-01 | 债务增长率指标定义 | 上一版本 tag + 当前代码 | 定义三项核心指标：TODO 数增长率、高复杂度函数新增数、代码重复率增量 | 指标定义文档（写入 coding-stage-execution） |
| FR-02 | 阈值配置 | 项目类型、规模 | 定义默认阈值：TODO 新增 ≤5 个/版本、高复杂度函数新增 ≤3 个、重复率新增 ≤2% | 阈值表（可按项目调整） |
| FR-03 | 对比基线确定 | git tag + 当前 commit | 与上一版本发布 tag 对比，计算差异 | 基线版本号 + 差异统计 |
| FR-04 | 超阈值处理流程 | 超阈值的指标 | 定义三级处置：P0 超阈值→阻塞+必须修复；P1 超阈值→评审后决定；P2 超阈值→记录+挂起 | 处置流程说明 |
| FR-05 | 豁免机制 | 超阈值且无法在本版本修复 | 定义豁免申请条件、审批流程、记录要求 | 豁免模板和流程 |

#### 3.1.4 验收标准

| AC-ID | 关联 FR | 验收条件 | 验证方法 |
|:-----:|:-------:|---------|---------|
| AC-01 | FR-01 | coding-stage-execution 中有明确的技术债务增长率检查章节和三项指标定义 | 检查技能文档 |
| AC-02 | FR-02 | 有明确的默认阈值表，每项指标有具体数值 | 检查阈值定义 |
| AC-03 | FR-03 | 明确说明对比基线为上一版本发布 tag，计算方法可操作 | 检查基线定义 |
| AC-04 | FR-04 | 超阈值时有明确的分级处置流程，P0 超阈值明确标注"阻塞 Step 3" | 检查处置流程 |
| AC-05 | FR-05 | 有豁免机制说明，含申请条件和审批要求 | 检查豁免说明 |

### 3.2 V284-002：实际运行 + 冒烟测试三层模型

#### 3.2.1 需求描述

在 coding-stage-execution 中新增"实际运行验证"章节，建立"构建验证→启动验证→冒烟测试"三层模型，作为 Step 3 完成的强制门禁，从根本上解决"文档证据 ≠ 可执行证据"问题。

#### 3.2.2 用户故事

As a DevFlow 使用者,
I want Step 3 完成时必须经过实际运行验证,
so that 确保代码真的能跑起来，不是只在文档里说完成了。

#### 3.2.3 功能需求

| FR-ID | 需求项 | 输入 | 处理 | 输出 |
|:-----:|--------|------|------|------|
| FR-06 | 三层模型定义 | 项目类型 | 定义三层：L1 构建验证、L2 启动验证、L3 冒烟测试；每层有明确的通过标准 | 三层模型定义（写入 coding-stage-execution） |
| FR-07 | 不同产出物类型适配 | 产出物类型（后端/前端/脚本/数据库/文档） | 为 5 类产出物分别定义验证方法和最低标准 | 分类适配指南 |
| FR-08 | 构建验证（L1） | 源代码 + 构建命令 | 执行构建命令，零错误通过；输出构建产物 | 构建结果 + 产物列表 |
| FR-09 | 启动验证（L2） | 构建产物 + 启动命令 | 实际启动服务/脚本，验证健康检查端点返回 200 或脚本退出码为 0 | 启动结果 + 健康检查响应 |
| FR-10 | 冒烟测试（L3） | 运行中的系统 + 核心用例清单 | 执行 3~5 个最核心用例，全部通过 | 冒烟测试报告 + 用例结果 |
| FR-11 | 纳入 Step 3 完成门禁 | Step 3 完成标准 | 将"冒烟测试通过"加入 Step 3 强制完成标准 | 更新后的完成标准列表 |

#### 3.2.4 验收标准

| AC-ID | 关联 FR | 验收条件 | 验证方法 |
|:-----:|:-------:|---------|---------|
| AC-06 | FR-06 | coding-stage-execution 中有完整的三层模型定义，每层有明确通过标准 | 检查技能文档 |
| AC-07 | FR-07 | 覆盖至少 5 类产出物（后端API/前端页面/脚本CLI/数据库变更/文档型项目）的验证方法 | 检查分类适配指南 |
| AC-08 | FR-08 | 构建验证有明确的命令、输出、通过标准 | 检查 L1 定义 |
| AC-09 | FR-09 | 启动验证有明确的健康检查方法和通过标准 | 检查 L2 定义 |
| AC-10 | FR-10 | 冒烟测试有用例数量要求（3~5 个核心用例）和通过标准 | 检查 L3 定义 |
| AC-11 | FR-11 | Step 3 完成标准列表中包含"冒烟测试通过"作为强制项 | 检查完成标准 |

### 3.4 V284-004：证据真实性强化

#### 3.4.1 需求描述

DevLogReport 增加证据交叉验证要求和新鲜度要求，确保静态质量检查、开发自测、代码逻辑审查三者互相印证，减少 LLM 编造测试结果的风险。

#### 3.4.2 用户故事

As a DevFlow 审计者,
I want DevLogReport 中的证据可以交叉验证,
so that 不容易被编造的测试结果蒙混过关。

#### 3.4.3 功能需求

| FR-ID | 需求项 | 输入 | 处理 | 输出 |
|:-----:|--------|------|------|------|
| FR-18 | 交叉验证要求 | 静态检查报告 + 自测报告 + 审查报告 | 三者必须互相印证：静态检查说"构建通过"↔自测说"API可访问"↔审查说"代码逻辑可运行" | 交叉验证矩阵（写入 DevLogReport 模板） |
| FR-19 | 证据新鲜度要求 | 执行时间 + commit hash | 自测和静态检查的执行时间必须在提交前 24 小时内，且对应当前 commit | 新鲜度规则 |
| FR-20 | 实际输出片段要求 | 命令输出 | 关键验证必须包含实际输出片段（不只是"通过"二字），如构建日志最后 20 行、curl 响应、测试结果摘要 | 输出片段要求 |
| FR-21 | 抽查机制 | Step 4 测试阶段 | Step 4 入场时随机抽取 1~2 个自测用例进行复核，发现造假则倒查 | 抽查规则 |

#### 3.4.4 验收标准

| AC-ID | 关联 FR | 验收条件 | 验证方法 |
|:-----:|:-------:|---------|---------|
| AC-18 | FR-18 | DevLogReport 模板中有"证据交叉验证"章节，列出三者印证关系 | 检查模板 |
| AC-19 | FR-19 | 有明确的 24 小时新鲜度要求和当前 commit 对应要求 | 检查新鲜度规则 |
| AC-20 | FR-20 | 要求关键验证包含实际输出片段，不能只写"通过" | 检查输出要求 |
| AC-21 | FR-21 | Step 4 入场检查中有自测抽查机制说明 | 检查 testing-stage-execution 或 coding-stage-execution |
