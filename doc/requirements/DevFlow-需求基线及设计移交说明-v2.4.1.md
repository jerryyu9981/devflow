## 3. 变更规则

### 3.1 变更触发条件

进入 Step 2 后，以下情况触发基线变更流程：

1. **需求变更**：新增、删除或修改已批准的需求项（包括功能范围、验收标准的调整）
2. **优先级调整**：P0/P1 优先级的升降级
3. **依赖/风险变更**：关键依赖关系变化或新增高风险项
4. **范围蔓延**：任何可能导致版本范围扩大的新增需求

### 3.2 变更记录要求

进入 Step 2 后变更需求必须记录以下内容：

| 记录项 | 说明 |
|--------|------|
| 范围 | 变更涉及的需求编号、变更前后的范围差异描述 |
| 影响 | 变更对进度、资源、质量、依赖的影响评估 |
| 审批 | 变更审批人、审批级别、审批日期及审批结论 |
| 下游同步结果 | 变更后对受影响文档（设计文档、测试计划等）的同步更新状态 |

### 3.3 变更审批要求

| 变更类型 | 审批级别 | 审批人 |
|----------|----------|--------|
| P0 需求变更 | L3 — 版本 Owner + 需求负责人 + 设计负责人 | jerry.yu |
| P1 需求变更 | L2 — 需求负责人 + 设计负责人 | jerry.yu |

## 5. 向 Step 2 的输入说明

### 5.1 设计阶段需要关注的修改文件和影响范围

设计阶段须基于 v2.4.1 需求基线，重点关注以下方面的设计工作：

| 影响领域 | 涉及修改内容 | 影响说明 |
|----------|-------------|----------|
| Skill 文件 | 需求对应的 Skill 文件新增或修改 | 需根据功能需求确定 Skill 层级（L1/L2/L3）和引用关系 |
| 脚本文件 | 构建脚本、初始化脚本、检查脚本的修改或新增 | 需评估脚本变更对现有工作流的影响 |
| 配置文件 | .devflow/config.json 等配置结构的变更 | 需向后兼容现有项目的配置文件 |
| 文档模板 | 需求文档模板、设计文档模板的调整 | 需确保模板变更不影响已使用旧模板的项目 |
| 测试用例 | 对应需求的测试策略和测试用例设计 | 需在测试阶段提供可执行的验证手段 |

### 5.2 设计阶段输入约束

1. **范围约束**：设计方案不得超出 Step 0 版本规划定义的范围，不得引入未纳入 Backlog 的功能
2. **优先级约束**：不得修改已批准的 P0/P1 优先级排序；P2 项仅在资源有余力时纳入设计
3. **架构一致性约束**：设计方案须与现有技能架构保持一致，不得引入破坏性的架构变更
