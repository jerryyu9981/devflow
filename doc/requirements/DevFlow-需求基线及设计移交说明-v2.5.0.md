## 3. 变更规则

### 3.1 变更触发条件

进入 Step 2 后，以下情况触发基线变更流程：

1. **需求变更**：新增、删除或修改已批准的需求项（包括功能范围、验收标准的调整）
2. **优先级调整**：P1 优先级的升降级
3. **依赖/风险变更**：关键依赖关系变化或新增高风险项
4. **范围蔓延**：任何可能导致版本范围扩大的新增需求

### 3.2 变更流程要求

进入 Step 2 后，需求基线变更须执行以下流程：

1. **记录变更**：在需求评审记录中记录变更原因、影响范围
2. **更新追溯矩阵**：同步更新需求追溯矩阵，保持追溯链完整
3. **双重审批**：获取需求负责人和版本规划负责人双重审批
4. **通知下游**：通知设计阶段负责人，确保设计文档同步更新

### 3.3 变更记录要求

| 记录项 | 说明 |
|--------|------|
| 范围 | 变更涉及的需求编号、变更前后的范围差异描述 |
| 影响 | 变更对进度、资源、质量、依赖的影响评估 |
| 审批 | 变更审批人、审批级别、审批日期及审批结论 |
| 下游同步结果 | 变更后对受影响文档（设计文档、测试计划等）的同步更新状态 |

### 3.4 变更审批要求

| 变更类型 | 审批级别 | 审批人 |
|----------|----------|--------|
| P1 需求变更 | L3 — 版本 Owner + 需求负责人 + 设计负责人 | jerry.yu |
| P2 需求变更 | L2 — 需求负责人 + 设计负责人 | jerry.yu |
| 优先级调整 | L3 — 版本 Owner + 需求负责人 | jerry.yu |
| 文档修正（错别字、表述优化） | L0 — 自行修正，记录日志 | — |

## 5. 向 Step 2 的输入说明

### 5.1 设计阶段需要关注的需求

Step 2 需要基于 FR-001~005 设计具体实现方案。以下为各需求的设计重点：

| 需求编号 | 需求名称 | 设计重点 |
|----------|----------|----------|
| FR-001 | devflow-init 增强 | devflow-init/SKILL.md 的交互流程设计 |
| FR-002 | 技能市场集成 | 技能市场元数据文件结构设计 |
| FR-003 | 性能工程技能 | 性能工程 L3 技能的章节结构和内容规划 |
| FR-004 | 数据库迁移技能 | 数据库迁移 L3 技能的章节结构和内容规划 |
| FR-005 | Codex CLI 适配 | Codex CLI 兼容性测试方案和修复策略 |

### 5.2 设计阶段输入约束

1. **范围约束**：设计方案不得超出 Step 0 版本规划定义的范围，不得引入未纳入 Backlog 的功能
2. **优先级约束**：不得修改已批准的 P1 优先级排序；P2 项仅在资源有余力时纳入设计
3. **架构一致性约束**：设计方案须与现有技能架构保持一致，不得引入破坏性的架构变更
4. **技术债务配额约束**：每个 Phase 预留 15-20% 技术债务配额，确保有缓冲空间应对设计变更
