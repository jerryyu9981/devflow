## 3. 核心功能需求

### 3.1 F1: 阶段产出物清单审计门禁（BL-213-001）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **AU（审计员）**, I want audit-agent **按标准清单逐项核对**阶段产出物, so that **跳过无清单目录扫描、确保审计覆盖100%标准文档** |
| **输入** | project-document-management 定义的各阶段产出物命名规范 |
| **处理逻辑** | (1) 为 Step 0~5 各创建一份标准产出物清单（YAML/JSON 格式）<br>(2) audit-agent 能力 2 升级为"读取清单 --> 逐项 LS 核对 --> 输出通过率"<br>(3) 非清单内的文件不计入通过率，仅做提示 |
| **输出** | 6 份标准清单配置文件 + audit-agent 审计能力增强 |
| **验收标准** | (1) audit-agent 阶段审计输出含"清单核对通过率"字段<br>(2) 所有标准文件存在时通过率=100%<br>(3) 任意标准文件缺失时通过率=0%<br>(4) 非清单文件不影响通过率 |

### 3.2 F2: 文档命名统一核查（BL-213-002）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **PM-DevFlow-Dev**, I want 运行命名核查脚本, so that **自动发现命名违规并修正, 确保全文档库命名一致** |
| **输入** | project-document-management 定义的 `{项目名}-{文档类型}-v{版本号}.md` 命名规范 |
| **处理逻辑** | (1) 从 project-document-management 提取命名规则到独立规则集<br>(2) 创建 validate-naming 规则脚本/Grep 模式集<br>(3) 集成到 audit-agent 中作为可选检查项, 也可独立运行 |
| **验收标准** | (1) validate-naming 脚本对 doc/ 目录运行零违规输出<br>(2) 违规文件被正确定位并输出差异详情 |

### 3.3 F3: 用户指南/手册规范化（BL-213-003）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **运维人员**, I want 用户指南/手册有统一模板且版本号自动同步, so that **发布的文档版本总是与软件版本一致** |
| **关联需求** | V2100-006（用户手册模板创建） |
| **处理逻辑** | (1) 创建标准用户指南/手册 Markdown 模板（含版本号占位符）<br>(2) 标准化更新流程：修改内容 --> 更新版本号 --> 提交 PR<br>(3) Release Checklist 新增验证命令，自动核对用户指南版本号<br>(4) 纳入发布门禁：发布时版本号不一致则阻断 |
| **验收标准** | (1) 模板文件存在于项目 templates/ 目录下<br>(2) Release Checklist 包含用户指南版本验证命令且可执行<br>(3) 发布门禁脚本在版本号不一致时返回非零退出码 |

### 3.4 F4: Release Note 双文件对齐（BL-213-004）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **发布经理**, I want 单版本 Release Note 和汇总 Release Note 同时生成且一致, so that **无论查看哪个文件都能获取准确的发布历史** |
| **处理逻辑** | (1) 创建 `DevFlow-Release-Note-All.md` 标准模板（汇总全部版本）<br>(2) 发布门禁新增双文件存在性验证<br>(3) 发布门禁新增内容一致性验证（至少最新版本行一致）<br>(4) release.ps1 结束后自动执行对齐检查 |
| **验收标准** | (1) `doc/release/DevFlow-Release-Note-v{version}.md` 文件存在<br>(2) `doc/release/DevFlow-Release-Note-All.md` 文件存在<br>(3) 两个文件中最新版本的版本号行完全一致 |

### 3.5 F5: 路线图同步纳入发布门禁（BL-213-005）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **PM-DevFlow-Dev**, I want 发布前强制检查路线图已更新, so that **路线图始终反映最新版本规划** |
| **处理逻辑** | (1) Release Checklist 的"发布前准备"阶段新增一行："路线图状态已同步"<br>(2) 该行需手动确认或自动检测路线图文件最近修改时间 |
| **验收标准** | Release Checklist 文件中包含"路线图状态已同步"检查行 |

### 3.6 F6: release.ps1 分支推送补齐（BL-213-006）

| 维度 | 内容 |
|:-----|:------|
| **用户故事** | As a **发布工程师**, I want release.ps1 自动推送 master 到三远程, so that **Tag 推送后 master 分支也同步，消除手动推送遗漏风险** |
| **处理逻辑** | (1) 在 release.ps1 的 Tag 推送步骤后新增：`git push origin master`<br>(2) 新增 `git push backup master`（推送到 backup 远程）<br>(3) 新增 `git push github master`（推送到 github 远程）<br>(4) 三行均为非阻塞执行，各自带错误处理（继续执行后续推送） |
| **验收标准** | (1) release.ps1 执行完毕后 `git log origin/master` 可看到最新 commit<br>(2) `git log backup/master` 可看到最新 commit<br>(3) `git log github/master` 可看到最新 commit |

## 5. 风险、假设与约束

| 类型 | 描述 | 影响 | 缓解措施 |
