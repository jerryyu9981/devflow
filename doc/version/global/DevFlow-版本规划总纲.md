# DevFlow 版本规划总纲

> **文档类型**: 版本规划总纲
> **文档状态**: Draft
> **版本**: v1.1
> **日期**: 2026-07-26
> **维护者**: DevFlow 维护团队
> **说明**: 本文件为全部版本共享文档，定义 DevFlow 项目长期目标、版本节奏、版本命名、发布策略、兼容策略和治理原则。

---

## 1. 项目长期目标

| 目标 | 说明 |
|:----|:------|
| 🏛️ **工程规范标准化** | 建立覆盖全生命周期的软件开发工程规范，让"规范不依赖个人记忆" |
| 🔄 **全流程自动化** | 逐步实现版本规划→需求→设计→开发→测试→部署的全自动循环（目标 v3.0） |
| 📊 **数据驱动治理** | 以度量指标和门禁替代人工判断，让每个阶段的"完成"可衡量、可验证 |
| 🧹 **债务持续下降** | 还债配额 + 生命周期管理确保技术债务总量不持续增长 |

## 2. 版本节奏

| 节奏 | 定义 | 说明 |
|:----|:------|:------|
| 版本周期 | 每月 1 个版本 | 每个自然月发布一个功能/增强版本 |
| Patch 发布 | 按需 | 严重缺陷（P0/P1）可跨版本发布 Hotfix |
| LTS | 不设 LTS | 持续迭代，无长期支持分支 |

## 3. 版本命名规则

格式：`v{主版本}.{次版本}.{修订号}`

| 字段 | 规则 | 示例 |
|:----|:------|:-----|
| 主版本 | 重大架构重构或破坏性变更 | v3.0.0 |
| 次版本 | 功能增强或流程变更 | v2.9.0 |
| 修订号 | Bug 修复或微小调整 | v2.8.1 |
| 预发布 | `-alpha.{n}`, `-beta.{n}`, `-rc.{n}` | v2.9.0-beta.1 |

**版本递增规则：**
- 次版本（如 v2.8→v2.9）：正常功能发布/流程变更
- 修订号（如 v2.8.3→v2.8.4）：缺陷修复/微小增强
- 不单独使用 v2.8 格式，必须写全 v2.8.x

## 4. 版本类型与状态

| 阶段 | 说明 |
|:----|:------|
| 规划中（Planning） | Step 0 进行中 |
| 开发中（In Development） | Step 1~3 进行中 |
| 测试中（In Testing） | Step 4 进行中 |
| 已发布（Released） | Step 5 完成 |
| 已废弃（Deprecated） | 不再维护的版本 |

## 5. 发布策略总则

| 策略 | 说明 |
|:----|:------|
| 发布节奏 | 按版本周期发布，不跳版本号 |
| 增量发布 | 每个版本基于上一版本增量，不进行全量重写 |
| Tag 命名 | 严格与版本号一致，前导 `v` 小写 |
| 双仓库推送 | 发布时同时推送到 origin + backup |
| 后验机制 | 发布后自动校验 Tag/备份/版本号一致性 |

> **详细发布策略**：参见 `doc/version/global/DevFlow-版本发布策略总则.md`

## 6. 兼容策略

| 层面 | 策略 |
|:----|:------|
| 技能接口 | 同一主版本内向后兼容，不删除已有功能，仅新增或增强 |
| 文档格式 | 维持现有文档模板结构，如需修改在版本规划中说明 |
| state.json | 新增字段为 optional，不破坏已有解析逻辑 |
| 配置字段 | config.json 新增字段不删除已有字段 |

## 7. 治理原则

| 原则 | 说明 |
|:----|:------|
| 单一事实源 | 版本号以 TRAE 系统目录 `version.json` 为唯一权威来源 |
| 门禁驱动 | 每个阶段完成以门禁检查为通过标准，不依赖人工判断 |
| 追溯闭环 | 需求→设计→开发→测试→部署全链路可追溯 |
| 债务不遗忘 | 全局技术债务总表 + 0.0a 跨版本审查确保债务可接续 |
| 文档伴随 | 文档与代码同步修改，阶段交付物必含文档 |
