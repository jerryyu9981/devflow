## 1. 版本目标

v2.8.4 为质量保障基础版（修订版 patch），核心目标：建立 Step 3 "可执行证据" 的底线——从"文档说完成了"升级为"实际运行验证通过"，同时建立技术债务增长率红线，防止债务持续累积。

### 1.1 核心目标

1. **技术债务增长率红线**（V284-001）：在 coding-stage-execution 中新增技术债务增长率门禁，每个版本新增 TODO/高复杂度函数/重复代码不得超过阈值，超过则阻塞 Step 3 完成
2. **实际运行 + 冒烟测试三层模型**（V284-002）：在 coding-stage-execution 中新增"构建验证→启动验证→冒烟测试"三层模型，作为 Step 3 完成的强制门禁，从根本上解决"文档证据 ≠ 可执行证据"问题
3. **全局技术债务总表建立**（V284-003）：在 `doc/version/global/` 下创建技术债务总表，汇总所有历史债务，建立跨版本流转基础
4. **证据真实性强化**（V284-004）：DevLogReport 增加证据交叉验证要求——静态检查、自测、审查三者必须互相印证

### 1.2 版本范围

**包含范围**：
- V284-001：技术债务增长率红线（新增 TODO 数 + 复杂度 + 重复率三重门禁）
- V284-002：实际运行 + 冒烟测试三层模型（构建验证 / 启动验证 / 冒烟测试）
- V284-003：全局技术债务总表建立（doc/version/global/ + 15 字段标准）
- V284-004：证据真实性强化（交叉验证 + 新鲜度要求 + 抽查机制）
- V284-005：可维护性审查权重升级（从第 11 位移至第 6 位，增加否决项）
- V284-006：DevLogReport 模板增加技术债务章节

**不包含范围**（后续版本）：
- 还债配额机制（目标 v2.9.0）
- 跨版本债务流转机制（目标 v2.9.0）
- 测试覆盖率门禁（目标 v2.9.0）
- 端到端集成验证（目标 v2.9.0）
- 性能基准测试（目标 v2.10.0）
- 季度审计机制（目标 v2.10.0）
- 全自动循环架构（目标 v3.0.0）

### 1.3 版本规划说明

本次质量保障体系升级源于实际项目中发现的 Step 3 "假完成"问题——文档完善但存在大量历史技术债务。根因分析显示：
1. 技术债务散落在 5 个环节，全是软约束
2. 缺少全局技术债务台账和跨版本流转机制
3. "文档证据"与"可执行证据"之间存在分水岭

v2.8.4 作为质量保障第一版，聚焦于建立**最底线的可执行验证**和**债务增长刹车**，先遏制债务增长势头，再在后续版本中建立还债机制和完整质量体系。

### 1.4 版本成功指标

| 指标 | 目标值 | 衡量方法 |
|-----|:------:|---------|
| 技术债务增长率 | ≤ 5%/版本 | 对比版本前后的 TODO 数、高复杂度函数数、重复代码量 |
| Step 3 完成标准可执行性 | 100% | coding-stage-execution 中必须包含"实际运行验证"章节 |
| 历史债务底数清晰度 | 100% | 全局技术债务总表已建立，所有已知债务已登记 |
| 证据交叉验证率 | 100% | DevLogReport 中静态检查、自测、审查三者必须有交叉印证 |

## 5. 版本发布策略草案

| 项目 | 内容 |
|------|------|
| **发布类型** | Patch 修订版（v2.8.x） |
| **发布节奏** | 单版本单周期，预计 2.5 人天 |
| **灰度策略** | 无需灰度，技能文档更新直接生效 |
| **回滚策略** | 技能文档修改可通过 Git 回滚；tag v2.8.3 为回滚基线 |
| **兼容策略** | 向后兼容，所有新增章节为增量添加，不破坏现有流程 |
| **发布窗口** | 开发完成 + 自测通过 + 评审通过即可发布 |
