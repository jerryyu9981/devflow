## 需求详情

### BL-291-001：JSON 配置文件精简合并

| 字段 | 值 |
|:-----|:----|
| 需求 ID | V291-001 |
| 标题 | JSON 配置文件精简合并 |
| 优先级 | 🟡 P1 |
| 来源 | 架构精简讨论（用户提出配置文件混淆问题） |
| 关联债务 | 架构债务（配置文件职责不清、重复存储） |
| 技术可行性 | ✅ 可行 |
| 所属 Phase | Phase 1 |

**需求描述**：
当前 DevFlow 有 6 个现役 JSON 配置文件，职责交叉、信息重复，容易混淆。需要精简为 3 个：
1. `devflow-plugin/devflow-config.json` — 框架权威配置（source of truth），合并原 version.json + devflow-manifest.json
2. IDE 系统目录 `devflow-config.json` — 运行时副本，setup 时从框架 devflow-config 复制
3. `.devflow/project-config.json` — 项目配置，原 `.devflow/config.json` 改名，合并项目根 version.json 字段

**验收标准**：
- JSON 配置文件从 6 个减少到 3 个
- 每个文件职责单一，零重复
- 所有脚本和文档中的旧路径引用全部更新
- 旧版本用户升级时自动迁移，无破坏性变更

**任务分解**：
1. devflow-plugin/version.json 重命名为 devflow-config.json，合并 devflow-manifest.json
2. .devflow/config.json 重命名为 .devflow/project-config.json
3. 删除项目根 version.json 和 .devflow/version.json
4. setup.ps1 更新写入路径
5. devflow-init 增加旧路径自动迁移逻辑
6. 所有技能文档路径引用更新
7. 全量 grep 验证无遗漏

### BL-291-002：安装脚本精简

| 字段 | 值 |
|:-----|:----|
| 需求 ID | V291-002 |
| 标题 | 安装脚本精简 |
| 优先级 | 🟡 P1 |
| 来源 | 架构精简讨论（用户提出脚本太多） |
| 关联债务 | 流程债务（脚本冗余、功能重复） |
| 技术可行性 | ✅ 可行 |
| 所属 Phase | Phase 2 |

**需求描述**：
当前 DevFlow 有 5 个生命周期脚本（download-devflow.ps1 / setup.ps1 / install.ps1 / update.ps1 / sync-skills.ps1），功能重叠多。精简为 2 个入口 + 2 个内部模块：
- `install.ps1` — 首次安装入口（编排 download + setup）
- `update.ps1` — 更新主入口（含原 sync-skills.ps1 全部功能）
- `download-devflow.ps1` — 内部模块（保留）
- `setup.ps1` — 内部模块（保留）

**验收标准**：
- 生命周期脚本从 5 个精简为 2 个入口
- sync-skills.ps1 功能完全合并进 update.ps1
- install / update / sync 三种场景全部通过回归测试
- 参数规范和错误处理统一

**任务分解**：
1. sync-skills.ps1 功能合并进 update.ps1
2. 删除 sync-skills.ps1
3. install.ps1 精简为纯编排
4. 统一参数规范、错误处理、BOM 修复函数
5. 全量回归测试

### BL-291-003：全阶段产出真实性验证门禁

| 字段 | 值 |
|:-----|:----|
| 需求 ID | V291-003 |
| 标题 | 全阶段产出真实性验证门禁 |
| 优先级 | 🟡 P1 |
| 来源 | 内部改进（v2.9.1 启动初期发现"空输出"问题） |
| 关联债务 | TD-023（流程债务：缺少全阶段产出真实性验证机制） |
| 技术可行性 | ✅ 可行 |
| 所属 Phase | Phase 3 |

**需求描述**：
v2.9.1 启动初期发现严重流程问题：LLM 执行阶段任务时可能"声称完成但文件未实际创建"（空输出）。根因是 6 个阶段（Step 0~5）的完成标准中均无"产出物存在性验证"强制规则。需在所有阶段新增产出物存在性验证门禁：
1. 每个阶段完成前必须通过 LS/Glob 工具列出目标目录，确认所有产出文件实际存在
2. 各阶段审计环节新增"产出物存在性核查"检查项
3. Step 5 全流程闭环审计新增"全阶段产出物盘点"章节，汇总所有阶段的产出物清单并逐一验证存在性
4. 验证结果必须包含实际工具输出作为证据，不得仅靠文字描述

**验收标准**：
- 6 个阶段（Step 0~5）的 L2 技能文档全部新增产出物存在性验证门禁
- 每个阶段的完成标准中包含"产出物存在性验证"强制步骤
- 各阶段审计检查清单中包含"产出物存在性核查"项
- Step 5 全流程闭环审计包含"全阶段产出物盘点"章节
- 验证门禁要求必须包含 LS/Glob 的实际输出列表作为证据

**任务分解**：
1. version-planning-stage-execution 新增产出物验证门禁
2. requirements-stage-execution 新增产出物验证门禁
3. design-stage-execution 新增产出物验证门禁
4. coding-stage-execution 新增产出物验证门禁
5. testing-stage-execution 新增产出物验证门禁
6. operations-stage-execution 新增产出物验证门禁
7. Step 5 全流程闭环审计新增"全阶段产出物盘点"章节
8. 制定标准化产出物验证模板，确保 6 个阶段规则一致
