## 3. 系统架构设计

### 3.1 技术债务增长率门禁设计（DT-01）

#### 3.1.1 设计目标

在 coding-stage-execution 的 §3.4 静态质量检查之后新增"3.4.1 技术债务增长率检查"子步骤，建立债务增长刹车机制。

#### 3.1.2 章节位置

```
coding-stage-execution.md
├── 3.4 代码静态质量检查
│   └── 3.4.1 技术债务增长率检查  ← ★ 新增
├── 3.5 开发自测
│   └── ...
```

> **设计决策**：使用小数编号（3.4.1）插入，不移动原有章节编号，确保向后兼容。

#### 3.1.3 三项核心指标

| 指标 | 默认阈值 | 计算方法 | 对比基线 |
|------|:--------:|---------|---------|
| 新增 TODO 数 | ≤ 5 个/版本 | `git diff v{上一版本}..HEAD -- '*.md' '*.ps1' '*.sh' | grep -c 'TODO\|FIXME\|HACK' | 上一版本发布 tag |
| 新增高复杂度函数 | ≤ 3 个/版本 | 静态检查工具输出的圈复杂度 >15 的函数增量 | 上一版本发布 tag |
| 代码重复率增量 | ≤ 2%/版本 | 新代码重复率增量 | 上一版本发布 tag |

#### 3.1.4 分级处置流程

```
超阈值检测
    ├── P0 超阈值（三项全超或任意一项超 2 倍阈值）
    │   └→ 阻塞 Step 3 完成
    │       └→ 必须在本版本内修复或申请豁免
    ├── P1 超阈值（一项或两项超阈值）
    │   └→ 评审后决定
    │       ├→ 本版本修复
    │       └→ 记录+挂起（需 PM 批准）
    └── P2 超阈值（接近阈值但未超）
        └→ 记录 + 挂起 + 下个版本重点关注
```

#### 3.1.5 豁免机制

- **适用条件**：架构重构、历史遗留代码整理、紧急修复等特殊情况
- **审批流程**：开发负责人申请 → PM + 架构师双批
- **记录要求**：豁免原因、预计偿还版本、负责人
- **豁免有效期**：仅限当前版本，下个版本重新评估

#### 3.1.6 可配置性设计

阈值在 coding-stage-execution 中设为默认值，同时提供"项目级自定义"说明：
- 项目可在 `.devflow/config.json` 中设置自定义阈值
- 自定义阈值需在版本规划时确认
- 阈值收紧需说明理由，放宽需 PM 批准

### 3.2 实际运行验证三层模型设计（DT-02）

#### 3.2.1 设计目标

在 coding-stage-execution 中新增"3.5 实际运行验证"章节（原 3.5 开发自测顺延为 3.6，以此类推），建立"构建→启动→冒烟"三层验证模型，作为 Step 3 完成的强制门禁。

#### 3.2.2 章节位置调整

```
coding-stage-execution.md 原有章节（v2.8.3）：
├── 3.1 编码准备
├── 3.2 任务拆解
├── 3.3 编码实现
├── 3.4 代码静态质量检查
├── 3.5 开发自测          ← 顺延为 3.6
├── 3.6 代码逻辑审查      ← 顺延为 3.7
├── 3.7 问题修复与复审     ← 顺延为 3.8
└── 3.8 DevLogReport      ← 顺延为 3.9

v2.8.4 调整后：
├── 3.1 编码准备
├── 3.2 任务拆解
├── 3.3 编码实现
├── 3.4 代码静态质量检查
│   └── 3.4.1 技术债务增长率检查  ← 新增（DT-01）
├── 3.5 实际运行验证        ← ★ 新增（DT-02）
│   ├── 3.5.1 L1 构建验证
│   ├── 3.5.2 L2 启动验证
│   └── 3.5.3 L3 冒烟测试
├── 3.6 开发自测          ← 顺延
├── 3.7 代码逻辑审查       ← 顺延
├── 3.8 问题修复与复审     ← 顺延
└── 3.9 DevLogReport      ← 顺延
```

> **设计决策**：将"实际运行验证"放在自测之前，逻辑上更合理——先确保能跑起来，再做详细自测。同时顺延后续章节编号，保持结构清晰。

#### 3.2.3 三层模型定义

| 层级 | 名称 | 验证内容 | 通过标准 | 产出物 |
|:----:|------|---------|---------|--------|
| L1 | 构建验证 | 执行构建/编译命令 | 零错误，构建产物生成 | 构建日志 + 产物列表 |
| L2 | 启动验证 | 启动服务/脚本/应用 | 健康检查返回 200 或退出码为 0 | 启动日志 + 健康检查响应 |
| L3 | 冒烟测试 | 3~5 个核心用例 | 全部通过 | 冒烟测试报告 + 用例结果 |

#### 3.2.4 不同产出物类型适配方案

| 产出物类型 | L1 构建验证 | L2 启动验证 | L3 冒烟测试 |
|-----------|-----------|-----------|------------|
| **后端 API 项目** | `npm run build` / `cargo build` / `python setup.py build` | 启动服务，`curl /health` 返回 200 | 登录 + 创建 + 查询 + 删除 + 登出（5个核心用例） |
| **前端项目** | `npm run build` 零错误 | `npm run dev` 启动后首页可访问 | 打开首页 → 导航到列表页 → 打开详情页（3个核心用例） |
| **脚本/CLI 工具** | PowerShell 语法检查 / `bash -n` 语法检查 | 执行 `--help` 或 `--version`，退出码 0 | 执行 3 个核心命令，验证输出和退出码 |
| **数据库变更** | SQL 语法检查 / migration dry-run | 在测试库执行 migration | 验证表结构、数据迁移结果、回滚可用性 |
| **文档型项目（DevFlow 这类）** | Markdown 链接检查 / 格式校验 | 实际打开关键文档，验证可阅读性 | 按照流程描述模拟执行一遍走查验证 |

> **设计决策**：DevFlow 自身属于"文档型项目"，其冒烟测试对应"走查验证"——按照文档描述的流程实际模拟执行，验证流程通顺、逻辑自洽。

#### 3.2.5 Step 3 完成门禁修改

Step 3 完成标准列表中新增一条：

> **实际运行验证通过**：L1 构建验证 + L2 启动验证 + L3 冒烟测试全部通过，DevLogReport 中有对应的验证记录和输出片段。

#### 3.3.4 状态流转设计

```
        新增
         ↓
      待偿还 ←───────────┐
         ↓                │ 重新激活
      偿还中              │
         ↓                │
      已偿还           挂起中
                      ↑    │
                      └────┘
                       挂起
```

**状态定义**：
| 状态 | 说明 |
|------|------|
| 新增 | 刚发现，未分类 |
| 待偿还 | 已分级，等待排期 |
| 偿还中 | 当前版本正在偿还 |
| 已偿还 | 已完成偿还并验证 |
| 挂起中 | 暂时不处理，有挂起理由 |

#### 3.3.5 老化升级规则

| 当前级别 | 挂起超过 | 自动升级为 |
|:--------:|:--------:|:----------:|
| P3 | 2 个版本 | P2 |
| P2 | 2 个版本 | P1 |
| P1 | 2 个版本 | P0（阻塞 Step 3） |

> **设计决策**：P1 升级到 P0 后自动阻塞 Step 3，确保债务不会无限挂起。

#### 3.3.6 版本变化追踪章节

- 挂起债务清单

### 3.4 证据真实性强化设计（DT-04）

#### 3.4.1 设计目标

在 DevLogReport 模板中新增"证据交叉验证"章节，同时增加证据新鲜度和输出片段要求，减少 LLM 编造测试结果的风险。

#### 3.4.2 交叉验证矩阵

| 证据类型 | 与谁交叉验证 | 验证点 |
|---------|-------------|--------|
| 静态质量检查 | 代码逻辑审查 | 静态检查说"无告警" ↔ 审查说"代码质量良好" → 一致 |
| 开发自测 | 静态质量检查 | 自测说"全部通过" ↔ 静态检查说"构建通过" → 一致 |
| 代码逻辑审查 | 开发自测 | 审查说"逻辑正确" ↔ 自测说"功能正常" → 一致 |
| 冒烟测试 | 启动验证 | 冒烟说"全部通过" ↔ 启动验证说"服务正常" → 一致 |

> **设计决策**：如果三者互相矛盾（比如静态检查有告警但审查说没问题），必须在 DevLogReport 中说明原因。

#### 3.4.3 新鲜度要求

- 静态质量检查和开发自测的执行时间必须在提交前 **24 小时内**
- 检查结果必须对应当前 commit（记录 commit hash）
- 如果修改了代码后重新提交，必须重新运行检查和自测

#### 3.4.4 实际输出片段要求

关键验证不能只写"通过"二字，必须包含实际输出片段：
- 构建验证：构建日志最后 20 行 + 产物列表
- 启动验证：健康检查端点的实际响应（状态码 + 响应体摘要）
- 冒烟测试：每个用例的输入 + 输出摘要 + 通过/失败标记
- 静态检查：告警数量统计 + Top 3 告警示例

#### 3.4.5 Step 4 抽查机制

Step 4 入场时随机抽取 1~2 个自测用例进行复核：
- 抽取方法：从自测用例列表中随机选择
- 复核方式：按照自测描述重新执行一遍
- 如果发现造假：直接回退 Step 3，全部重做 + 增加抽查比例

### 3.5 可维护性权重升级设计（DT-05）

#### 3.5.1 设计目标

在 code-logic-review 技能中，将"可维护性审查"从第 11 位（最后一位）提升至第 6 位，并增加 2 项否决条件，防止可维护性审查被放水。

#### 3.5.2 审查维度重排

```
v2.8.3 原有顺序（11 维）：
1. 需求覆盖审查
2. 设计一致性审查
3. 业务流程审查
4. API 契约审查
5. 数据一致性审查
6. 异常路径审查
7. 权限边界审查
8. 并发与资源审查
9. 静态质量证据审查
10. 自测证据审查
11. 可维护性审查    ← 最后一位，容易被放水

v2.8.4 调整后：
1. 需求覆盖审查
2. 设计一致性审查
3. 业务流程审查
4. API 契约审查
5. 数据一致性审查
6. 可维护性审查    ← ★ 提升到第 6 位（DT-05）
7. 异常路径审查
8. 权限边界审查
9. 并发与资源审查
10. 静态质量证据审查
11. 自测证据审查
```

> **设计决策**：放在第 6 位，在核心功能审查之后、边缘场景审查之前，既保证重要性，又不喧宾夺主。

#### 3.5.3 新增否决条件

| 否决项 | 阈值 | 处置 |
|--------|:----:|------|
| 高复杂度函数数量 | > 5 个 | 审查不通过，必须优化 |
| 代码重复率 | > 5% | 审查不通过，必须重构 |

> **设计决策**：否决条件的阈值设得比较宽松（>5 个 / >5%），主要防止极端情况，不是要每个函数都完美。

#### 3.5.4 证据关联要求

可维护性审查结论必须引用静态质量检查的具体数据：
- 不能只写"可维护性：好"
- 必须写"可维护性：中，发现 3 个高复杂度函数（见静态检查报告第 X 页），未超过 5 个否决阈值"

### 3.7 version-planning 债务引用设计（DT-07）

## 7. 设计决策记录（ADR）

### ADR-001：使用小数编号插入新章节

- **上下文**：在 coding-stage-execution 的 3.4 和 3.5 之间插入新章节
- **备选方案**：① 小数编号（3.4.1） ② 整体重排后续章节编号
- **决策**：同时使用两种方式——3.4.1 用小数编号插入，3.5 新增大章节后整体顺延
- **理由**：3.4.1 是子步骤，用小数编号合理；3.5 是完整的新章节，放在 3.4 之后逻辑上通顺
- **后果**：后续章节编号顺延 1 位，需要同步检查外部引用

### ADR-002：冒烟测试放在自测之前

- **上下文**：实际运行验证（冒烟测试）和开发自测的顺序
- **备选方案**：① 先自测再冒烟 ② 先冒烟再自测
- **决策**：先冒烟再自测
- **理由**：逻辑上先确保"能跑起来"，再做详细自测；冒烟测试是底线验证，自测是深度验证
- **后果**：coding-stage-execution 中自测及后续章节全部顺延 1 位

### ADR-003：否决条件阈值设得比较宽松

- **上下文**：可维护性否决条件的阈值设定
- **备选方案**：① 严格（>3个 / >3%） ② 宽松（>5个 / >5%）
- **决策**：宽松（>5个 / >5%）
- **理由**：v2.8.4 是质量保障第一版，先建立机制，再逐步收紧；避免一开始太严导致抵触
- **后果**：可能有些可维护性问题漏过，但 v2.9.0 可根据实际数据调整阈值
