# DevFlow 项目结构一致性保障方案

> **文档类型**: 技术解决方案报告
> **版本**: v1.0
> **日期**: 2026-07-23
> **作者**: PM-DevFlow-Dev
> **状态**: [Draft]

---

## 1. 问题背景

v2.9.1 配置架构重构中存在一个典型的**设计-执行断裂**问题：设计文档明确规划了 `.devflow/config.json → .devflow/project-config.json` 重命名和根 `version.json` 删除，但编码实现中这两个子任务被静默遗漏，且追溯矩阵虚报了完成状态，三道现有检查门禁（静态质量检查、产出验证门禁、全阶段盘点）都只验证了文件内容和存在性，没有验证"文件名是否符合设计"，导致问题跨越整条流水线直到 v2.9.2 才被修复。

## 2. 根因分析

```
设计写: .devflow/config.json → .devflow/project-config.json
         ↓ ① Backlog 子任务无强制跟踪
编码实现: 只更新了字段值，没改文件名
         ↓ ② 追溯矩阵只验功能不验结构
追溯矩阵: 记录为 "project-config.json ✅ 已实现"（伪闭环）
         ↓ ③ 现有门禁验存在+内容，不验命名
三道门禁: 全部通过（验字段/存在性 ✅，不检查文件名是否符合设计）
         ↓
发布: "配置体系重构完成" ✅（遗留不一致）
```

三个断点：

| 断点 | 问题 | 涉及技能 |
|:----:|:-----|:---------|
| ① | Backlog 子任务无强制可见性—编码时静默降级无记录 | `version-planning-stage-execution` |
| ② | code-logic-review 不检查文件结构一致性—设计写了"改名"但审查只验功能 | `code-logic-review` |
| ③ | 全阶段产出物盘点只验文件存在性，不验命名是否符合设计 | `operations-stage-execution` |

## 3. 解决方案

### 3.1 补强 A：Backlog 子任务可见性门禁

**改动文件**: `version-planning-stage-execution.md`（编码准备 §3.2）

**当前**: Backlog 只有需求级状态（已实现/未实现），没有子任务级逐项跟踪。

**增强**: 为每条设计文档中有明确"新建/重命名/删除"操作的需求，在追溯矩阵创建时自动生成 **Subtask CheckList**：

``````markdown
### Subtask CheckList — V291-001（示例）

| 子项 | 设计指定操作 | 编码状态 | 验收方法 | 若未完成 |
|:-----|:-----------|:--------:|:---------|:---------|
| .devflow/config.json → project-config.json | 重命名 | ❌ 未实施 | LS 文件系统 | 推迟至 v2.10.0 |
| 项目根 version.json 删除+合并 | 删除 | ❌ 未实施 | Glob 不存在 | 推迟至 v2.10.0 |
| ... | ... | ... | ... | ... |
``````

**规则**: 编码阶段结束时，Subtask CheckList 中不得有"未标记推迟版本"的未完成项。零异常退出。

**预估改动量**: 约 15 行（在 §3.2 中追加表格模板 + 规则说明）。

---

### 3.2 补强 B：code-logic-review 新增命名一致性审查维度

**改动文件**: `code-logic-review.md`（审查维度 → 新增第 14 维度）

**当前**: 11 个审查维度中没有检查"文件命名是否符合设计"。

**增强**: 新增第 14 个审查维度 **"命名与结构一致性"**：

| 审查维度 | 检查内容 | 不通过规则 |
|:---------|:---------|:----------|
| 14. 命名与结构一致性 | 设计文档中标记的"新建/重命名/删除"文件是否与实际文件系统一致 | 任一不匹配为 P1 |

**执行方式**:
- 设计文档输出时由 AI 根据明确的新建/重命名/删除操作自动生成 **File Manifest**（预期文件清单）
- code-logic-review 将 File Manifest 与实际文件系统的 LS/Glob 输出逐行对比
- 不匹配项标记为 **P1**（非 P0，不影响运行时功能但反映结构不一致）
- File Manifest 纳入设计评审记录或追溯矩阵的附件

**预估改动量**: 约 20 行（1 个新维度 + 1 个执行规则段落）。

---

### 3.3 补强 C：全阶段产出物盘点增加命名对齐检查

**改动文件**: `operations-stage-execution.md`（全阶段产出物盘点门禁）

**当前**: 盘点只有"确认文件存在"（LS/Glob 列出目录核对），不检查命名。

**增强**: 在 Step 2（设计）→ Step 3（开发）的盘点行中增加命名一致性维度：

``````markdown
| Step 2 架构与设计 | 架构设计、API设计... | LS 文件存在性 + **设计 File Manifest 命名一致性** |
| Step 3 开发/编码 | 源代码、DevLogReport... | LS 文件存在性 + **对比 File Manifest 命名一致性** |
``````

同时 Release Checklist 发布前新增：

- [ ] **命名一致性**：设计文档的 File Manifest 与文件系统实际文件名 100% 匹配（含新建/重命名/删除操作）

**预估改动量**: 约 10 行（盘点表单元格追加 + 1 行 Checklist 追加）。

## 4. 改动影响分析

| 维度 | 影响 |
|:-----|:------|
| 受影响模块 | `version-planning-stage-execution`、`code-logic-review`、`operations-stage-execution` |
| 功能影响 | 无运行时或 API 影响，纯流程规则增强 |
| 向后兼容 | ✅ 完全向后兼容—新增门禁仅在新阶段执行时触发，不影响已有流程 |
| 生效范围 | Subtask CheckList 从 v2.9.3+ 编码阶段开始强制执行；命名一致性维度从 v2.9.3+ code-logic-review 开始启用 |
| 编码实现难度 | 低—纯文档规则增强，三处不到 50 行总改动 |

## 5. 验收标准

| AC-ID | 验证方法 |
|:------|:---------|
| AC-01 | Subtask CheckList 表格模板存在于 version-planning-stage-execution.md |
| AC-02 | code-logic-review 包含"命名与结构一致性"审查维度 |
| AC-03 | operations-stage-execution 全阶段盘点表包含命名一致性描述 |
