## 一、背景与目标

### 1.1 问题定义

在现有 DevFlow 五步开发流程中，Step 2（架构与设计阶段）虽有"UI/UX 与原型"设计类别，但存在以下缺口：

- **页面遗漏风险**：无法系统性地确认"所有该有原型的页面是否都有了原型"。
- **状态覆盖不全**：原型往往只覆盖"正常态"，忽略空态、错误态、加载态、边界态。
- **流程断点未知**：单页面原型完整，但页面间跳转逻辑可能在真实用户路径中出现断点。
- **需求-原型脱节**：需求文档中的用户故事与原型文件之间缺乏双向可追溯的映射关系。
- **测试视角缺失**：设计阶段未预埋测试关注点，导致测试阶段频繁发现设计遗漏。

### 1.2 核心目标

建立一套**可执行、可检查、可审计**的前端设计工程化规范，确保：

1. **无遗漏**：所有 P0/P1 需求涉及的前端页面均有原型覆盖。
2. **状态完整**：每个页面的关键交互状态均在原型中体现。
3. **流程贯通**：核心用户路径通过原型走查验证，无断点。
4. **双向追溯**：需求 ↔ 页面 ↔ 原型 ↔ 测试用例 形成完整追溯链。
5. **设计即测试**：设计阶段预埋测试关注点，减少下游返工。

### 1.3 方案定位

本方案是 `design-stage-execution` 技能的**专项增强补充**，不是替代。所有增强内容必须在 Step 2 设计阶段执行，并遵循 `project-document-management` 技能的文档命名与存储规范。

## 三、具体实施规范

### 3.1 前端页面清单（Page Inventory）

#### 3.1.1 定义

前端页面清单是从需求文档中系统提取的**所有前端页面（含弹窗、抽屉、浮层）的汇总表**，是检查原型覆盖率的基准。

### 未覆盖页面跟踪

|---|---|---|---|---|---|

```

#### 3.1.3 生成规则

1. **从需求文档提取**：每个涉及用户界面的用户故事（User Story）必须映射到至少一个页面或弹窗。
2. **统一编号**：页面ID格式为 `PG-{三位数字}`，弹窗为 `MD-{三位数字}`，抽屉为 `DW-{三位数字}`。
3. **入口-出口必填**：每个页面必须列出所有可能的入口来源和出口去向。
4. **优先级继承**：页面优先级不低于其对应需求的优先级。

#### 3.1.4 通过标准

- P0 页面：原型覆盖率 100%
- P1 页面：原型覆盖率 >= 80%
- P2 页面：原型覆盖率 >= 50%，或记录"不适用"理由
- 任何"未覆盖"项必须有明确的完成计划和责任人

### 3.2 需求-设计追溯矩阵增强

#### 3.2.1 在现有矩阵基础上增加三列

| 新增列 | 说明 | 填写规则 |
|---|---|---|
| **涉及页面** | 该需求涉及的所有页面ID（引用页面清单） | 多个页面用逗号分隔 |

#### 3.2.2 增强后矩阵示例

| 需求ID | 用户故事 | 涉及页面 | 原型状态 | 测试关注点 | 交互状态 | 评审状态 |

| REQ-002 | 作为用户，我要查看仪表盘 | PG-003 | 全部已设计 | 1. 大数据量加载性能（>1000条记录）<br>2. 实时数据刷新间隔（30秒） | 空态✓ 加载态✓ 错误态✗ 边界态✗ | 待评审 |
| REQ-003 | 作为用户，我要导出报表 | PG-003, PG-004 | 部分待设计 | 1. 大文件导出超时（>30秒）<br>2. 并发导出限制（同时最多3个） | — | — |

#### 3.2.3 双向验证规则

- **正向验证**：每个 P0/P1 需求必须至少映射到一个页面。
- **反向验证**：页面清单中的每个 P0 页面必须至少被一个 P0/P1 需求引用。
- 双向验证不通过时，以**需求为准**，补齐页面或原型。

### 3.3 交互状态覆盖检查

#### 3.3.1 每个页面必须覆盖的状态

| 状态类型 | 定义 | 示例 | 强制要求 |
|---|---|---|---|
| **空态（Empty State）** | 页面/列表无数据时的展示 | 空列表提示"暂无数据，点击添加" | P0 页面强制 |
| **加载态（Loading State）** | 数据正在加载时的展示 | Skeleton 骨架屏、Loading  spinner | P0 页面强制 |
| **错误态（Error State）** | 加载失败或操作失败时的展示 | 网络错误提示、权限不足提示 | P0 页面强制 |
| **成功态（Success State）** | 操作成功后的展示 | 保存成功 Toast、提交成功跳转 | P0 页面强制 |
| **边界态（Edge Case）** | 极端数据量或极端条件下的展示 | 表格横向滚动、超长文本截断 | P0/P1 建议 |
| **权限态（Permission State）** | 无权限时的展示 | "您无权查看此页面"、按钮禁用 | 涉及权限时强制 |

#### 3.3.2 状态覆盖检查表

```markdown
## 页面状态覆盖检查表

| 页面ID | 页面名称 | 空态 | 加载态 | 错误态 | 成功态 | 边界态 | 权限态 | 检查结论 |
|---|---|---|---|---|---|---|---|---|
| PG-001 | 登录页 | ✓ | ✓ | ✓ | ✓ | ✓ | N/A | 通过 |
| PG-003 | 仪表盘首页 | ✓ | ✓ | ✗ | ✓ | ✗ | ✓ | 不通过：缺少错误态、边界态 |
```

#### 3.3.3 通过标准

- P0 页面：空态、加载态、错误态、成功态 四种状态必须全部覆盖。
- P1 页面：至少覆盖空态、错误态 两种状态。
- 涉及权限的页面：必须覆盖权限态。

### 3.4 原型走查（Prototype Walkthrough）

#### 3.4.1 定义

原型走查是**以用户角色视角，按真实业务场景在原型中模拟操作**，目的是暴露页面间的流程断点、逻辑漏洞和交互矛盾。

#### 3.4.2 走查规则

1. **按角色分组**：每个主要用户角色（如管理员、普通用户、访客）独立走查。
2. **选择核心路径**：每个角色选择 3-5 条最高频的核心用户路径。
3. **完整模拟**：从入口页面开始，一步一步点击/操作，记录每一步的预期结果和实际原型表现。
4. **标注断点**：任何"不知道该点哪里"、"点完后不知道会去哪"、"去了不该去的地方"都记为断点。

#### 3.4.3 走查记录模板

```markdown

- 走查人: 李四（设计师）、王五（产品经理）

### 走查路径 1：新用户注册 → 首次登录 → 完成首单
**用户角色**: 普通顾客
**路径描述**: 模拟一名新用户从注册到完成首次购买的完整流程

| 4 | 首页 | 浏览商品并点击"加入购物车" | 商品加入购物车，购物车数量+1 | 购物车数量+1 ✓ | 通过 | — |
| 5 | 购物车 | 点击"去结算" | 跳转订单确认页 | 跳转订单确认页 ✓ | 通过 | — |
| 6 | 订单确认页 | 选择收货地址、支付方式 | 可选择 | 可选择 ✓ | 通过 | — |

**路径结论**: 不通过
**发现断点**: 2 个（步骤3、步骤8）
**修复计划**:
  - 步骤3: 注册成功后自动跳转首页，预计 2026-07-01 修复

### 走查路径 2：已登录用户找回密码
...

### 3.5 用例场景演练（Scenario-Based Validation）

#### 3.5.1 定义

用例场景演练是**基于需求文档中的用例规约，在原型中逐条验证基本流程和所有异常分支**，确保原型与需求的一致性。

#### 3.5.2 演练规则

1. **覆盖所有 P0 用例**：每个 P0 用例必须在原型中完整演练一遍。
2. **基本流程 + 异常分支**：不仅验证"正常怎么走"，还要验证"异常怎么办"。
3. **前置条件验证**：演练开始前确认前置条件是否满足（如"已登录"、"购物车有商品"）。
4. **后置状态确认**：演练结束后确认系统状态是否符合预期（如"订单状态=已支付"、"库存-1"）。

#### 3.5.3 演练报告模板

```markdown
## 用例场景演练报告

### 用例 1：下单支付

**用例ID**: UC-004
**需求ID**: REQ-010
**优先级**: P0
**主要参与者**: 顾客

#### 前置条件检查
| 条件 | 要求 | 原型支持 | 结论 |
|---|---|---|---|
| 已登录 | 用户必须已登录 | 登录态保持 ✓ | 通过 |
| 购物车有商品 | 购物车中至少有一件商品 | 购物车非空校验 ✓ | 通过 |

#### 基本流程演练

| 步骤 | 动作 | 原型页面 | 原型表现 | 结论 |
|---|---|---|---|---|
| 1 | 用户点击"去结算" | 购物车页 | 跳转订单确认页 ✓ | 通过 |
| 2 | 系统显示收货地址与商品清单 | 订单确认页 | 地址和商品正确显示 ✓ | 通过 |
| 3 | 用户选择支付方式 | 订单确认页 | 支付方式可选 ✓ | 通过 |
| 4 | 用户点击"确认支付" | 订单确认页 | 跳转支付网关 ✓ | 通过 |
| 5 | 系统跳转至支付网关 | 支付网关页 | 正确跳转 ✓ | 通过 |
| 6 | 支付成功后，系统生成订单并扣减库存 | 支付结果页 | 显示支付成功，订单生成 ✓ | 通过 |

| 分支ID | 触发条件 | 预期行为 | 原型表现 | 结论 |
|---|---|---|---|---|
| 3a | 库存不足 | 提示"部分商品缺货"，阻止提交 | 提示并阻止 ✓ | 通过 |

| 4b | 支付超时（>15分钟） | 显示"支付超时，请重新下单"，释放库存 | 无超时处理 [缺失] | 不通过 |
| 4c | 网络中断 | 显示"网络异常，请检查网络后重试" | 提示网络错误 ✓ | 通过 |

#### 后置状态确认

| 检查项 | 预期状态 | 原型体现 | 结论 |
|---|---|---|---|
| 订单状态 | 已支付 | 订单详情页显示"已支付" ✓ | 通过 |
| 库存扣减 | 对应商品库存 -1 | 无库存展示 [无法验证] | 待确认 |
| 用户积分 | 增加对应积分 | 无积分系统 [不适用] | 不适用 |

#### 用例结论

| 项目 | 结果 |

| 基本流程 | 通过 |

| 修复项 | 增加支付超时处理逻辑和页面 |
| 修复责任人 | 张三 |
| 修复截止时间 | 2026-07-03 |
```

#### 3.5.4 通过标准

- P0 用例：基本流程 100% 通过，异常分支覆盖率 >= 80%。
- P1 用例：基本流程 100% 通过，异常分支覆盖率 >= 50%。
- 任何"不通过"项必须在设计阶段内修复并重新演练。

### 3.6 元素级交互标注

#### 3.6.1 定义

元素级交互标注是对**页面中每个可交互元素**（按钮、链接、输入框、下拉框等）的详细行为说明，确保前端开发时不遗漏交互细节。

#### 3.6.2 标注规范

每个可交互元素必须标注以下信息：

```markdown
### 元素标注规范

**元素标识**: #{元素ID} 或 {元素名称}
**所属页面**: {页面ID} - {页面名称}

| 属性 | 说明 | 示例 |
|---|---|---|
| **触发事件** | 用户如何触发（click / hover / focus / blur / change / submit） | click |
| **前置条件** | 什么情况下元素可用/不可用 | 已登录且拥有编辑权限 |
| **条件判断** | 触发后系统做什么判断 | 1. 若表单验证失败 → 显示错误提示<br>2. 若网络异常 → 显示重试按钮 |
| **成功路径** | 正常情况下的走向 | 跳转至 /success?orderId=xxx |
| **错误处理** | 异常情况下的反馈 | 显示 Toast "提交失败，请稍后重试"，按钮恢复可点击 |
| **边界限制** | 长度、大小、频率等限制 | 最多输入 200 字符；60 秒内不可重复提交 |
| **加载状态** | 操作进行中的展示 | 按钮变为 Loading 状态，文案改为"提交中..." |
| **权限控制** | 无权限时的展示 | 按钮隐藏或置灰，hover 显示"无权限"提示 |
```

#### 3.6.3 标注示例

```markdown
#### 元素 #btn-submit-order（提交订单按钮）

**所属页面**: PG-007 - 订单确认页

| 属性 | 内容 |
|---|---|
| 触发事件 | click |
| 前置条件 | 1. 用户已登录<br>2. 收货地址已选择<br>3. 支付方式已选择<br>4. 购物车非空 |

### 3.7 设计-测试预映射

#### 3.7.1 定义

设计-测试预映射是在设计阶段**从设计文档中提取测试关注点**，为后续测试用例设计提供结构化输入，减少测试阶段的设计返工。

#### 3.7.2 预映射内容

| 来源文档 | 可提取的测试关注点 | 示例 |
|---|---|---|
| 前端页面清单 | 页面覆盖率、页面间跳转关系 | "登录页必须支持 3 种登录方式" |
| 交互状态覆盖检查表 | 状态切换的正确性 | "空态切换到加载态再切换到数据态，不能有闪烁" |
| 原型走查记录 | 流程完整性 | "注册 → 登录 → 首单 流程必须在 5 步内完成" |
| 用例场景演练报告 | 异常分支覆盖 | "支付超时后库存必须自动释放" |
| 元素级交互标注 | 边界值、权限、并发 | "密码输入框边界：最少 8 位，最多 32 位" |
| 前端架构设计文档 | 性能、兼容性 | "首页首屏加载时间 <= 2 秒（95% 请求）" |

#### 3.7.3 预映射输出格式

```markdown

## 五、设计规范矩阵增强

### 5.1 新增设计类别

在现有 `design-stage-execution` 设计规范矩阵中新增以下行：

| 设计类别 | 必须执行内容 | 通过标准 | 强制产出 |
|---|---|---|---|
| **前端页面清单建立** | 1. 从需求文档提取所有涉及界面的需求项；2. 建立"页面清单"，包含页面ID、名称、路由、角色、对应需求、优先级；3. 建立页面间的入口-出口关系图 | 所有 P0/P1 涉及界面的需求项均有对应页面记录；无孤立页面 | 前端页面清单 |
| **前端原型覆盖检查** | 1. 从页面清单提取所有 P0/P1 页面；2. 检查每个页面是否有对应原型文件；3. 检查每个页面的关键交互状态（空态、加载态、错误态、成功态）是否有原型覆盖 | 所有 P0 页面 100% 原型覆盖且四种状态齐全；P1 页面 >= 80% 覆盖 | 前端原型覆盖检查表 |
| **原型走查** | 1. 按用户角色分组；2. 每个角色选择 3-5 条核心用户路径；3. 用原型模拟完整操作，记录断点 | 所有 P0 用户路径无严重断点；P1 路径断点有修复计划 | 原型走查记录 |
| **用例场景演练** | 1. 从需求文档提取所有用例规约；2. 每个 P0 用例在原型中完整演练基本流程 + 所有异常分支；3. 验证前置条件和后置状态 | P0 用例基本流程 100% 通过，异常分支覆盖率 >= 80% | 用例场景演练报告 |
| **元素级交互标注** | 1. 识别 P0 页面中所有可交互元素；2. 对每个主操作按钮和表单输入框标注触发事件、条件判断、成功路径、错误处理、边界限制 | P0 页面主操作按钮和表单输入框 100% 标注；P1 涉及安全/资金的操作 100% 标注 | 元素级交互标注 |

### 5.2 新增强制规则

在现有 7 条强制规则后增加：

**8. 不得遗漏 P0/P1 前端页面原型**：任何涉及用户界面的 P0/P1 需求，如果没有对应页面清单记录和原型覆盖，设计阶段不得完成。

**9. 原型必须覆盖关键交互状态**：每个有原型的 P0 页面，必须至少覆盖空态、加载态、错误态、成功态四种状态；涉及权限的页面必须覆盖权限态。

**10. 原型走查不得跳过核心路径**：所有 P0 用户路径必须通过原型走查验证，走查不通过不得进入设计评审。

**11. 用例场景演练必须覆盖异常分支**：每个 P0 用例的场景演练必须覆盖所有异常分支，异常分支覆盖率低于 80% 不得进入设计评审。

**12. 设计-测试预映射必须在设计评审前完成**：设计-测试预映射表必须在设计评审会议前提交给测试代表审阅，测试代表签字确认后方可进行设计评审。

### 8.1 术语表

| 边界态（Edge Case） | 极端数据量或极端条件下的展示状态 |
| 权限态（Permission State） | 无权限时的展示状态 |
