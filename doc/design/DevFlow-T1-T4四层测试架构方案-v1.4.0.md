## 1. 项目概述

### 1.1 背景

DevFlow 现有测试规范以 `testing-stage-execution` 为主控，定义了强制测试矩阵（13 类测试）和四轨并行工作流（4.0~4.11）。但实际项目测试中暴露了以下问题：

- **前后端接口定义不一致**（422/404 类问题）在测试阶段才被发现，缺少前置契约 diff 机制
- **接口测试通过但页面不可用**（字段映射错误、渲染空、console.error），缺少全页面巡检手段
- **E2E 测试覆盖薄弱**，缺少"低成本高覆盖"的全页面巡检与按业务影响排序的深度用例分层
- **层间追溯缺失**，无法证明每个契约定义在每一层都有测试覆盖
- **静默失败检测盲区**：自动化巡检仅检测"错误信号"（HTTP≥400/console.error/pageerror），对"按钮点击无响应"等静默失败无感知（OpenLLM BUG-v2.9.0-MODEL-001 暴露）
- **软断言泛滥**：if-else 分支让测试总是通过，掩盖功能缺失
- **缺少测试度量体系**：无覆盖矩阵、无缺陷逃逸率指标，无法量化测试有效性

### 1.2 目标

引入 T1-T4 四层测试架构，增强 DevFlow 测试规范的完整性和可执行性，确保测试完成后可安全交付生产。

### 1.3 命名说明

本方案使用 **T1-T4**（T = Test）命名测试层级，与 DevFlow 技能分层 L1/L2/L3 区分，避免混淆。

| 测试层级 | 名称 | DevFlow 技能层级 |
|:--------:|:-----|:-----------------|
| T1 | 契约层 | L2 testing-stage-execution + L3 api-contract-management |
| T2 | 接口层 | L2 testing-stage-execution |
| T3 | 页面/集成层 | L2 testing-stage-execution + 内置 e2e-test-gen/webapp-testing |
| T4 | 验收层 | L2 testing-stage-execution（UAT） |

## 2. T1-T4 四层架构定义

### 2.1 层级总览

| 层级 | 名称 | 解决问题 | 通过标准 | 关键产出 |
|:----:|:-----|:---------|:---------|:---------|
| T1 | 契约层 | 前后端接口定义不一致（422/404 类） | 路由映射表 diff 无差异 + Schemathesis 契约测试通过 | 路由映射表 diff 报告 |
| T2 | 接口层 | 后端接口功能正确性 | P0/P1 API 全通过：状态码 + 响应结构 + 边界参数 | API 测试报告 |
| T3 | 页面/集成层 | 页面实际可用性或服务间集成正确性 | 全页面/全链路巡检无阻塞性问题 + 深度用例通过 | 逐页/逐链路巡检问题表 + E2E 报告 |
| T4 | 验收层 | 主观判断（交互体验/业务流程正确性） | 核心业务流走查全部通过 | UAT 走查清单 |

### 2.2 层间追溯要求

每个 T1 契约定义的路由，必须能在 T2 找到对应 API 测试、在 T3 找到页面巡检覆盖、在 T4 确认业务验收。

| 追溯维度 | 格式 | 覆盖率要求 |
|:---------|:-----|:---------|
| T1 路由 → T2 API 测试 | 路由路径 ↔ TT-ID(API) | P0/P1 路由 100% |
| T2 API 测试 → T3 页面/集成覆盖 | TT-ID(API) ↔ TT-ID(E2E) | P0/P1 API 100% |
| T3 页面/集成覆盖 → T4 UAT 验收 | TT-ID(E2E) ↔ UAT-ID | 核心业务流 100% |

> 层间追溯矩阵作为测试回溯审计报告的必填附件。

### 2.3 项目类型适配

T3 和 T4 按项目类型分模式执行：

| 层级 | 全栈项目（有前端） | 纯后端项目（无前端） |
|:-----|:-------------------|:---------------------|
| T1 契约层 | 路由映射 diff + Schemathesis + MSW | OpenAPI/gRPC proto 契约测试 + Schemathesis |
| T2 接口层 | API 三要素校验（状态码+结构+边界） | 同左 |
| T3 | T3a 全页面巡检 + T3b 深度用例 | T3a 服务间集成巡检 + T3b 深度集成用例 |
| T4 | 核心业务流页面走查 | 核心业务流 API/CLI 走查 |

#### T3 纯后端模式

**T3a 服务间集成巡检**（替代全页面巡检）：
- 自动遍历全部服务间调用链路（从路由定义或服务注册表提取）
- 逐链路采集：调用超时、5xx 错误、响应结构不符合预期
- 输出逐链路问题表

**T3b 深度集成用例**：
- 对高频服务间调用写 CRUD/错误态/重试/幂等性用例
- 按业务影响排序（计费服务 > 配置服务 > 辅助服务）

#### T4 纯后端模式

走查清单从"页面操作"变为"API/CLI 调用序列"：

| 序号 | 业务流 | 步骤（API 调用序列） | 预期结果 | 通过 |
|:----:|:-------|:-----|:---------|:----:|
| 1 | 配置→计费→调用 | POST /providers → POST /billing → POST /chat | 全链路无阻塞，数据正确 | ⬜ |

#### 不适用声明规则

如果项目既无前端也无服务间集成（单服务纯 API），T3 可标记"不适用"，但必须在测试报告中说明原因、影响和补救计划（与现有规范跳过项规则一致）。

## 3. 各层详细规范

### 3.1 T1 契约层

#### 3.1.1 执行内容

| 检查项 | 方法 | 工具 |
|:-------|:-----|:-----|
| 路由映射表 diff | 维护"路由→请求/响应字段"映射表，脚本自动 diff 前后端定义差异 | 自定义脚本 |
| OpenAPI 契约测试 | 后端 Schemathesis 校验 API 响应符合 OpenAPI 规范 | Schemathesis |
| 前端 Mock 联调 | 前端 MSW 基于 OpenAPI 生成 Mock 数据，验证前端消费契约 | MSW |
| 字段一致性校验 | 对照 OpenAPI 契约验证每个 endpoint 的响应 schema 和参数 | code-static-quality-check |

#### 3.1.2 路由映射表 diff 机制

当项目无 OpenAPI 规范或作为契约测试的补充手段，维护一张"路由→请求/响应字段"映射表。

**映射表格式**（YAML）：

```yaml
routes:
  - path: /api/v1/providers
    method: POST
    request_fields:
      - name: provider_name
        type: string
        required: true
    response_fields:
      - name: id
        type: string
      - name: provider_name
        type: string
    frontend_consumer: "src/pages/providers/create.tsx"
```

**diff 脚本规范**：

1. 从后端路由定义提取路由→字段映射（或从 OpenAPI spec 生成）
2. 从前端 API 调用代码提取实际使用的路由和字段
3. diff 两份映射，输出差异清单：
   - 后端有但前端未调用的路由
   - 前端调用但后端未定义的路由
   - 字段名/类型不一致
   - 必填规则不一致

**执行时机**：Step 4 测试阶段执行（非仅 Step 5 CI），测试报告中记录 diff 结果。

#### 3.1.3 通过标准

- 路由映射表 diff 无 P0/P1 差异（或差异已修复）
- Schemathesis 契约测试通过（无 5xx 错误，响应格式符合 OpenAPI 定义）
- MSW Mock 数据结构与 OpenAPI 契约一致
- 前后端字段一致性校验已纳入 code-static-quality-check

#### 3.1.4 检查清单

- [ ] MSW 已配置，前端可脱离后端独立开发
- [ ] Mock 数据结构与 OpenAPI 契约一致
- [ ] 后端契约测试已通过（Schemathesis 或等效工具）
- [ ] 前后端字段一致性校验已纳入 code-static-quality-check
- [ ] 路由映射表 diff 已执行，无 P0/P1 差异（或差异已修复）

### 3.2 T2 接口层

#### 3.2.1 三要素校验标准

每条 API 测试必须包含以下三要素：

| 要素 | 校验内容 | 示例 |
|:-----|:---------|:-----|
| ① 状态码断言 | 验证 HTTP 状态码符合预期 | `assert response.status_code == 200` |
| ② 响应结构断言 | 验证响应体字段名和类型符合契约 | `assert "id" in response.json() and isinstance(response.json()["id"], str)` |
| ③ 边界参数测试 | 验证边界条件、异常输入的处理 | 空字符串、超长字符串、特殊字符、缺失必填字段 |

#### 3.2.2 显式声明

> **接口通过 ≠ 页面可用**。接口层验证的是后端单独正确，但页面可能因字段映射错误、渲染时序问题、空数据处理不当而不可用。页面可用性由 T3 验证。

#### 3.2.3 通过标准

- P0/P1 API 全部通过三要素校验
- 无非预期 5xx 错误
- 边界参数测试覆盖空值、超长、特殊字符、缺失必填

#### 3.2.4 断言分级规范

> **v1.3.0 新增**，源自 OpenLLM 测试方法论改进方案。软断言是测试"全绿但功能缺失"的根因，必须从规范层面根除。

所有测试（T2 接口层 + T3b 深度用例）的断言必须按以下三级分类执行：

| 断言级别 | 适用场景 | 规则 | 示例 |
|:---------|:---------|:-----|:-----|
| **L1-硬断言** | 关键交互（创建/编辑/删除/提交） | 必须 `wait_for + assert`，超时即失败，不允许任何回退分支 | 按钮点击后对话框必须出现 |
| **L2-条件断言** | 可选功能（搜索/筛选/分页） | 元素存在则验证，不存在则 `pytest.skip`（**非 else 通过**） | 搜索框存在则测试搜索功能 |
| **L3-存在性断言** | 页面加载/基础渲染 | 核心元素必须可见，辅助元素可选 | 表格/卡片/空状态至少一个可见 |

#### 3.2.5 禁止模式清单

以下三种断言模式在 T2 和 T3b 测试中**严格禁止**，代码审查时必须检查：

**禁止模式 1：if-else 软断言**

```python
# ❌ 禁止：else 分支让测试永远通过
if search_input.is_visible():
    search_input.fill("gpt")
    assert page.locator(".el-table").is_visible()
else:
    assert page.locator(".el-table, .el-card, .el-empty").first.is_visible()
```

**禁止模式 2：try-except 吞异常**

```python
# ❌ 禁止：异常被吞，测试静默通过
try:
    btn.click()
    dialog.wait_for(state="visible", timeout=5000)
except Exception:
    pass  # 异常被吞，问题被掩盖
```

**禁止模式 3：超宽容断言**

```python
# ❌ 禁止：断言条件过于宽松，任何元素都满足
assert page.locator("div").first.is_visible()  # 页面总有 div
```

> 软断言清零是测试阶段的通过标准之一：`grep -r "if.*is_visible.*else.*assert" tests/` 结果必须为 0。

#### 3.2.6 推荐断言模式（v1.4.0 新增）

> 源自 OpenLLM 测试方法论改进方案。仅有禁止模式不够，必须提供"正确写法"的标准模板，让测试人员有可直接复用的参考。

**L1-硬断言标准模板**（关键按钮点击场景）：

```python
# ✅ 推荐：关键按钮点击后必须有响应
def test_click_add_button(self, e2e_page_context, e2e_base_url):
    """E2E-MODEL-003: 点击添加模型按钮（L1-硬断言）

    验证点：
    - 按钮可见且可点击
    - 点击后弹出对话框/抽屉
    - 对话框包含表单元素

    断言策略：L1-硬断言
    """
    if e2e_page_context.get("mock_mode", False):
        pytest.skip("E2E 测试需要前端服务运行")

    page = e2e_page_context["page"]
    page.goto(f"{e2e_base_url}/models")
    page.wait_for_load_state("networkidle")

    # 步骤1：按钮必须可见（硬断言）
    add_btn = page.locator("button:has-text('添加模型')")
    add_btn.wait_for(state="visible", timeout=10000)
    assert add_btn.is_visible(), "添加模型按钮必须可见"

    # 步骤2：点击后必须出现对话框/抽屉（硬断言）
    add_btn.click()
    dialog = page.locator(".el-dialog, .el-drawer")
    dialog.wait_for(state="visible", timeout=5000)
    assert dialog.is_visible(), "点击添加模型后必须弹出对话框或抽屉"

    # 步骤3：对话框必须包含表单元素（硬断言）
    form_elements = dialog.locator("input, .el-select, .el-form-item")
    assert form_elements.count() > 0, "对话框必须包含表单元素"
```

**L2-条件断言标准模板**（可选功能场景）：

```python
# ✅ 推荐：可选功能存在则测试，不存在则 skip（非 else 通过）
def test_search_filter(self, e2e_page_context, e2e_base_url):
    """E2E-MODEL-002: 模型搜索筛选（L2-条件断言）

    验证点：
    - 搜索框存在时验证搜索功能
    - 搜索后显示结果或空状态

    断言策略：L2-条件断言
    """
    page = e2e_page_context["page"]
    page.goto(f"{e2e_base_url}/models")
    page.wait_for_load_state("networkidle")

    search_input = page.locator("input[placeholder*='搜索'], input[placeholder*='search']")
    if not search_input.is_visible():
        pytest.skip("当前页面无搜索框，跳过搜索测试")  # 明确 skip，而非 else 通过

    search_input.fill("gpt")
    page.wait_for_timeout(2000)
    # 搜索后必须有结果或空状态（硬断言）
    result = page.locator(".el-table__row, .el-empty")
    result.wait_for(state="visible", timeout=5000)
    assert result.is_visible(), "搜索后必须显示结果或空状态"
```

#### 3.2.7 断言策略速查表（v1.4.0 新增）

> 源自 OpenLLM 测试方法论改进方案附录。速查表供测试人员在编写用例时快速选择正确的断言级别和写法。

| 场景 | 断言级别 | 推荐写法 |
|:-----|:--------:|:---------|
| 关键按钮点击 | L1 | `btn.wait_for(state="visible"); btn.click(); dialog.wait_for(state="visible"); assert dialog.is_visible()` |
| 表单提交 | L1 | `submit.click(); msg.wait_for(state="visible"); assert "成功" in msg.text_content()` |
| 页面加载 | L1 | `page.goto(url); page.wait_for_load_state("networkidle"); assert page.locator(".el-table").is_visible()` |
| 列表数据 | L1 | `assert table.locator(".el-table__row").count() > 0, "列表必须有数据"` |
| 可选搜索功能 | L2 | `if not search.is_visible(): pytest.skip("无搜索框"); search.fill("x"); assert result.is_visible()` |
| 可选分页 | L2 | `if not pager.is_visible(): pytest.skip("无分页"); pager.click(); assert table.locator(".el-table__row").count() > 0` |

### 3.3 T3 页面/集成层

#### 3.3.1 T3a 全页面巡检（全栈项目）

**目标**：自动导航全部路由，一次跑完输出逐页问题表，发现联调断点成本最低、覆盖面最大。

**执行规范**：

1. **路由收集**：从前端路由配置或 sitemap 自动提取全部路由（含动态路由参数化）
2. **登录态注入**：通过 `page.evaluate` 注入 token/cookie，避免每页重复登录
3. **逐页采集**（每页等待 networkidle 或 timeout 5s）：
   - HTTP ≥ 400 的请求（422/404/500）
   - `console.error` 事件
   - `pageerror` 事件（未捕获异常）
   - **"接口 200 但渲染空"检测**：页面主内容区域 DOM 为空或仅有骨架屏未消失
   - **"静默失败"检测**（v1.3.0 新增）：关键按钮（添加/创建/新建/编辑/删除/导出/刷新）点击后既无新网络请求、也无对话框/抽屉/消息提示弹出，判定为疑似空实现
   - **"表单提交响应"检测**（v1.4.0 新增）：对包含表单的对话框，提交后检查是否出现错误提示，发现前端吞掉 4xx/5xx 错误的情况
4. **输出**：逐页问题表（页面路径 × 问题类型 × 问题详情）

**通过标准**：P0/P1 页面无阻塞性问题（HTTP 500、pageerror、渲染空）

#### 3.3.2 T3a 服务间集成巡检（纯后端项目）

**目标**：自动遍历全部服务间调用链路，发现集成断点。

**执行规范**：

1. **链路收集**：从路由定义或服务注册表提取全部服务间调用链路
2. **逐链路采集**：
   - 调用超时
   - 5xx 错误
   - 响应结构不符合预期
3. **输出**：逐链路问题表

**通过标准**：P0/P1 链路无阻塞性问题

#### 3.3.3 T3a 巡检工作流（六步闭环）

T3a 巡检采用六步闭环工作流，从清单盘点到报告更新形成完整链路：

```
清单盘点 → 自动化巡检 → 问题分类 → 根因定位 → 修复回归 → 报告更新
```

**步骤 1：清单盘点**

从前端路由配置或 sitemap 自动提取全部路由，生成页面清单（含路由路径、页面优先级、动态路由参数化方案）。

| 产出 | 说明 |
|:-----|:-----|
| 页面清单 | 路由路径 × 优先级（P0/P1/P2）× 是否需登录 × 动态参数 |

**步骤 2：自动化巡检（6 类信号采集）**

> v1.4.0 升级：从 5 类信号增至 6 类，新增"表单提交响应检测"信号；扩展关键按钮清单和对话框清理逻辑。

使用 Playwright 自动导航全部路由，逐页采集 6 类信号：

| 信号类型 | Playwright API | 采集方式 | 对应问题 |
|:---------|:---------------|:---------|:---------|
| HTTP ≥ 400 | `page.on('response')` | 拦截响应，检查 `response.status()` | 接口契约不一致/后端错误 |
| console.error | `page.on('console')` | 过滤 `msg.type() === 'error'` | 前端逻辑错误 |
| pageerror | `page.on('pageerror')` | 直接捕获未处理异常 | 前端运行时异常 |
| 接口 200 但渲染空 | `page.evaluate()` + DOM 检查 | 检查主内容区域 `children.length === 0` | 字段映射/渲染问题 |
| **静默失败（行为信号）** | `btn.click()` + 网络计数器 + DOM 检查 | 点击关键按钮后检查：①是否有新网络请求 ②是否有对话框/抽屉/消息提示弹出。两者皆无→疑似空实现 | **空实现/事件未绑定/API 未调用** |
| **表单提交响应**（v1.4.0 新增） | `submit_btn.click()` + 错误消息检测 | 对包含表单的对话框，点击提交按钮后检查是否出现错误提示（`.el-message--error`），4xx/5xx 被前端吞掉的情况 | **表单提交失败被吞/校验逻辑缺失** |

**关键按钮清单**（v1.4.0 扩展）：静默失败检测覆盖以下 7 类关键按钮（源自 OpenLLM 实践）：

```
KEY_BUTTONS = ["添加", "创建", "新建", "删除", "编辑", "导出", "刷新"]
```

> v1.3.0 仅列出 5 类（添加/创建/编辑/删除/导出），v1.4.0 补充"新建"和"刷新"。

**对话框清理逻辑**（v1.4.0 新增）：每次关键按钮检测后，若弹出了对话框/抽屉，必须关闭后再检测下一个按钮，避免对话框叠加影响后续检测：

```python
# 关闭可能出现的对话框，避免影响后续检测
close_btn = page.locator(".el-dialog__close, .el-drawer__close").first
if close_btn.is_visible():
    close_btn.click()
    page.wait_for_timeout(500)
```

**登录态注入**：通过 `page.evaluate` 注入 token/cookie，避免每页重复登录。

**网络请求计数器注入**（v1.3.0 新增）：在页面上下文注入 `window.__requestLog`，拦截 `fetch` 和 `XMLHttpRequest.open`，记录所有网络请求供静默失败检测使用。

**表单提交检测逻辑**（v1.4.0 新增）：对包含表单的对话框，尝试提交并检测响应。提交后若出现 `.el-message--error` 错误提示，记录为"表单提交错误"问题。此检测可发现前端吞掉 4xx/5xx 错误的情况。

**步骤 3：问题分类（7 类标准模式）**

> v1.4.0 升级：从 6 类增至 7 类，新增 G 类"表单提交错误被吞没"。

巡检采集的信号按以下 7 类标准模式分类，每类对应不同的修复路径：

| 类别 | 模式名称 | 典型信号 | 根因方向 | 修复路径 |
|:----:|:---------|:---------|:---------|:---------|
| A 类 | 接口契约不一致 | HTTP 422/404 | 前后端路由或字段定义不匹配 | T1 契约层修复（改契约或改调用） |
| B 类 | 后端运行时错误 | HTTP 500 | 后端代码异常、数据库错误 | Step 3 后端修复 |
| C 类 | 前端运行时异常 | pageerror | 未捕获异常、空指针、类型错误 | Step 3 前端修复 |
| D 类 | 前端逻辑错误 | console.error | 状态管理错误、条件判断错误 | Step 3 前端修复 |
| E 类 | 渲染空/白屏 | 接口 200 但 DOM 空 | 字段映射错误、渲染时序、空数据未处理 | Step 3 前端修复（查字段映射） |
| **F 类** | **静默失败/空实现** | **按钮点击后无网络请求且无 UI 响应** | **事件未绑定、handler 空实现（TODO）、API 未调用** | **Step 3 前端修复（补全 handler 实现）** |
| **G 类**（v1.4.0 新增） | **表单提交错误被吞没** | **表单提交后 API 返回 4xx/5xx 但前端未显示错误提示** | **前端 error handler 缺失或 catch 后未提示用户** | **Step 3 前端修复（补全错误提示逻辑）** |

> 7 类分类法使每个问题都有对应的修复路径，可以直接指导步骤 4 的根因定位。F 类是 v1.3.0 新增，源自 OpenLLM BUG-v2.9.0-MODEL-001 实践教训；G 类是 v1.4.0 新增，源自表单提交响应检测信号。

**步骤 4：根因定位**

对每个分类后的问题执行根因定位：

| 定位手段 | 适用类别 | 方法 |
|:---------|:---------|:-----|
| 日志分析 | A/B/C/D 类 | 查看后端日志、浏览器 Network 面板 |
| 堆栈追踪 | C/D 类 | pageerror 的 stack trace、console.error 的调用链 |
| 直连复现 | A/B 类 | 用 curl/httpie 直接调用接口，绕过前端确认是后端还是前端问题 |
| DOM 检查 | E 类 | 检查接口返回数据结构 vs 前端渲染代码的字段映射 |
| **源码检查** | **F 类** | **检查按钮 handler 是否为空实现/TODO，检查事件绑定是否缺失** |
| **错误处理检查**（v1.4.0 新增） | **G 类** | **检查前端 API 调用的 catch/then 分支是否包含错误提示逻辑，检查 error handler 是否被注释或遗漏** |

**步骤 5：修复回归**

| 修复级别 | 流程 | 对接 DevFlow |
|:---------|:-----|:-------------|
| P0/P1 问题 | 回退 Step 3 修复 → 更新 DevLogReport → 重新执行相关测试 | 复用 `testing-stage-execution` 缺陷闭环流程 |
| P2 问题 | 记录到问题跟踪记录 → 本版本修复或列入下一版本 | 复用问题跟踪记录机制 |

> 修复回归直接复用 DevFlow 现有的缺陷闭环流程（P0/P1 回退 Step 3 修复→重新测试），不另建修复流程。

#### 3.3.4 T3b 深度用例

**目标**：对高频页面/链路验证 CRUD/筛选/分页/错误态，验证功能正确性而非仅"不报错"。

**优先级排序规则**：按业务影响排序，而非页面复杂度。

| 优先级 | 排序依据 | 典型页面/服务 |
|:------:|:---------|:-------------|
| P0 | 直接影响收入或安全 | billing、api-keys |
| P1 | 核心业务配置 | providers、models |
| P2 | 辅助功能页面 | settings、open-models |

**CRUD 全覆盖硬性规则**（v1.3.0 新增）：

> 每个管理类模块必须覆盖 CRUD（Create/Read/Update/Delete）至少 3 类操作。仅做只读用例（Read-only）不允许通过 T3b 门禁。此规则源自 OpenLLM BUG-v2.9.0-MODEL-001 教训：模型管理仅有 2 个只读用例，"添加模型"按钮空实现未被任何用例覆盖。

| 模块类型 | CRUD 最低要求 | 不适用声明 |
|:---------|:-------------|:-----------|
| 管理类模块（增删改查） | C+R+U+D 至少 3 类 | 如某操作确不适用，需在测试报告中说明原因 |
| 配置类模块（仅查看/修改） | R+U 至少 2 类 | 删除/创建不适用时需声明 |
| 审计/日志类模块（仅查看） | R+搜索+分页 | C/U/D 不适用时需声明 |

**每个高频页面/链路必须覆盖**：

- CRUD 操作（创建/读取/更新/删除）
- 筛选/搜索/分页
- 错误态（接口失败时的错误提示和恢复）
- 空态（无数据时的引导）

#### 3.3.4a 用例设计规范（v1.3.0 新增）

**用例命名规范**：

```

```

**用例结构规范**：

每个 E2E 用例必须包含以下结构：

```python
@pytest.mark.e2e
def test_xxx(self, e2e_page_context, e2e_base_url):
    """E2E-XXX-NNN: 用例描述

    验证点：
    - 验证点1
    - 验证点2

    断言策略：L1-硬断言 / L2-条件断言

    # 1. 前置条件检查

    page = e2e_page_context["page"]
    page.goto(f"{e2e_base_url}/xxx")

    # 3. 操作步骤（每步都有明确的断言）
    # 步骤1：...
    # 步骤2：...

    # 4. 结果验证（硬断言）
    assert ...
```

**用例评审规则**：

新增 E2E 用例需通过以下评审检查：

| 检查项 | 要求 |

| 覆盖对齐 | 用例数是否满足覆盖矩阵要求 |

#### 3.4.1a 人机协同定位（v1.3.0 新增）

> 源自 OpenLLM 测试方法论改进方案。自动化测试通过后，人工测试不是"可选"而是"必选"。必须明确"自动化覆盖什么、人工补位什么"。

| 测试类型 | 负责方 | 覆盖范围 | 时机 |
|:---------|:-------|:---------|:-----|
| T3a 自动化巡检 | 工具 | 页面加载 + 错误信号 + 静默失败检测 | 每次构建 |

| **T4 人工测试** | **测试人员** | **探索性测试 + 边界条件 + 视觉验证 + 真实用户流** | **自动化通过后（必选）** |

#### 3.4.1b 人工测试检查清单（v1.3.0 新增）

每个核心模块的人工测试必须覆盖以下 5 大类检查项：

**A. 基础功能验证**

- [ ] 页面正常加载，核心元素可见
- [ ] 所有按钮可点击且有预期响应（无静默失败）
- [ ] 所有表单可填写且可提交
- [ ] 所有筛选/搜索功能正常工作

**B. CRUD 完整链路**

- [ ] 创建：填写表单→提交→成功提示→列表刷新→新数据可见
- [ ] 读取：列表加载→详情页加载→数据正确
- [ ] 编辑：打开编辑→修改数据→保存→列表更新→详情页数据一致
- [ ] 删除：点击删除→确认对话框→确认→成功提示→列表移除

**C. 边界条件与异常**

- [ ] 必填字段为空时提交→显示校验错误
- [ ] 输入超长字符→不崩溃
- [ ] 输入特殊字符（SQL 注入、XSS）→被正确处理
- [ ] 网络断开时操作→显示友好错误提示
- [ ] 并发操作（两人同时编辑）→数据一致性

**D. 视觉与交互体验**

- [ ] 响应式布局在不同分辨率下正常
- [ ] 加载状态（loading）正确显示
- [ ] 空状态（empty）正确显示
- [ ] 错误状态正确显示
- [ ] 操作反馈（成功/失败提示）及时且清晰

**E. 真实用户流**

- [ ] 模拟真实用户从登录到完成核心任务的完整路径
- [ ] 跨模块数据流转正确（如：创建模型→配置路由→调用 API）
- [ ] 浏览器前进/后退按钮行为正确

### 3.5 测试覆盖矩阵（v1.3.0 新增）

> 源自 OpenLLM 测试方法论改进方案。覆盖矩阵是识别测试缺口的核心工具，使"哪些模块覆盖薄弱"可视化。

#### 3.5.1 矩阵结构

每个管理类模块按以下维度建立覆盖矩阵：

| 模块 | 页面加载 | 创建交互 | 编辑交互 | 删除交互 | 搜索筛选 | 分页 | 导出 | 目标用例数 |
|:-----|:-------:|:-------:|:-------:|:-------:|:-------:|:---:|:---:|:---------:|
| {核心模块1} | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | — | 6 |
| {核心模块2} | ✅ | ✅ | ✅ | ⭕ | ✅ | ✅ | — | 5 |
| {辅助模块} | ✅ | — | — | — | ✅ | ✅ | ✅ | 4 |

**图例**：✅ 必须覆盖 | ⭕ 按需覆盖 | — 不适用

#### 3.5.2 矩阵维护规则

1. **矩阵文件位置**：`doc/testing/{项目名}-测试覆盖矩阵-v{版本}.md`
2. **更新时机**：每次版本发布前、每次新增模块时、每次新增用例时
3. **审批流程**：矩阵变更需测试负责人评审，确保覆盖完整性
4. **缺口追踪**：矩阵中标记为 ✅ 但无对应用例的项，列为测试缺口，按优先级补全

#### 3.5.2a 覆盖缺口分析方法论（v1.4.0 新增）

> 源自 OpenLLM 测试方法论改进方案。覆盖矩阵建立后，必须进行"现有 vs 目标"缺口分析，量化测试覆盖薄弱点并制定补全计划。

**缺口分析表格式**：

| 模块 | 现有用例数 | 目标用例数 | 缺口 | 补全优先级 | 计划补全版本 |
|:-----|:---------:|:---------:|:----:|:----------:|:----------:|
| {核心模块1} | 2 | 5 | **+3** | P1 | v{当前版本} |
| {核心模块2} | 3 | 6 | +3 | P2 | v{下一版本} |
| {辅助模块} | 4 | 4 | — | — | — |
| **合计** | **{总和}** | **{目标总和}** | **+{缺口总和}** | — | — |

**缺口分级规则**：

| 缺口等级 | 判定条件 | 处置要求 |
|:--------:|:---------|:---------|
| 🔴 P0 缺口 | 核心业务模块（直接影响收入/安全）且缺口 ≥ 2 | 本版本必须补全，阻塞发布 |
| 🟡 P1 缺口 | 核心配置模块且缺口 ≥ 1，或核心业务模块缺口 = 1 | 本版本补全，可延期 1 版本但需技术债登记 |
| 🟢 P2 缺口 | 辅助模块/配置类模块的缺口 | 列入后续版本计划，不阻塞发布 |

**缺口追踪闭环**：

```
矩阵建立 → 缺口识别 → 缺口分级 → 补全计划 → 用例编写 → 矩阵更新 → 缺口关闭
                                                    ↑                    │
                                                    └── 未关闭的缺口流转到下一版本 ──┘
```

> 缺口分析表作为测试覆盖矩阵文档的必填附件，每版本更新。未关闭的 P0/P1 缺口需在技术债务总表中登记。

#### 3.5.3 覆盖矩阵作为 Stage4 强制产出

测试覆盖矩阵纳入 Stage4 产出物清单，作为测试回溯审计的必填附件。

### 3.6 测试度量体系（v1.3.0 新增）

> 源自 OpenLLM 测试方法论改进方案。度量驱动测试改进，无度量则无法评估测试有效性。

#### 3.6.1 度量指标

| 指标 | 定义 | 目标值 | 度量频率 |
|:-----|:-----|:------:|:---------|
| 用例覆盖率 | 已有用例数 / 目标用例数 | ≥90% | 每版本 |
| 硬断言比例 | L1 硬断言用例数 / 总用例数 | ≥60% | 每版本 |
| 软断言数量 | 禁止模式出现次数 | 0 | 每版本 |
| 巡检覆盖率 | 巡检覆盖页面数 / 总页面数 | 100% | 每构建 |
| 静默失败检测覆盖率 | 检测的关键按钮数 / 总关键按钮数 | ≥90% | 每构建 |
| **缺陷逃逸率** | 人工发现的缺陷数 / (自动化发现 + 人工发现) | ≤20% | 每版本 |
| 人工测试执行率 | 实际执行的人工测试项 / 计划项 | 100% | 每版本 |

> **缺陷逃逸率**是衡量自动化测试有效性的核心指标。逃逸率 >20% 说明自动化测试存在系统性盲区，需触发测试架构评审。

## 10. 术语表（v1.4.0 新增）

> 源自 OpenLLM 测试方法论改进方案附录。统一术语定义，确保规范全文理解一致。

| 术语 | 说明 |
|:-----|:-----|
| CRUD | Create-Read-Update-Delete，标准数据操作四件套 |
| 软断言 | if-else 分支让测试总是通过的断言模式，掩盖功能缺失 |
| 硬断言（L1） | 关键元素必须满足预期，否则测试失败的断言模式 |
| 条件断言（L2） | 可选功能存在则验证，不存在则 skip（非 else 通过） |
| 存在性断言（L3） | 核心元素必须可见，辅助元素可选 |
| 静默失败 | 不产生错误信号但功能未实现的状态（如按钮点击无响应） |
| 行为信号检测 | 检测用户操作后系统是否有预期响应（区别于错误信号检测） |
| 表单提交错误被吞没 | API 返回 4xx/5xx 但前端未显示错误提示给用户 |
| 缺陷逃逸率 | 人工发现的缺陷占总缺陷的比例，衡量自动化测试有效性 |
| 覆盖矩阵 | 模块×用例类型的二维矩阵，可视化测试覆盖完整性 |
| 覆盖缺口 | 覆盖矩阵中标记为"必须覆盖"但无对应用例的项 |
| 巡检工具 | 自动化遍历页面检测错误的工具（如 page_scan.py） |
