## 3. 内容一致性风险分析

### 风险 1（🔴 高）：技术债务总表 —— 6 阶段独立修改，无同步锁

每个阶段的风险归集门禁都要求"发现 P1+ 风险时打开总表新增条目并列入本阶段输出"，但：

| 风险 | 描述 |
|:-----|:------|
| **并发修改** | Stage 2 和 Stage 3 可能同时对总表做修改，后改的会覆盖先改的 |
| **版本漂移** | 总表只有一个文件，没有版本分支控制，无法区分"v2.8.4 的总表"和"v2.8.5 的总表" |
| **缺乏变更记录** | 谁在什么时候改了什么条目，没有日志 |
| **当前规避方式** | 各阶段顺序执行，不存在真正并发；但跨阶段回溯时无法追溯 |

**建议**：总表添加修订历史章节，每次修改追加一行记录。

### 风险 2（🟡 中）：候选需求池/规划总纲/路线图 —— 仅 Step 0 修改

这些文档只在 Step 0 创建或更新，后续阶段不会再触及。但：

| 风险 | 描述 |
|:-----|:------|
| **候选需求池冻结** | 如果 Step 2 或 Step 3 发现新需求或新风险，按规范应该走范围变更流程，但**没有强制要求同步更新候选需求池** |
| **路线图过期** | 版本发布后路线图不会自动更新状态，需要手动维护 |
| **当前规避方式** | 版本范围变更总记录手动记录延期/新增 |

**建议**：Step 5 的发布复盘阶段追加一条"同步候选需求池状态"的检查项。

### ~~风险 3（🟡 中）：version.json / config.json —— 跨阶段信息孤岛~~【已消除】

| 文件 | 说明 |
|:-----|:------|
| `version.json` | TD-029 规划合并到 `devflow-config.json`（框架权威配置），不再是独立配置源 |
| `.devflow/config.json` | TD-029 规划重命名为 `.devflow/project-config.json`（项目配置），不再是独立文件 |
| 现状 | 当前遗留的旧文件是过渡状态，待 TD-029 偿还后自然消除 |

**结论：此问题已在候选需求池 V2100-004 和 TD-029 中覆盖，不再单独跟踪。**
