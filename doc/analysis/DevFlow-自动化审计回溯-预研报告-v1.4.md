## 1. 现状分析

### 1.1 当前审计门禁总览

DevFlow 项目当前共定义了 **44 个审计/验证检查点**，分布在 6 个阶段中：

| 阶段 | 检查点数 | 覆盖范围 |
|:----:|:--------:|:---------|
| **全局门禁**（跨阶段） | 3 | 产出物真实性、风险归集、问题跟踪 |
| **Step 0 版本规划** | 1 | 版本规划评审 |
| **Step 1 需求分析** | 2 | 需求评审、需求评估审计 |
| **Step 2 架构设计** | 6 | 入场门禁、后端/原型/可观测性覆盖、设计评审、需求架构对比 |
| **Step 3 编码** | 12 | 静态质量、安全审计、运行验证、逻辑审查、审计移交 |
| **Step 4 测试** | 6 | 证据抽查、覆盖率门禁、E2E 验证、回溯审计 |
| **Step 5 部署运维** | 14 | Release Checklist、证据审计、运维审计、闭环审计 |
| **总计** | **44** | |

### 1.2 现有审计流程

各阶段审计的验证逻辑：

```
Step 2 完成 → 需求架构对比审计    验证 RT→DT（人工对比追溯矩阵）
Step 3 完成 → 开发审计移交        验证 DT→TD（人工对比追溯矩阵）
Step 4 完成 → 测试回溯审计        验证 TT→RT（人工对比追溯矩阵）
Step 5 完成 → 全流程闭环审计      汇总确认（人工编写审计报告）
```

### 1.3 当前审计的薄弱点

| 问题 | 描述 | 严重度 |
|:-----|:------|:------:|
| **P1** 依赖"声称"而非"证据" | 审计主要是检查文档中填写的 ID 对应关系，而不是独立重新执行验证 | 🔴 |
| **P2** 追溯链验证全人工 | 人工逐项核对 ID 链条，耗时 30~60 分钟/次且容易遗漏 | 🔴 |
| **P3** 审计报告手工编写 | 全流程闭环审计报告靠手动整理，耗时 60~120 分钟/次 | 🟡 |
| **P4** 审计证据分散 | Git log、文档、测试报告分别在不同文件中，需要打开 6~10 个文件交叉对比 | 🟡 |

## 2. 核心问题识别

### 2.1 本质问题：审计是"形式核验"还是"独立复审"？

当前审计的实质是**形式核验**——检查各阶段声称的产出物是否存在、ID 是否一一对应。这不等于"阶段真实完成了"。

**举例**：
- 测试报告写了"覆盖率 85%，用例全部通过" → 审计只检查了这句话有没有写，**没有重新跑一遍测试验证**
- 开发阶段声称"产出物全部创建" → 审计只核对追溯矩阵里的文件名清单，**没有独立去 LS 目录重新盘点**
- Release Checklist 全部打勾 → 审计只确认是否都有 ✅ 标记，**没有重新执行验证命令看结果是否一致**

### 2.2 什么是真正的"独立审计"

DevFlow 的 v2.10.0 已经引入了两条独立复审机制作为先例：
- **4.0b 自测证据抽查**：进入 Step 4 后，随机抽取 Step 3 的 1~2 个自测用例独立重新执行，对比结果是否一致
- **5.11b 发布后证据审计**：从 Release Checklist 随机抽 3 项，独立重新执行验证命令

这两条的核心逻辑是相同的：**AI 独立重做一遍，看结果跟声称的是否一致**。

### 2.3 投入产出估算

| 环节 | 当前耗时（每次发布） | 预期独立审计后 |
|:-----|:-------------------:|:--------------:|
| 追溯链独立验证 | 30~60 分钟 | 5~10 分钟 |
| 产出物独立盘点 | 15~30 分钟 | 2~5 分钟 |
| 关键检查点复查 | 15~30 分钟 | 5~10 分钟 |
| 审计报告编写 | 60~120 分钟 | 5~15 分钟 |
| **合计** | **120~240 分钟** | **15~40 分钟** |

## 3. 核心方案：独立审计师

### 3.1 方案定位

新增 `audit-agent` 技能，定位为**独立审计师**。不是替代各阶段执行检查，而是在各阶段完成后**独立重新验证关键审计点**，对比"声称结果"和"实际结果"是否一致。

**核心理念**：

```
各阶段 → 声称完成（自我声明）
    ↓
audit-agent → 独立复审（重新验证）
    ↓
判决：✅ 一致 → 通过      ❌ 不一致 → 标记虚假勾选，返回修正
```

### 3.2 与传统审计的区别

| 对比维度 | 传统形式审计 | 独立审计师方案 |
|:---------|:------------|:--------------|
| **验证方式** | 检查文档内容（"有没有写"） | 独立重新执行（"结果对不对"） |
| **追溯链验证** | 人工对比追溯矩阵中的 ID | AI 从 Git log 和文件自行提取 ID 交叉比对 |
| **产出物盘点** | 人工查看目录列表 | AI 执行 LS 命令逐一盘点 |
| **检查点复查** | 无复查机制 | 随机或全量重新执行关键验证命令 |
| **证据真实性** | 假设声称者为真 | 对比声称结果和实际结果，不一致则标记 |
| **审计报告** | 手工编写 Markdown | AI 汇总所有审计发现生成报告 |

### 3.3 为什么用技能而不是脚本

不编写独立脚本，而是创建 SKILL.md。由 AI 自主完成以下操作：

```
Read    → 读文档内容、追溯矩阵、测试报告
Grep    → 搜索 ID 引用、匹配关键字
LS      → 列出目录确认文件存在性
RunCommand → 执行验证命令（git tag/ls-remote/coverage）
对比    → 声称结果 vs 实际结果，标记不一致
Write   → 生成审计报告 Markdown
```

## 4. 审计能力设计

### 4.1 审计能力矩阵

```
audit-agent（独立审计师）
│
├─ 能力 1：追溯链独立验证     ← AI 独立提取 ID 交叉比对
│   ├─ RT→DT（Step 2 完成后调用）
│   ├─ DT→TD（Step 3 完成后调用）
│   ├─ TT→RT（Step 4 完成后调用）
│   └─ 全链汇总（Step 5 发布时调用）
│
├─ 能力 2：产出物独立盘点     ← AI 独立 LS 目录核对
│   ├─ 各阶段完成时核对本阶段产出物
│   ├─ Step 5 全阶段汇总盘点
│   └─ ⭐ 子步骤产出物完整性验证 ← 按子步骤清单逐一检查产出物存在性
│
├─ 能力 3：关键检查点复查     ← AI 独立重新执行验证命令
│   ├─ 版本号一致性（cat version.json vs Git tag）
│   ├─ 测试覆盖率（重新扫描或读取报告数据）
│   ├─ 构建验证（重新执行构建命令）
│   ├─ 远程同步（git ls-remote 各远程 Tag）
│   ├─ ⭐ 仓库备份验证（git push --dry-run 检查远程连通性 + ls-remote 对比各远程 Tag 一致性）
│   └─ 随机抽查（从本阶段检查点中抽 1~2 项复现）
│
└─ 能力 4：审计报告生成       ← AI 汇总发现生成报告
    ├─ 各阶段审计记录
    └─ 全流程闭环审计报告
```

### 4.2 能力 2 详解：子步骤产出物完整性验证

**背景**：每个阶段的技能文档定义了若干子步骤，每个子步骤都有明确的产出物。LLM 可能跳过部分子步骤（如不执行静态质量检查直接进入自测），但现有门禁无法发现这种"跳步"。

**验证逻辑**：

```
For 每个阶段:
  读取该阶段技能文档 → 提取所有子步骤及其标准产出物
  LS 目标目录 → 获取实际产生的文件列表
  逐一对比:
    子步骤产出物存在 ✅ → 该子步骤已执行
    子步骤产出物缺失 ❌ → 该子步骤可能被跳过，标记为"待确认"
```

**各阶段子步骤产出物验证清单**：

| 阶段 | 子步骤数 | 关键验证目录 | 典型可跳过检查点 |
|:----:|:--------:|:-------------|:-----------------|
| Step 0 | 7 | `doc/version/releases/v{版本号}/` | 版本规划评审记录存在性 |
| Step 1 | 10 | `doc/requirements/` | 需求评估报告存在性 |
| Step 2 | 12 | `doc/design/` | 后端/原型/可观测性覆盖检查报告 |
| Step 3 | 12 | `doc/development/` | 静态质量检查记录、代码逻辑审查记录、开发审计移交材料 |
| Step 4 | 11 | `doc/testing/` | 自测证据抽查记录、覆盖率报告、测试回溯审计报告 |
| Step 5 | 12 | `doc/release/` | 发布复盘报告、运维审计报告、全流程闭环审计报告 |

**与编码规范审查的分工**：

| 责任方 | 职责 | 时机 |
|:-------|:-----|:-----|
| **编码规范审查（coding-stage-execution 3.4a/3.4b）** | 在编码阶段执行时阻止跳步，"你跳过了 3.4a，请返回执行" | 编码进行中 |
| **audit-agent 产出物完整性验证** | 阶段完成后独立验证，"你声称完成了但缺少 XX 产出物" | 阶段审计时 |

### 4.4 能力 3 详解：仓库备份验证

**背景**：Step 5 的远程仓库备份（push 到 origin / backup / github 三个远程）是发布流程的关键环节，也是 LLM 最容易跳过或虚假勾选的步骤。v2.10.0 发布复盘发现，release.ps1 中 backup 和 github 推送被标记为"非阻塞"（失败仍可继续），且无独立验证机制。

**验证方式**：

```
验证步骤：
[1] 读取当前 Tag：git tag -l v{版本号}
[2] 列出配置的远程仓库：git remote -v
[3] 对每个远程：
      git ls-remote {remote} refs/tags/v{版本号}
      → 返回 commit hash，与本地 Tag 的 hash 对比
[4] 全部一致 ✅ → 备份完整
    任一远程缺失 ❌ → 标记"备份不完整" + 输出缺失的远程名
```

**验证命令**：

```bash
# 获取本地 Tag 的 commit hash
git rev-parse v{版本号}

# 获取各远程 Tag 的 commit hash
git ls-remote origin refs/tags/v{版本号}
git ls-remote backup refs/tags/v{版本号}
git ls-remote github refs/tags/v{版本号}

# 三方 hash 必须全部一致
```

**自愈建议**：对于缺失的远程，输出补推命令：

```bash
git push {缺失远程名} v{版本号}
```

### 4.5 触发时机

```
Step 2 完成 → 调用 audit-agent：验证 RT→DT + 设计阶段产出物盘点
                                              + 设计阶段 1 个关键检查点复查
Step 3 完成 → 调用 audit-agent：验证 DT→TD + 编码阶段产出物盘点
                                              + 编码阶段 1 个关键检查点复查
Step 4 完成 → 调用 audit-agent：验证 TT→RT + 测试阶段产出物盘点
                                              + 测试阶段 1 个关键检查点复查
Step 5 发布 → 调用 audit-agent：全链汇总 + 全阶段产出物总盘点
                                              + 随机抽取 3 项关键检查点复查（5.11b）
                                              + 生成全流程闭环审计报告
```

### 4.3 证据真实性判定逻辑

```
对于每次复查：

[1] 读取阶段声称结果（文档/报告/Checklist）
[2] 独立重新执行验证
[3] 对比声称 vs 实际

    一致 ✅ → "证据真实，审计通过"
    不一致 ❌ → "证据虚假：声称{A}但实际{B}，返回修正"
    部分一致 ⚠️ → "N 项中有 M 项不一致，其余通过"
```

### 4.4 各阶段审计能力覆盖

| 阶段 | 审计能力 | 验证方式 |
|:----:|:---------|:---------|
| **Step 2** | ① 追溯链：RT→DT  | Grep 追溯矩阵 + Read 设计文档交叉比对 |
| | ② 产出物：设计阶段文档 | LS doc/design/ 核对标准产出清单 |
| | ③ 复查：抽取 1 个设计检查点 | 重新验证（如：API 字段是否与需求一致） |
| **Step 3** | ① 追溯链：DT→TD | Git log footer 提取 TD-ID + Read 编码文档交叉比对 |
| | ② 产出物：编码阶段文档 | LS doc/development/ + 构建产物目录 |
| | ③ 复查：抽取 1 个编码检查点 | 重新执行静态质量检查或运行验证 |
| **Step 4** | ① 追溯链：TT→RT | Read 测试报告提取 TT-ID + 追溯矩阵交叉比对 |
| | ② 产出物：测试阶段文档 | LS doc/testing/ 核对标准产出清单 |
| | ③ 复查：抽取 1 个测试检查点 | 重新执行 1 个核心测试用例（4.0b 升级） |
| **Step 5** | ① 全链汇总 | 将前三段的链条串联为完整链路 |
| | ② 全阶段产出物总盘点 | LS 六个目录全量核对 |
| | ③ 复查：随机 3 项关键检查点 | 重新执行验证命令对比结果（5.11b） |
| | ④ 审计报告生成 | 汇总所有发现生成全流程闭环审计报告 |

## 5. 实施路径与阶段规划

### 5.1 三阶段交付

```
Phase 1（最小可行版本）
  创建 audit-agent 技能 + 追溯链独立验证
  └─ 创建 audit-agent/SKILL.md 基础框架
  └─ 实现能力 1：追溯链独立验证（RT→DT→TD→TT）
  └─ Step 2/3/4 完成时人工调用试运行
  └─ 预估投入：半天

Phase 2（扩展）
  产出物独立盘点（含子步骤完整性验证）+ 关键检查点复查
  └─ 追加能力 2：产出物独立盘点 + 子步骤产出物完整性验证
  └─ 追加能力 3：关键检查点复查
  └─ 替代现有的 4.0b 和 5.11b 手工抽查机制
  └─ 预估投入：1 天

Phase 3（成熟）
  审计报告自动生成 + 全流程集成
  └─ 追加能力 4：审计报告自动生成
  └─ 与 Step 5 全流程闭环审计无缝集成
  └─ AI 独立产出审计报告，人工仅需审核确认
  └─ 预估投入：1~2 天
```

### 5.2 每个 Phase 的输入输出

| Phase | 输入 | 输出 | 前置条件 |
|:-----:|:-----|:-----|:---------|
| **Phase 1** | Git log、追溯矩阵、各阶段文档 | 追溯链完整度报告 + 断点清单 | 各阶段 ID 编号规范 |
| **Phase 2** | 六阶段产出目录、现有检查命令 | 产出物盘点表 + 复查结果对比表 | Phase 1 验证通过 |
| **Phase 3** | Phase 1+2 的输出 + 历史审计报告 | 全流程闭环审计报告（Markdown） | Phase 2 验证通过 |

## 6. 风险评估

| 风险 | 级别 | 应对措施 |
|:-----|:----:|:---------|
| AI 复查时误判"声称"和"实际"不一致（假阳性） | 🟡 中 | 提供人工复核按钮，AI 标记"可疑"而非直接"否决" |
| 部分检查点无法用命令重新执行（如设计评审） | 🟢 低 | 这类检查点标记为"人工不可替代"，保留人工评审，AI 只验证可重现的部分 |
| AI 生成的审计报告出现幻觉 | 🟡 中 | 报告头部标注"AI 生成，人工已审核"；关键数据（数字/通过率）直接填入，LLM 只写分析文本 |
| 历史版本无标准 ID 引用 | 🟢 低 | 从当前版本开始启用，历史版本标记"未启用自动化审计" |
| 每个阶段都调用 audit-agent 是否太频繁 | 🟢 低 | Phase 1 仅 Step 2/3/4/5 各一次，共 4 次调用，与现有审计频率一致 |

## 7. 结论与建议

### 7.1 可行性判断

| 维度 | 结论 |
|:-----|:------|
| **技术可行性** | ✅ **高** — 创建 SKILL.md，零代码开发成本，AI 利用现有能力完成阅读/搜索/执行/生成全流程 |
| **投入产出比** | ✅ **高** — 半天完成 Phase 1，每次发布节省 2~4 小时审计时间 |
| **审计质量** | ✅ **高于现状** — 从"形式核验"升级为"独立复审"，能发现虚假勾选 |
| **与现有流程兼容性** | ✅ **高** — 与 4.0b/5.11b 机制一脉相承，不改变现有 6 阶段流程 |

### 7.2 推荐路径

```
优先实施 Phase 1：创建 audit-agent 技能 + 追溯链独立验证
  └─ 投入：半天
  └─ 收益：从"人工核验追溯矩阵"升级为"AI 独立提取 ID 交叉比对"
  └─ 验证后推进 Phase 2/3
```

## 附录 A：Phase 1 技能设计（概念示意）

```markdown
## audit-agent — 独立审计师

本技能作为独立审计师，在各阶段完成后独立重新验证关键审计点。
不替代各阶段的执行检查，而是验证"声称结果 vs 实际结果"是否一致。

### 审计准备
1. 读取当前版本号：从 version.json 获取
2. 确定审计范围：当前阶段和前序阶段
3. 读取阶段声称结果：审计移交文档、Checklist

### 能力 1：追溯链独立验证

步骤：
1. 从 Git log 提取所有 commit footer 中的 RT-ID / DT-ID / TD-ID / TT-ID
2. 从各阶段文档提取相同的 ID 集合
3. 交叉比对两个集合的覆盖率
4. 输出：通过率 + 断点清单（声称有但 Git 无 / Git 有但声称无）

### 能力 2：产出物独立盘点

步骤：
1. 用 LS 列出目标阶段目录
2. 对照标准产出清单逐一核对
3. 标记：存在 ✅ / 缺失 ❌ / 多余 ⚠️

### 能力 3：关键检查点复查

步骤：
1. 读取本阶段检查记录中的"验证命令"和"声称输出"
2. 重新执行该命令
3. 对比实际输出与声称输出

### 能力 4：审计报告生成

汇总以上发现生成审计报告。
```
