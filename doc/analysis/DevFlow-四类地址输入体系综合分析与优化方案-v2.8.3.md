## 一、问题总览

### 1.1 四类地址定义

DevFlow 的"三步走"工作流（下载 → 安装 → 初始化）涉及四类关键地址，分属不同层级、由不同组件管理：

| 编号 | 地址类型 | 概念 | 存储位置 | 管理组件 |
|:---:|---|---|---|---|
| A | **DevFlow 远程仓库地址** | DevFlow 工具链自身的 Git 仓库，用于下载和更新 DevFlow 插件 | 插件根目录 `version.json` → `repository` | `download-devflow.ps1` |
| B | **下载到本地的副本地址** | DevFlow 插件包在用户本地文件系统中的存放目录 | 不存储，命令行参数指定 | `download-devflow.ps1` |
| C | **本地项目地址** | 用户业务项目的根目录路径（即 Git 仓库所在目录） | 不存储，即当前工作目录 | （用户自行决定） |
| D | **项目远程仓库地址** | 用户项目的 origin / backup Git 远程仓库地址 | `.devflow/config.json` → `remote.*` | `devflow-init`（应）+ `devflow-project-config`（规范） |

### 1.2 问题全景

当前四类地址的输入体系存在**三类核心问题**：

| 问题类别 | 涉及地址 | 严重程度 | 说明 |
|---|---|---|---|
| **① 概念混淆** | A + D | P1 | 用户分不清"DevFlow 仓库地址"和"项目仓库地址" |
| **② 执行缺口** | D（项目远程仓库） | P0 | 规范要求交互输入，但 devflow-init 直接写空值，绕过了整个流程 |
| **③ 默认值策略不一致** | A/B/C/D | P2 | 有的阻断、有的静默、有的自动检测，缺乏统一的分级策略 |

## 二、四类地址现状详解

### 2.1 A — DevFlow 远程仓库地址

| 项目 | 详情 |
|---|---|
| **概念** | DevFlow 工具链自身的 Git 仓库地址，用于下载和更新 DevFlow 插件 |
| **存储位置** | 插件根目录 `version.json` → `repository` 字段 |
| **输入时机** | 运行 `download-devflow.ps1 -Action SetRepo` 时交互式输入 |
| **默认值** | **空字符串 `""`**（全新安装时为空） |
| **空值行为** | 🔴 **阻断操作** — Clone/Update 模式报错：`Repository URL not set in version.json` |
| **输入校验** | 无显式 URL 格式校验，仅判断是否为空 |
| **devflow-init 是否处理** | ❌ 不处理 — devflow-init 只读 TRAE 系统目录版本号 |

**流程**：
```
download-devflow.ps1 -Action SetRepo
  → 显示当前值（空则提示"No repository URL configured"）
  → Read-Host 输入新地址
  → 写入 version.json 的 repository/homepage/bugs 字段
  → 提示下一步运行 Clone
```

### 2.2 B — 下载到本地的副本地址

| 项目 | 详情 |
|---|---|
| **概念** | DevFlow 插件包在用户本地文件系统中的存放路径 |
| **存储位置** | 不存储，由命令行参数 `-TargetDir` 指定 |
| **输入时机** | `download-devflow.ps1 -Action Clone` 时交互式确认 |
| **默认值** | 🟢 **脚本所在目录**（`$ScriptDir`） |
| **输入方式** | 先显示默认目录，用户 Y 确认或 n 后输入自定义目录 |
| **devflow-init 是否处理** | ❌ 不处理 |

**流程**：
```
download-devflow.ps1 -Action Clone
  → 读取 version.json 中的 repository
  → 显示目标目录（默认：脚本所在目录）
  → Read-Host "Clone to this directory? (Y/n)"
  → Y: 使用默认目录 / n: 输入自定义目录
  → 执行 git clone
```

### 2.3 C — 本地项目地址

| 项目 | 详情 |
|---|---|
| **概念** | 用户业务项目的根目录路径，即 Git 仓库所在目录 |
| **存储位置** | 不存储（就是当前工作目录） |
| **设置时机** | 用户 `git clone` 或创建项目时自行决定 |
| **devflow-init 中的项目名检测** | 自动检测：`package.json` → `git remote get-url origin` → 当前目录名 |
| **devflow-init 是否交互输入** | ❌ 不交互，纯自动检测 |
| **devflow-init 是否修改路径** | ❌ 不修改，只在当前目录工作 |

**项目名检测优先级链**：
```
① package.json 的 name 字段
② git remote get-url origin 中的仓库名
③ 当前目录名
```

### 2.4 D — 项目远程仓库地址（origin / backup）

| 项目 | origin | backup |
|---|---|---|
| **概念** | 用户项目的主 Git 远程仓库地址 | 用户项目的备份 Git 远程仓库地址 |
| **存储位置** | `.devflow/config.json` → `remote.origin` | `.devflow/config.json` → `remote.backup` |
| **输入时机** | ⚠️ **规范有要求但实际未执行** | ⚠️ **规范有要求但实际未执行** |
| **模板默认值** | 🟡 **空字符串 `""`** | 🟡 **空字符串 `""`** |
| **devflow-init 交互输入？** | ❌ 不输入，直接写空 | ❌ 不输入，直接写空 |
| **devflow-project-config 规范要求** | ✅ 必须交互输入，留空需强警告 + 用户主动确认 | ✅ 同上 |
| **空值影响** | 项目名检测时 fallback 到目录名 | 自动备份 Hook 不工作，静默跳过 |

**规范来源**：`devflow-project-config/SKILL.md` §"初始化仓库地址设置"

```
规范要求的流程：
1. 展示仓库地址输入界面
2. 提示用户输入 Git 远程仓库地址（origin 和 backup）
3. 输入可留空，但必须显示强警告
4. 用户必须主动确认留空或填写后方可进入下一步
5. 确认后写入 config.json

实际 devflow-init 的行为：
→ 直接创建 config.json，remote.origin 和 remote.backup 写死为空字符串
→ 无任何交互提示
→ 无警告信息
→ 无地址区分说明
```

## 三、执行缺口深度分析（D 类地址核心问题）

### 3.1 缺口是怎么产生的？

通过 git 历史追溯，还原了时间线：

| 版本 | devflow-project-config | devflow-init | 缺口状态 |
|---|---|---|---|
| v2.1.0~v2.5.0 | 基础结构，逐步完善 | 基础结构，逐步完善 | 尚无交互规范 |
| **v2.6.1** | **新增"初始化仓库地址设置"章节**，明确 5 步交互流程 | config.json 模板 remote 仍为空 | **缺口产生** |
| v2.7.0~v2.8.3 | 字段重命名等维护 | 增加版本检测、技能检测等新功能 | 缺口**持续 7 个版本未修复** |

### 3.2 为什么会产生这个缺口？

#### 根因一：规范写在被调用方，执行入口在调用方

这是最核心的架构设计问题：

```
devflow-init（调用方，执行入口）
  │
  ├── §3 有 config.json 完整模板（remote 写死为空） ← LLM 看到这个，直接用
  │
  └── 文末表格："devflow-project-config：生成 config.json 的具体逻辑委托给此技能" ← 权重太低，LLM 容易忽略
        │
        └── devflow-project-config（被调用方，规范定义）
              └── "初始化仓库地址设置"：要求 5 步交互 ← 规范在这里，但 LLM 不容易读到
```

**本质**：对于基于文档的技能系统（不是代码的函数调用），"委托关系"只是一行文字描述，没有强制约束力。LLM 的倾向是"就地取材"——文档里有模板就直接用，不会主动跳去读另一个技能的详细规范。

#### 根因二：v2.6.1 补全规范时只改了被调用方

v2.6.1 的 commit 是 "backfill V260-006~012"，是一次补全性修改。推测当时：
1. 在 devflow-project-config 中补充了初始化交互的规范
2. 但忘记同步修改 devflow-init 中的模板和流程
3. 之后的版本都在加新功能，没人回头审查这个老缺口

#### 根因三：技能是文档而非代码，没有编译期检查

| 代码系统 | 文档技能系统 |
|---|---|
| 函数签名不一致 → 编译报错 | 规范与执行不一致 → 无人知晓 |
| 有单元测试覆盖 | 无自动化测试 |
| 有静态检查工具 | 只能靠人工评审 |

#### 根因四：问题的隐蔽性

这个问题藏得深：
- **不报错** — config.json 生成了，只是值为空
- **有退路** — 用户可以手动编辑
- **跨技能** — 单独看任何一个技能都觉得"没问题"
- **功能降级不明显** — 主要影响的是备份功能，而备份本身是可选的

## 四、综合优化方案

### 4.1 设计原则

1. **执行入口原则**：关键流程必须写在触发执行的技能里，不能只放在被调用方
2. **统一分级原则**：四类地址的默认值和空值处理遵循统一的分级策略
3. **清晰区分原则**：在每个地址输入点都明确说明"这是什么地址，不是什么地址"
4. **渐进暴露原则**：先展示当前值，再询问是否修改，降低用户认知负担

### 4.2 地址分级策略（统一）

对四类地址建立统一的重要性分级，指导默认值策略和交互方式：

| 级别 | 地址类型 | 重要性 | 默认值策略 | 空值处理 |
|---|---|---|---|---|
| 🔴 核心必配 | DevFlow 下载地址（A） | 没有就无法下载更新 | 空，必须手动设置 | 阻断操作，报错提示 |
| 🟡 重要建议 | 项目 origin（D1） | 影响项目名检测和备份 | 空，建议设置 | 强警告 + 用户主动确认留空 |
| 🟢 可选配置 | 项目 backup（D2） | 仅影响自动备份 | 空，可选设置 | 提示功能不可用，不阻断 |
| 🟢 自动检测 | 下载目录（B） | 只是存放位置 | 脚本所在目录 | 交互确认，可修改 |
| 🟢 自动检测 | 项目根目录（C） | 就是当前目录 | 当前目录 | 自动检测，无需交互 |

### 4.3 方案一：devflow-init 增加完整的远程仓库交互流程（P0）

**修改位置**：`devflow-init/SKILL.md`

在 §1.7（检测项目版本号）和 §2（推断当前阶段）之间插入 **§1.8 项目远程仓库地址配置（交互式）**

#### §1.8.1 地址类型区分说明

```markdown
> ⚠️ 【重要区分】以下配置的是「您的业务项目」的 Git 远程仓库地址，
> 不是 DevFlow 工具链的下载地址。
>
> | 地址类型 | 说明 | 示例 |
> |---------|------|------|
> | DevFlow 下载地址 | DevFlow 工具链自身的仓库，用于下载更新 | `http://git.example.com/devflow.git` |
> | 项目 origin 地址 | 您当前项目的主 Git 仓库 | `http://git.example.com/your-project.git` |
> | 项目 backup 地址 | 您当前项目的备份 Git 仓库（可选） | `http://backup.example.com/your-project.git` |
```

#### §1.8.2 已有配置检测

```
如果 .devflow/config.json 已存在：
  → 读取 remote.origin 和 remote.backup 的当前值
  → 展示当前配置
  → 询问用户："远程仓库地址是否需要修改？(Y/n)"
  → n（默认）: 保持不变，继续下一步
  → Y: 进入交互修改流程

如果 .devflow/config.json 不存在（首次初始化）：
  → 进入首次配置流程
```

#### §1.8.3 Step A — 输入 origin 地址

```
提示：
  请输入您项目的 Git 远程仓库地址（origin）：
  格式：https://host/org/repo.git 或 git@host:org/repo.git
  （可留空，但将影响项目名检测和自动备份功能）

校验：
  - 允许空值
  - 非空值须为合法 Git URL 格式（http/https/ssh/git 协议）
  - 格式错误时提示并重试（最多 3 次）
```

#### §1.8.4 Step B — 输入 backup 地址（可选）

```
提示：
  请输入备份仓库地址（backup，可选）：
  用于自动镜像备份，留空则不启用自动备份。

校验：同 Step A，但始终可选。
```

#### §1.8.5 Step C — 空值强警告（当 origin 留空时）

```
⚠️ 【警告】您未配置项目远程仓库地址（origin）
后果：
  - 项目名称只能从目录名推断（可能不准确）
  - 自动备份功能将不可用
  - 版本发布时需手动配置远程仓库

确认继续留空吗？(y/N)
默认 N：返回 Step A 重新输入
输入 y 确认：继续
```

#### §1.8.6 写入配置

将确认后的地址写入 `.devflow/config.json` 的 `remote.origin` 和 `remote.backup` 字段。

### 4.4 方案二：config.json 模板移除空值默认值（P0）

**修改位置**：`devflow-init/SKILL.md` §3

**当前问题**：模板中直接写了 `"origin": ""` 和 `"backup": ""`，LLM 看到就直接用了。

**修改后**：

```json
{
  "project": "{项目名称}",
  "projectVersion": "{1.7 检测到的版本号}",
  "branchStrategy": "git-flow",
  "remote": {
    "origin": "{由 §1.8 交互式配置获取，不得直接写空值}",
    "backup": "{由 §1.8 交互式配置获取，可选，默认为空}"
  },
  ...
}
```

并在模板上方增加 ⛔ 标记：

```
⛔ 【强制】remote.origin 和 remote.backup 字段必须通过 §1.8 的交互式配置获取。
不得在初始化时直接写入空字符串。
如果用户确认留空，应记录用户确认操作后再写入空值。
```

### 4.5 方案三：初始化报告增加四类地址汇总表（P1）

在 devflow-init §5 的输出报告中，增加地址配置汇总表，让用户一目了然：

| 地址类型 | 当前值 | 状态 |
|---|---|---|
| DevFlow 下载地址 | `http://.../devflow.git` | ✅ 已配置 |
| DevFlow 本地目录 | `D:\tools\devflow-plugin\` | ✅ |
| 项目根目录 | `D:\projects\myproject\` | ✅ |
| 项目 origin | `http://.../myproject.git` | ✅ 已配置 |
| 项目 backup | *(空)* | ⚠️ 未配置，自动备份不可用 |

### 4.6 方案四：download-devflow.ps1 增加 URL 格式校验（P2）

在 SetRepo 模式中增加 Git URL 格式校验：

```powershell
function Test-GitUrl($url) {
    if ($url -match '^(https?|git|ssh)://') { return $true }
    if ($url -match '^git@[\w.-]+:[\w.-]+/[\w.-]+\.git$') { return $true }
    return $false
}
```

格式错误时提示并重试，避免用户输入无效地址后 clone 失败才发现。

### 4.7 方案五：跨技能一致性审计机制（P2，长期防御）

在 `code-logic-review` 技能的审查维度中，增加一条：

> **技能间委托关系一致性**：如果 A 技能声明"委托给 B 技能"或"调用 B 技能"，必须验证：
> 1. B 技能中存在对应的规范/流程描述
> 2. A 技能的执行流程中包含了对 B 技能规范的正确引用（而非仅在文末表格中提及）
> 3. A 技能中没有内联与 B 技能规范不一致的模板或流程

**作用**：防止未来其他技能间出现类似的"规范架空"问题。

## 七、验证方案

### 7.1 功能验证

| 场景 | 预期行为 |
|---|---|
| 全新项目，首次初始化 | 执行完整交互流程：区分说明 → origin 输入 → backup 输入 → 写入 config.json |
| 全新项目，origin 留空 | 显示强警告，要求用户输入 y 确认留空 |
| 已有项目，origin 已配置 | 显示当前值，询问是否修改（默认不修改） |
| 已有项目，origin 为空 | 提示 origin 未配置，询问是否现在配置 |
| URL 格式错误（方案四上线后） | 提示格式错误，允许重新输入 |

### 7.2 一致性验证

| 验证项 | 通过标准 |
|---|---|
| devflow-init 与 devflow-project-config 一致 | 交互流程的步骤、字段、警告文案一致 |

## 八、核心结论与教训

### 8.1 问题本质

四类地址输入体系的问题不是一个单点 bug，而是**系统性的设计偏差**：

1. **执行入口与规范定义分离** — 规范在被调用方，执行在调用方，中间靠一行文字连接
2. **默认值策略不统一** — 有的阻断、有的静默、有的自动检测，缺乏全局设计
3. **概念区分不充分** — DevFlow 仓库 vs 项目仓库的区别只在一个技能里提了一句，用户容易混淆

### 8.2 核心教训

对于基于文档的技能系统（不是代码的函数调用）：

> **教训一**：关键流程必须写在触发执行的那个技能里，不能假设 LLM 会主动去读被调用方的详细规范。
>
> **教训二**："委托关系"只能作为补充说明，不能作为主要的执行驱动。
>
> **教训三**：跨技能的一致性需要有审计机制保障，不能只靠人工评审。

### 8.3 预期收益

| 收益 | 说明 |
|---|---|
| 用户体验提升 | 首次初始化时自动引导配置，不需要用户手动编辑 config.json |
| 备份功能可用率 | 更多用户正确配置 backup，自动备份才能真正发挥作用 |
| 地址混淆减少 | 明确的区分说明降低用户填错地址的概率 |
| 规范执行一致 | 技能间的委托关系不再是纸面约定 |
| 长期防御能力 | 跨技能审计机制防止类似问题在其他地方复发 |
