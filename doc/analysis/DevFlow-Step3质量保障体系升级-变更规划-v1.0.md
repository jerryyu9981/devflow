## 一、变更背景

### 1.1 问题来源

在实际项目中发现 Step 3 编码阶段存在"假完成"现象：
- 文档（DevLogReport、静态检查报告、代码审查报告）写得很完善
- 但代码积累了大量历史技术债务
- 代码质量持续劣化，长期拖慢迭代速度

### 1.2 核心根因（7 条）

1. **完成标准结构性缺陷** — 只卡 P0/P1，P2/P3 只记录不解决
2. **技术债务只进不出** — 没有还债机制，只记录不偿还
3. **可维护性审查太软** — 排第 11 位，不影响结论
4. **LLM 天然倾向** — 先求能用，不求好，审查放水
5. **散落在多环节但全是软约束** — Step 0/Step 3/CI/CD 都管，但都管不住
6. **缺少全局台账和跨版本流转** — 历史债无人认领，总账一笔糊涂账
7. **缺少"可执行证据"层** — 全是文档证据，没有实际运行验证

### 1.3 与现有版本规划的关系

| 当前规划 | 状态 | 本次变更影响 |
|---|---|---|
| v2.8.3 | 已纳入（manifest 架构修复） | 不影响，v2.8.3 按原计划 |
| v2.9.0 | 原候选（全自动循环架构） | **重大调整** — 全自动循环移至 v3.0，v2.9.0 改为质量保障强化版 |
| v3.0.0 | 路线图规划（架构升级版本） | 增加全自动循环架构内容 |
| v2.8.x 后续 patch | 无规划 | **新增 v2.8.4** — 质量保障第一阶段（立即可落地的 P0 项） |

**v2.x 阶段整体定位**：人机协同 + 质量保障。在有人工介入和审批的前提下，确保每一步输出都是高质量的。不追求全自动，但追求"每一步都扎实"。

## 三、版本分配规划

### 3.1 分配原则

1. **P0 项优先落地** — 债务增长率红线 + 实际运行验证，这两项是核心分水岭
2. **全局台账先建后用** — 先有总表，还债配额和流转机制才能跑起来
3. **v2.x 聚焦质量保障** — 全自动循环移至 v3.0，v2.x 专注"人机协同 + 质量有保障"
4. **分三阶段，渐进式落地** — 每个版本都有独立价值，不搞一次性大改造
5. **每个版本有明确主题** — v2.8.4 建基础、v2.9.0 强化体系、v2.10.0 完善收尾

### 3.2 版本分配总表

**v2.x 阶段主题**：人机协同 + 质量保障
- v2.8.x：快速迭代，修复问题，打基础
- v2.9.0：质量体系全面强化
- v2.10.0：质量体系完善收尾

**v3.0 阶段主题**：全自动循环 + 架构升级
- 在 v2.x 质量体系基础上，引入自动化循环
- 没有质量保障的自动化是"快速生产垃圾"，所以必须先质量后自动化

### 4.3 v2.9.0 范围变更

原 v2.9.0 只有 5 项全自动循环需求，现在调整为：
- 移出：5 项全自动循环（移至 v3.0）
- 移入：15 项质量保障强化需求
- 净变化：工作量从"需预研"变为 ~3.9 人天，更可控

### 4.4 v3.0.0 范围调整

原 v3.0.0 规划：架构升级版本（技能架构重构、智能推荐、可观测性度量、多语言支持）

新增：全自动循环 5 项（retry-manager / empty-pool-detector / auto-degrade / fatal-error-handler / cycle-state-machine）

v3.0.0 成为"架构升级 + 全自动循环"双主题大版本。

### 4.5 风险评估

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 质量门禁太严，初期不适应 | 高 | 中 | 初期阈值放宽，逐步收紧；提供清晰模板 |
| v2.9.0 范围是否过大 | 中 | 中 | 15 项都是规范文档修改，代码量不大；可按需拆分到 v2.9.x |
| 全局总表维护成本 | 中 | 低 | 自动化工具辅助（静态检查生成报告） |
| v3.0 全自动循环依赖质量体系 | 低 | 高 | v2.x 先把质量打牢，v3.0 才有意义 |
| 人工审批工作量增加 | 高 | 低 | 这是 v2.x "人机协同"的正常代价，v3.0 再自动化 |
