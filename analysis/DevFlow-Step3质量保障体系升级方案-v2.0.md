## 一、问题现象

### 1.1 一句话概括

> **Step 3 的"完成"是文档层面的完成，不是代码质量层面的完成。**
>
> DevLogReport 写得很完善、代码逻辑审查结论是"通过"、静态检查记录齐全——但代码里积累了大量技术债务。

### 1.2 典型表现

| 层面 | 文档中的样子 | 实际代码中的样子 |
|---|---|---|
| **DevLogReport** | ✅ 结构完整，各章节齐全，技术债有记录 | — |
| **静态质量检查** | ✅ 有执行记录，P0/P1 全通过 | P2/P3 问题大量累积 |
| **代码逻辑审查** | ✅ 结论"通过"或"有条件通过" | 可维护性维度审查宽松 |
| **技术债务记录** | ✅ 每版本都有记录到 DevLogReport | 只记录不偿还，越积越多 |
| **功能交付** | ✅ 功能按需求实现了 | 实现质量差，后续维护成本高 |

### 1.3 更深层的问题："文档证据" ≠ "可执行证据"

技术债务只是冰山一角。更根本的问题是：

> **当前 Step 3 的所有质量门禁，本质上都是"文档证据"——LLM 可以写出来的证据。**

- ✅ LLM 可以写出静态质量检查的"命令和结果"
- ✅ LLM 可以写出自测用例和"测试通过"的记录
- ✅ LLM 可以写出代码逻辑审查报告
- ✅ LLM 可以写出 DevLogReport

**但 LLM 写出了"测试通过"不代表测试真的跑过。**

更严重的是：走查验证（代码审查的加强版）也解决不了这个问题。走查的本质还是"读代码"，只要没有实际运行，就存在以下盲区：

| 盲区 | 说明 | 走查能发现吗？ |
|---|---|---|
| **跑不起来** | 依赖缺失、配置错误、环境不兼容、路径写错 | ❌ 看不出来 |
| **性能差** | N+1 查询、内存泄漏、大循环、慢查询 | ❌ 看不出来 |
| **边界情况** | 空值、异常、并发、超时、重试路径 | ⚠️ 能发现一部分，太多了看不过来 |
| **集成问题** | 跨模块接口契约不一致、数据格式对不上 | ❌ 按模块看的，发现不了 |
| **审查者盲区** | LLM 审 LLM 的代码，有同类项盲区 | ❌ 自身局限 |

### 1.4 为什么说这是"假完成"？

Step 3 的完成标准（coding-stage-execution §完成标准）有 12 条，但核心门槛只有一条：

> **无未解决的 P0/P1 问题。**

这意味着：
- P2 级别的技术债务 → 不阻塞
- P3 级别的可维护性问题 → 不阻塞
- TODO/FIXME 标记 → 不阻塞
- 重复代码、高复杂度 → 不阻塞（只要没到 P1 阈值）
- 架构偏离、设计走样 → 记录下来就行，不阻塞
- **代码能不能真的跑起来** → 没有明确要求

**结果：每个版本都"完成"了，但每个版本都留下了一堆"以后再还"的债，而且没人真正确认过代码是不是真的能用。**

## 二、根因分析

### 2.1 根因一：完成标准的结构性缺陷

**当前完成标准的重心**：

```
P0/P1 问题全部关闭  ←  这是硬门槛，没通过就是没完成
    ↓
P2/P3 问题记录在案  ←  这是软要求，记录了就算完成
    ↓
技术债务写入 DevLogReport  ←  有记录就达标
```

**问题**：技术债务天然是 P2/P3 的，所以天然不阻塞 Step 3 完成。规范只要求"记录"，不要求"偿还"，也不设债务上限。

**类比**：就像考试只要求"不挂科"（P0/P1），但不管考了多少分。每学期都及格，但成绩一年比一年差。

### 2.2 根因二：技术债务只进不出的单向机制

当前规范中的技术债务管理流程：

```
编码中发现技术债 → 记录到 DevLogReport → Step 3 完成 → 进入 Step 4
                                                            ↑
                                             没有任何步骤要求还债！
```

coding-stage-execution §技术债务跟踪 写了 5 条规则，但其中：
- ✅ 记录新增债务（有）
- ✅ 分类（有）
- ⚠️ 偿还规则（只有一句话："评估是否在本版本内偿还"，没有强制执行）
- ✅ 自测时检查（有，但只是检查有没有记录）
- ✅ 三技能配合（有，但都是 P2/P3 级）

**核心缺失**：没有"债务上限"、没有"还债比例要求"、没有"累积到一定程度就阻塞新版本"的机制。

### 2.3 根因三：代码审查的可维护性维度太软

code-logic-review 的 11 个审查维度中，"可维护性"排在最后一位（第 11 维）。

审查优先级（code-logic-review §审查原则）：
> "先找阻塞测试/上线的问题，再找可维护性改进。"

这意味着：
1. 先查需求覆盖、设计一致、业务流程、API 契约、数据一致、权限安全——这些都是 P0/P1
2. 最后才看可维护性——这是 P2/P3
3. 如果前面的都过了，可维护性有点问题也只是"记录风险"，不阻塞通过

**结果**：可维护性审查成了"走过场"——有这个环节，但实际不影响结论。

### 2.4 根因四：LLM 的天然倾向——先求能用，再求（不）求好

LLM 写代码的典型模式：

1. 优先实现功能（满足需求）
2. 能跑通就行
3. 代码质量、可维护性、优雅程度——如果不明确要求，就不会主动做
4. 技术债务？先记下来，"以后再优化"

加上审查的 LLM 也是同样的倾向：
- "功能实现了吗？实现了。"
- "有 P0/P1 问题吗？没有。"
- "那通过吧。"

**两个人的标准都一样低 → 互相放水 → 债务累积。**

### 2.5 根因五：技术债务散落在多环节，但全是软约束

技术债务管理不是只在 Step 3，而是分布在 DevFlow 的多个环节中：

| 环节 | 规范位置 | 具体内容 | 约束强度 |
|---|---|---|---|
| **Step 0 版本规划** | version-planning-stage-execution §技术债务评估 | 审查现有债务，确定 15-20% 容量还债 | ⚠️ 软约束（"确定计划"≠"真的执行"） |
| **Step 3 静态质量检查** | coding-stage-execution §3.4 | 复杂度、重复率、TODO 扫描 | ⚠️ 软约束（P2/P3 不阻塞） |
| **Step 3 技术债务审计** | coding-stage-execution §3.7 | 扫描新增债务，记录到 DevLogReport | ⚠️ 软约束（只记录，不要求偿还） |
| **Step 3 代码逻辑审查** | code-logic-review 第 11 维 | 可维护性审查（含技术债） | ⚠️ 软约束（排最后一位，不影响结论） |
| **CI/CD 流水线** | cicd-pipeline-management | 技术债 >10% P1 阻断，>20% P0 阻断 | ✅ 硬约束（但阈值高，平时触不到） |

**问题**：每个环节都有技术债务管理的规范，但每个环节都是软约束——
- Step 0 说"15-20% 容量还债"，但执行不执行没人管
- Step 3 说"记录到 DevLogReport"，但记录了就完了
- CI/CD 有门禁，但阈值太高（10%/20%），大部分项目到不了

**结果**：看起来每个环节都在管技术债，实际上每个环节都管不住。

### 2.6 根因六：缺少全局技术债务台账和跨版本流转机制

这是本次分析的**重大发现**——规范里有每个版本的技术债务清单，但没有全局汇总和流转机制。

#### 当前的记录方式（分散在各版本）

| 记录位置 | 文档名 | 存放路径 | 覆盖范围 |
|---|---|---|---|
| 单版本规划文档章节 | 技术债务清单章节 | `doc/version/releases/v{版本号}/` | 单版本 |
| 独立技术债务清单 | `{项目名}-技术债务清单-v{版本号}.md` | `doc/version/releases/v{版本号}/` | 单版本 |
| DevLogReport | 新增债务记录章节 | `doc/development/` | 单版本新增 |

#### 缺失的关键一环

全部版本文档（`doc/version/global/`）中有这些全局文档：

| 全局文档 | 有吗？ |
|---|---|
| 版本规划总纲 | ✅ |
| 版本迭代路线图 | ✅ |
| 候选需求池 | ✅ |
| 版本范围变更总记录 | ✅ |
| 版本发布策略总则 | ✅ |
| **技术债务总表** | ❌ **没有！** |

#### 这导致了什么问题？

```
v2.5.0 技术债务清单：10 条债
    ↓
v2.6.0 技术债务清单：？（从哪来？从上版本继承吗？规范没说）
    ↓
v2.7.0 技术债务清单：？（更不知道了）
    ↓
v2.8.0 技术债务清单：？（历史债务已经一笔糊涂账了）
```

version-planning-stage-execution 说"审查现有技术债清单"，但没说从哪里审查——
- 是从上一个版本的清单继承吗？
- 还是每次重新扫描？
- 已偿还的债务怎么标记和验证？
- 挂起的债务怎么流转、怎么升级？

**规范没说清楚。** 实际执行时很可能就是：每个版本重新扫一遍，历史债要么忘了、要么不算了、要么越积越多但没人知道总数是多少。

### 2.7 根因七：缺少"可执行证据"层

这是最深层的根因——当前 Step 3 的质量体系完全建立在"文档证据"之上：

```
静态检查报告（文档）
    +
自测报告（文档）
    +
代码审查报告（文档）
    +
DevLogReport（文档）
    =
Step 3 完成
```

所有这些都是"写出来的证据"，没有一层是"跑出来的证据"。

**缺失的关键一层：实际运行验证。**

没有这一层，上面所有的文档证据都可能是"自证清白"——自己写报告证明自己做对了。

## 三、核心框架：Step 3 可信度金字塔

为了解决上述问题，我们建立一个从低到高的可信度层级模型：

```
┌─────────────────────────────────────────────────┐
│  第 5 层：端到端集成验证                          │  ←  最高可信度
│  （全链路跑通、多模块协同、契约一致）              │     真的能用
├─────────────────────────────────────────────────┤
│  第 4 层：性能基准测试                            │  ←  不仅能用，还够快
│  （响应时间、吞吐量、资源占用、退化对比）          │
├─────────────────────────────────────────────────┤
│  第 3 层：自动化测试 + 覆盖率                     │  ←  不仅主路径对，边界也有保障
│  （单元测试、集成测试、异常路径、覆盖率指标）      │
├─────────────────────────────────────────────────┤
│  第 2 层：实际运行 + 冒烟测试   ◄── 关键分水岭     │  ←  代码真的能跑起来
│  （构建通过、服务启动、健康检查、核心路径冒烟）    │
├─────────────────────────────────────────────────┤
│  第 1 层：走查 / 代码审查                        │  ←  逻辑上看起来是对的
│  （需求覆盖、设计一致、业务流程、可维护性）        │
├─────────────────────────────────────────────────┤
│  第 0 层：静态质量检查                            │  ←  没有低级错误
│  （语法、Lint、类型、一致性、复杂度、重复率）      │
└─────────────────────────────────────────────────┘
         ↑
  文档证据区 ← | → 可执行证据区
         第 2 层是分水岭
```

**关键洞察**：

> **第 2 层（实际运行 + 冒烟测试）是"文档证据"和"可执行证据"的分水岭。**
>
> 没有这一层，上面所有的审查、走查、分析——本质上都是"文档对文档"。
> 有了这一层，才算真正摸到了"代码能不能用"的底线。

各层级的可信度和成本：

| 层级 | 名称 | 可信度 | 实施成本 | 当前是否有 |
|---|---|---|---|---|
| L0 | 静态质量检查 | ⭐⭐ | 低 | ✅ 有（code-static-quality-check） |
| L1 | 走查/代码审查 | ⭐⭐⭐ | 中 | ✅ 有（code-logic-review） |
| L2 | 实际运行 + 冒烟测试 | ⭐⭐⭐⭐ | 中低 | ❌ 缺失 |
| L3 | 自动化测试 + 覆盖率 | ⭐⭐⭐⭐⭐ | 中高 | ⚠️ 有但不强制 |
| L4 | 性能基准测试 | ⭐⭐⭐⭐⭐ | 高 | ⚠️ 有但按需 |
| L5 | 端到端集成验证 | ⭐⭐⭐⭐⭐ | 高 | ⚠️ 有但仅多轨道时触发 |

## 四、完整治理方案

### 方案一：技术债务增长率红线（P0，立即可用）

**核心规则**：每个版本的**新增技术债务不得超过本版本变更代码量的 X%**，超过则 Step 3 不通过。

**具体设计**：

| 指标 | 定义 | 红线 |
|---|---|---|
| **新增 TODO/FIXME 数量** | 本版本新增的 TODO、FIXME、HACK、XXX 标记 | 新增 ≤ 5 个（或按代码量比例） |
| **代码复杂度增量** | 新增/修改函数的圈复杂度、认知复杂度 | 高复杂度函数新增 ≤ 3 个 |
| **重复代码增量** | 新增的重复代码块 | 新增重复率 ≤ 3% |
| **架构偏离度** | 新增代码中违反既有架构/分层约定的部分 | 零容忍（P1） |

**执行位置**：coding-stage-execution §3.4 静态质量检查 + §3.7 技术债务审计

**通过条件**：
- 所有红线指标均在阈值内 → 通过
- 超过红线但有合理理由（紧急修复、临时方案有明确偿还计划）→ 有条件通过，需在 DevLogReport 中明确偿还计划和时间
- 超过红线且无合理理由 → 不通过，必须优化后重新审查

---

### 方案二："还债配额"机制（P1，每个版本强制还债）

**核心规则**：每个版本必须偿还一定比例的历史技术债务，否则 Step 3 不通过。

**具体设计**：

| 规则 | 说明 |
|---|---|
| **还债比例** | 每个版本至少偿还 **本版本预估工作量的 15~20%** 的历史债务 |
| **还债来源** | 从候选需求池的技术债类需求中挑选，或从 DevLogReport 历史债务中认领 |
| **验证方式** | DevLogReport 中必须有"本版本偿还债务清单"章节，列出偿还了哪些债、怎么验证的 |
| **豁免条件** | P0 级紧急修复版本可以豁免，但必须在下一个正常版本补还 |

**类比**：就像信用卡还款——每个月必须还最低还款额，不能一直只借不还。

---

### 方案三：代码审查"可维护性"权重升级（P1）

**当前问题**：可维护性是第 11 维，排在最后，实际执行时容易放水。

**改进方案**：

1. **调整审查顺序**：把"可维护性"从最后一位移到第 6 位（中间位置），明确它不是"有空再看"的
2. **增加"可维护性否决项"**：以下情况即使功能正确也不能通过：
   - 单个函数超过 200 行且无合理理由
   - 复制粘贴超过 3 处的相似代码
   - 关键模块无注释、无文档
   - 魔数/硬编码字符串超过 5 个且未提取为常量
3. **审查结论中必须有可维护性专项评价**：不能只说"通过"，必须说明可维护性水平（好/中/差）和主要问题
4. **审查必须有证据支撑**：每一项审查结论必须引用具体的代码位置或数据，不能笼统说"可维护性好"

---

### 方案四：全局技术债务台账 + 跨版本流转机制（P1，长期治理基础）

> **这是本次分析的重大发现补充：当前规范只有单版本技术债务清单，缺少全局总表和跨版本流转机制，导致历史债务无人认领、越积越多。**

#### 4.1 全局技术债务总表

**定位**：技术债务的"总账本"，所有债务从产生到消亡的全生命周期记录。

**存放位置**：`doc/version/global/技术债务总表.md`（与版本规划总纲、候选需求池等全局文档同级）

**每条债务的完整字段**：

| 字段 | 说明 | 示例 |
|---|---|---|
| **债务编号** | 全局唯一编号，格式 TD-YYYY-NNN | TD-2026-017 |
| **类别** | 安全债/架构债/测试债/代码整洁债/性能债/文档债 | 架构债 |
| **严重级别** | P0 / P1 / P2 / P3 | P2 |
| **来源版本** | 在哪个版本被首次识别 | v2.5.0 |
| **发现方式** | 静态检查 / 代码审查 / 自测发现 / 线上问题 / 人工识别 | 静态检查 |
| **影响范围** | 哪些模块、功能或团队受影响 | 用户模块、订单模块 |
| **问题描述** | 具体是什么问题 | 用户服务分层不清晰，Controller 直接操作数据库 |
| **建议修复方式** | 怎么还这笔债 | 按三层架构重构，提取 Service 层 |
| **预估工作量** | 修复需要多少人天 | 3 人天 |
| **当前状态** | 待处理 / 偿还中 / 已偿还 / 已接受（不还了） | 待处理 |
| **计划偿还版本** | 预计在哪个版本还 | v2.9.0 |
| **实际偿还版本** | 实际在哪个版本还的 | — |
| **挂起/接受理由** | 如果不立即还，理由是什么 | 当前版本优先级低，先做核心功能 |
| **老化版本数** | 已经挂了多少个版本没处理 | 2 |
| **上次升级时间** | 严重级别上次升级是什么时候 | — |

#### 4.2 跨版本债务流转机制

**生命周期流程**：

```
Step 0 版本规划
    │
    ├─→ 从全局总表继承所有"待处理"债务
    ├─→ 选择本版本要偿还的债务（15-20% 容量）
    ├─→ 标记"偿还中"，指定计划版本
    └─→ 不偿还的记录挂起理由
            │
            ↓
    Step 3 编码阶段
            │
            ├─→ 偿还的债务：修复后验证 → 标记"已偿还"，记录实际版本
            ├─→ 新增的债务：录入全局总表，分配编号，标记"待处理"
            └─→ 未偿还的债务：老化版本数 +1
                    │
                    ↓
            债务老化升级规则
                    │
                    ├─→ P3 挂起 3 个版本 → 升级为 P2
                    ├─→ P2 挂起 3 个版本 → 升级为 P1
                    └─→ P1 升级后 → 阻塞 Step 3，必须处理
                            │
                            ↓
                    Step 5 版本发布后
                            │
                            └─→ 全局总表更新：所有债务状态同步
```

#### 4.3 季度回顾机制

1. **每季度做一次技术债务审计**：
   - 统计债务总量变化趋势（总数、各级别数量、环比变化）
   - 识别"最值得还的债"（收益/成本比最高的 Top 10）
   - 检查老化升级情况，看看有多少债升级了
   - 评估还债配额执行情况（每个版本真的还了 15-20% 吗？）

2. **输出季度技术债务报告**：
   - 债务概况（总量、分布、趋势）
   - 本季度偿还清单
   - 本季度新增清单
   - 下季度重点偿还建议
   - 风险预警（即将升级的债务、高风险债务）

3. **纳入版本规划**：
   - 季度审计结果作为下季度版本规划的重要输入
   - 高优先级债务必须纳入下个版本的还债配额

|---|---|
| version-planning-stage-execution §技术债务评估 | 明确"审查现有技术债清单"= 从全局技术债务总表继承 |
| project-document-management 全部版本文档 | 增加"技术债务总表"作为全局文档之一 |
| project-document-templates 技术债务清单模板 | 单版本清单增加"从全局总表继承"的说明 |

| DevLogReport | 增加"本版本偿还债务清单"和"新增债务清单"，与全局总表对应 |

### 方案五：实际运行 + 冒烟测试（P0，核心分水岭）

> **这是整个方案中最重要的一项——从"文档证据"跨越到"可执行证据"的关键一步。**

**核心规则**：Step 3 完成前，必须实际运行代码并验证核心路径可用。

#### 5.1 三层验证模型

| 层级 | 验证内容 | 具体做法 | 必须产出 |
|---|---|---|---|
| **L2-A 构建验证** | 代码能不能编译/打包 | 执行构建命令，必须零错误 | 构建命令 + 构建输出片段（最后 20 行） |
| **L2-B 启动验证** | 服务能不能起来 | 实际启动服务，等待健康检查端点返回 200 | 启动命令 + 健康检查结果 + 启动日志片段 |
| **L2-C 冒烟测试** | 核心功能能不能用 | 跑 3~5 个最核心的用例，必须全过 | 冒烟用例清单 + 每个用例的执行命令和输出 |

#### 5.2 不同类型产出物的验证方式

| 产出物类型 | L2-A 构建验证 | L2-B 启动验证 | L2-C 冒烟测试 |
|---|---|---|---|
| **后端 API 服务** | `npm run build` / `mvn package` | 启动服务 + `/health` 端点 | curl 调用 3~5 个核心接口 |
| **前端 Web 应用** | `npm run build` | 启动 dev server / 预览构建产物 | 浏览器打开 3~5 个核心页面 |
| **脚本 / CLI 工具** | 语法检查 / 类型检查 | —（脚本直接执行） | 运行 3~5 个核心命令场景 |
| **数据库变更** | — | 执行 migration 脚本 | 验证 schema 结构 + 种子数据 |
| **DevFlow 技能文档** | 格式检查（markdownlint） | — | 按文档流程模拟执行一遍 |
| **PowerShell 脚本** | 语法检查（`-NoProfile -Command`） | — | 实际运行脚本，验证退出码和输出 |
| **配置文件** | JSON/YAML schema 校验 | 加载配置验证 | 验证配置项完整性 |

#### 5.3 证据要求

- 所有命令必须是**可复现的**——审查者可以照着同样的命令跑出同样的结果
- 输出片段必须是**真实的**——不能只写"通过"，必须有实际输出
- 时间戳必须是**新鲜的**——执行时间必须在提交前 24 小时内
- 代码版本必须是**对应的**——验证的必须是当前 commit 的代码

#### 5.4 纳入 Step 3 完成标准

在 coding-stage-execution §完成标准中增加：

> **第 13 条：代码已通过实际运行验证（构建 + 启动 + 冒烟测试），核心路径可正常执行。**

### 方案六：测试覆盖率 + 异常路径专项（P1，边界保障）

**解决的问题**：走查只能覆盖主路径，边界情况看不过来。

#### 6.1 覆盖率底线

| 模块级别 | 行覆盖率底线 | 分支覆盖率底线 |
|---|---|---|
| **P0 核心模块** | ≥ 80% | ≥ 70% |
| **P1 重要模块** | ≥ 60% | ≥ 50% |
| **P2 一般模块** | ≥ 40% | ≥ 30% |
| **P3 边缘模块** | 不做强制要求 | 不做强制要求 |

#### 6.2 异常路径清单

Step 3 交付时必须列出"本功能有哪些异常场景"，形成一张矩阵：

| 异常场景 | 严重级别 | 是否有测试 | 测试结果 | 备注 |
|---|---|---|---|---|
| 入参为空 | P1 | ✅ | 通过 | |
| 依赖服务超时 | P1 | ✅ | 通过 | 超时时间 5s |
| 数据库连接失败 | P0 | ✅ | 通过 | 有重试机制 |
| 并发写入冲突 | P2 | ❌ | — | 记录风险，后续补充 |

未覆盖的异常场景必须说明风险和降级方案。

#### 6.3 覆盖率数据要求

- 必须是**工具生成的**（不是手写的）
- 必须包含**实际输出片段**（覆盖率报告的摘要部分）
- 必须与**当前代码版本**对应

### 方案七：性能基准测试（P2，按需强制）

**解决的问题**：走查看不出性能问题。

#### 7.1 适用范围

不是每个版本都做全面性能测试，但以下情况必须做：

- P0 功能开发或重大重构
- 性能敏感模块变更
- 上一版本有性能退化记录
- 用户反馈了性能问题

#### 7.2 基准指标

| 类型 | 验证方式 | 门槛设置 |
|---|---|---|
| **API 响应时间** | 压测工具（k6 / wrk / ab） | P0 接口 P95 < 200ms，P1 接口 P95 < 500ms |
| **页面加载** | Lighthouse / WebPageTest | LCP < 2.5s，CLS < 0.1 |
| **数据库** | 慢查询日志 + EXPLAIN 关键 SQL | 没有全表扫描，索引命中 |
| **内存** | 运行一段时间后观察内存占用 | 没有持续增长（内存泄漏） |

#### 7.3 退化对比

和上一个稳定版本对比，性能退化超过 20% 的必须解释或优化。

性能数据必须包含：测试命令、环境信息、结果数据、与上版本对比。

### 方案八：端到端集成验证（P1，多模块时强制）

**解决的问题**：每个模块单独看都对，拼到一起就错。

#### 8.1 触发条件

只要涉及两个以上模块/服务的变更，就必须有至少一条端到端集成验证用例。

#### 8.2 验证方式

| 方式 | 说明 | 适用场景 |
|---|---|---|
| **API 契约测试** | 前后端/各服务之间的接口用契约测试保证一致 | 多团队/多服务项目 |
| **端到端冒烟** | 从用户入口到数据落库全链路跑一遍 | 所有项目 |
| **数据流转验证** | 追踪一条数据从输入到存储到输出的完整路径 | 数据密集型项目 |
| **集成环境验证** | 在类生产环境中实际部署和运行 | 中大型项目 |

#### 8.3 与现有规范的衔接

coding-stage-execution 里已经有"三端贯通测试"（§3.6 跨轨道集成验证），但目前是"至少两个开发轨道激活"才触发。

**建议改为**：只要涉及两个以上模块/服务，就必须有至少一条端到端集成验证用例。

API 契约一致性验证（api-contract-management 技能）从"按需"升级为"涉及多端时强制"。

### 方案九：证据真实性强化（P1，防假证据）

**解决的问题**：LLM 可以写出假的测试/审查报告。

| 措施 | 说明 | 防放水效果 |
|---|---|---|
| **实际输出片段要求** | 所有测试、检查、构建的结果不能只写"通过"，必须包含实际命令和输出片段（至少 10~20 行关键输出） | ⭐⭐⭐⭐ |
| **可复现要求** | 所有命令必须是可复现的——审查者可以照着同样的命令跑出同样的结果 | ⭐⭐⭐ |
| **交叉验证** | 静态检查结果 ↔ 自测结果 ↔ DevLogReport 记录 ↔ 代码审查结论，四者必须互相印证 | ⭐⭐⭐⭐ |
| **新鲜度要求** | 所有验证必须在提交前 24 小时内执行，且必须对应当前 commit 的代码 | ⭐⭐⭐ |
| **随机抽查机制** | Step 4 测试阶段随机抽取 1~2 个自测用例实际运行，验证是否真的通过 | ⭐⭐⭐⭐⭐ |
| **审查证据链要求** | 每一项审查结论必须引用具体的代码位置或数据，不能笼统说"没问题" | ⭐⭐⭐ |

### 5.2 实施路径

#### 第一阶段：立即执行（本周内）

**目标**：建立"可执行证据"底线，遏制新增债务，先把总账建起来。

- **方案一**（债务增长率红线）：在 coding-stage-execution 中增加红线指标
- **方案五**（实际运行 + 冒烟测试）：Step 3 完成标准增加"构建 + 启动 + 冒烟"三层验证
- **方案三**（可维护性权重升级）：code-logic-review 调整可维护性位置和否决项

#### 第二阶段：下一个版本开始

**目标**：建立还债机制，提高边界质量，打通跨版本流转。

- **方案二**（还债配额）：每个版本 15~20% 工作量还债

- **方案六**（测试覆盖率 + 异常路径）：覆盖率底线 + 异常路径矩阵
- **方案九**（证据真实性强化）：交叉验证 + 新鲜度 + 抽查机制

**成本**：约 1 人天（规范修改）+ 每个版本实际还债工作量
**效果**：债务总量开始下降，边界质量提升，债务流转机制跑通

#### 第三阶段：下季度起

**目标**：建立长期治理体系，全面提升质量。

- **方案四第三步**（季度回顾机制）：每季度技术债务审计，输出季度报告
- **方案七**（性能基准测试）：P0 功能和性能敏感模块强制性能基准
- **方案八**（端到端集成验证）：多模块变更强制集成验证

**成本**：约 1 人天（机制建立）+ 每季度 0.5 人天（回顾）
**效果**：长期可持续的质量保障体系

## 六、对当前项目的建议

既然已经发现了大量历史技术债务，建议按以下步骤处理：

### 第一步：摸清底数（1~2 天）

1. 做一次全面的技术债务扫描（静态检查工具 + 人工审查）
2. 建立技术债务总表，按 P0/P1/P2/P3 分级
3. 统计总量和分布（哪些模块欠债最多、什么类型的债最多）
4. 做一次"实际运行验证"——当前版本的代码能不能构建、能不能启动、核心功能能不能用？（很可能这一步就能发现问题）

### 第二步：分类处置

| 债务级别 | 处置方式 |
|---|---|
| **P0/P1 债务** | 立即修复，不能拖 |
| **P2 高收益债务** | 在下个版本中优先偿还（收益/成本比高的） |
| **P2 低收益债务** | 排入还债配额，逐步消化 |
| **P3 债务** | 记录在案，接受现状，等有合适机会再处理 |

### 第三步：先做一次"实际运行验证"试点

在全面推行方案五之前，先在当前项目上做一次试点：

1. 尝试构建当前版本
2. 尝试启动服务
3. 跑几个核心用例
4. 看看会发现多少问题

这一步的结果本身就很有价值——它会告诉你当前的"完成"到底有多少水分。

### 第四步：建立机制

把方案一、三、五落地到 DevFlow 规范中，确保以后的版本不会再"假完成"。

## 八、总结

### 8.1 问题本质

Step 3 "假完成"的本质不是规范缺失——技术债务跟踪、可维护性审查、DevLogReport 这些规范都有。问题在于：

> 1. **规范只要求"记录"，不要求"解决"** — 技术债只进不出
> 2. **只卡 P0/P1，不管 P2/P3** — 质量底线太低
> 3. **全是文档证据，没有可执行证据** — 自己写报告证明自己做对了
> 4. **散落在多环节，但全是软约束** — 看起来每个环节都在管，实际上都管不住
> 5. **没有全局台账和跨版本流转** — 历史债无人认领，总账一笔糊涂账

### 8.2 核心对策

1. **给新增债务设红线** — 超过就不让过
2. **强制每个版本还一点债** — 不能只借不还
3. **建立"实际运行验证"层** — 从文档证据跨越到可执行证据（最关键）
4. **把可维护性审查从"软"变"硬"** — 不能功能对了就过
5. **覆盖率 + 异常路径** — 边界也要有保障
6. **建立全局台账和长期治理机制** — 不能一笔糊涂账
7. **强化证据真实性** — 防假证据、防放水

### 8.3 一句话总结

> **Step 3 的"完成"不应该是"文档写好了"，也不应该是"功能做出来了"，而应该是：**
>
> **代码能构建、能启动、核心路径能跑通、质量没有变差（最好还有所提升）。**
