# 系统架构设计技能覆盖评估报告

> **版本**：v1.0 | 2026-06-24
> **评估目的**：对比当前技能体系中的架构设计能力与业界最佳实践，识别覆盖缺口
> **评估范围**：单体服务、微服务、智能体（Agent）、混合架构 四种常见架构类型

---

## 一、当前技能中架构设计的覆盖现状

### 1.1 `design-stage-execution` 中架构相关内容

| 规范矩阵行 | 必须执行内容 | 通过标准 | 说明 |

## 二、四大架构模式的设计要素对比

### 2.1 单体架构（Monolithic Architecture）

**业界最佳实践应包含的设计要素：**

| 设计要素 | 业界推荐实践 | 当前技能覆盖 |
|:---------|:------------|:-----------:|
| 分层架构（表现层/业务层/数据层） | 明确的层职责和依赖方向 | ⚠️ 仅在 `project-coding-conventions` 中有三层约束（Controller/Service/Repository），但架构层面无完整定义 |
| 模块化拆分（按业务域分包） | 包结构设计、模块间依赖规则 | ❌ 未覆盖 |
| 启动/编译/构建策略 | Maven/Gradle 多模块、构建优化 | ❌ 未覆盖 |
| **单体拆分的触发条件** | CCN > 30 / 部署频率 < 周级 / 代码库 > 10万行 | ❌ 未覆盖 |

**适用场景判断**：当前模板没有关于"什么时候该选单体"的判断指引。业界标准认为用户量 ≤ 10 万、团队 ≤ 10 人、迭代周期 ≥ 2 周的项目适合单体起步。

### 2.2 微服务架构（Microservices Architecture）

**业界最佳实践应包含的设计要素：**

| 设计要素 | 业界推荐实践 | 当前技能覆盖 |
|:---------|:------------|:-----------:|
| 服务拆分（DDD 限界上下文） | 按业务域（用户/订单/支付）而非功能点拆分 | ❌ 未覆盖 |
| 服务通信 | gRPC（内部）+ RESTful（外部），HTTP/2 + Protobuf | ⚠️ `api-design` 覆盖 API 设计但未区分内外通信协议 |
| 服务注册与发现 | Kubernetes Service + CoreDNS / Nacos / Consul | ❌ 未覆盖 |
| **API 网关** | 统一入口、路由、限流、认证 | ❌ 未覆盖 |
| **配置中心** | Nacos / Apollo / K8s ConfigMap | ❌ 未覆盖 |
| **服务熔断/降级** | 断路器模式、熔断阈值、降级策略 | ❌ 未覆盖 |
| **分布式事务** | Seata TCC / RocketMQ 事务消息 / Saga 模式 | ❌ 未覆盖 |
| **服务网格** | Istio Sidecar 无侵入治理 | ❌ 未覆盖 |
| 容器化部署 | Docker + K8s（Deployment/Service/Ingress） | ✅ `docker` 技能存在，但无架构层面的服务编排设计 |
| 分布式链路追踪 | OpenTelemetry + Jaeger/Zipkin | ✅ `observability-standards` 有追踪规范 |
| **灰度发布/蓝绿部署** | Istio VirtualService + DestinationRule | ❌ 未覆盖 |
| 服务间依赖治理 | 禁止循环依赖、依赖 ≤ 3 层 | ❌ 未覆盖 |
| **弹性伸缩（HPA）** | K8s HorizontalPodAutoscaler | ❌ 未覆盖 |

**2025 年微服务技术栈共识**（基于业界调研）：Spring Cloud Alibaba / Micronaut + Kubernetes 1.30+ + Istio 1.20+ + RocketMQ 5.0 + MySQL 8.0 + Redis 7.0

### 2.3 智能体架构（Agent Architecture）

**业界最佳实践应包含的设计要素：**

| 设计要素 | 业界推荐实践 | 当前技能覆盖 |
|:---------|:------------|:-----------:|
| Agent 认知模式（ReAct） | Thought → Action → Observation 循环 | ❌ 未覆盖 |
| **Agent 工具使用** | @tool 装饰器定义、工具参数绑定、MCP 协议 | ⚠️ `mcp-builder` 覆盖 MCP，但 Agent 工具设计模式未覆盖 |
| **多 Agent 协作模式** | 顺序/广播/编排/聚合/级联/Human-in-the-loop | ⚠️ 当前仅一句话"多智能体关系" |
| **Agent 记忆系统** | 短期（滚动窗口）+ 长期（向量数据库/知识图谱） | ❌ 未覆盖 |
| **Agent 评测框架** | 工具调用精准率/参数准确率/任务成功率 | ❌ 未覆盖 |
| Agent 状态机 | PENDING→RUNNING→SUCCESS→FAILED→RETRY | ⚠️ 设计开发追溯矩阵有状态机，但 Agent 专用状态机未定义 |
| **Agent 可观测性** | 思维链日志、工具调用链追踪、Token 消耗监控 | ⚠️ `observability-standards` 有通用追踪但不含 Agent 思维链 |
| **Agent 安全** | 工具注入防护、权限边界（工具级/数据级）、敏感信息脱敏 | ❌ 未覆盖 |
| Agent 回退与降级 | LLM 调用失败时的 fallback、human-in-the-loop | ❌ 未覆盖 |
| **Agent 成本优化** | 模型路由（简单请求用小模型）、Token 预算控制 | ❌ 未覆盖 |

**Google 2025 年提出的多 Agent 8 种设计模式**：
1. **顺序链**（Sequential）：Agent A → Agent B → Agent C
2. **广播**（Broadcast）：1 个 Coordinator 同步分发给多个 Worker
3. **编排器**（Orchestrator）：1 个 Orchestrator 动态分配任务给 Worker
4. **聚合器**（Aggregator）：多个 Agent 产出汇聚到 1 个 Aggregator
5. **级联**（Cascade）：Agent 间条件跳转，类似决策树
6. **循环**（Loop）：Agent 可自我迭代改进产出
7. **门禁**（Gate）：Human-in-the-loop 干预点
8. **混合**（Hybrid）：上述模式的组合

当前 `design-stage-execution` 对 Agent 架构的描述仅一句话"Agent 角色、工具、工作流、上下文、记忆、失败处理、多智能体关系"，远不足以覆盖这些。

### 2.4 混合架构（Hybrid Architecture）

**业界最佳实践应包含的设计要素：**

| 设计要素 | 业界推荐实践 | 当前技能覆盖 |
|:---------|:------------|:-----------:|
| **单体+微服务混合** | 核心业务单体+边缘服务微服务化 | ❌ 未覆盖 |
| **微服务+Agent 混合** | 传统微服务对外暴露 API，由 Agent 编排调用 | ❌ 未覆盖 |
| **异构通信** | 单体内部方法调用 + 微服务 gRPC + Agent LLM 调用 | ❌ 未覆盖 |
| **混合部署** | 单体 JAR 包 + 微服务容器化 + Agent 运行环境 | ❌ 未覆盖 |
| **渐进式架构迁移** | Strangler Fig 模式：逐步从单体剥离服务 | ❌ 未覆盖 |
| **统一可观测性** | 单体日志 + 微服务追踪 + Agent 思维链 的统一 | ❌ 未覆盖 |
| **数据一致性分层** | 单体强一致 + 微服务最终一致 + Agent 语义一致 | ❌ 未覆盖 |

## 三、缺口严重性分析

```
                      业界标准覆盖度（越高=越缺失）
                      ↑
         Agent(8/18)   ●  微服务(2/13)
                      ●
                混合(0/7)  ●
                      ●
                 单体(1/4)  ●
                      └──────────────────→ 工程影响
                                           （不覆盖的后果）
```

| 架构类型 | 当前覆盖要素 | 业界标准要素 | 覆盖度 | 不覆盖的后果 |
|:---------|:----------:|:----------:|:-----:|:------------|
| **单体** | 1/4 | 4 | **25%** | 单体设计不规范，后期拆分困难 |
| **微服务** | 2/13 | 13 | **15%** | 微服务架构退化"分布式单体"、治理缺失 |
| **Agent** | 8/18 | 18 | **44%** | 已有基础，但缺评测/安全/成本/记忆模式 |
| **混合** | 0/7 | 7 | **0%** | **完全缺失**，无法处理渐进式迁移和多风格并存 |

### 核心问题

当前的 `系统架构设计文档` 模板是 **通用模板**——它对所有架构类型使用相同的 8 个章节。这导致：

1. **微服务项目**用该模板产出时，不会自然考虑网关/注册发现/熔断/分布式事务/链路追踪/灰度发布等微服务特定要素
2. **Agent 项目**用该模板产出时，不会自然考虑 ReAct 循环/多 Agent 协作模式/工具注入安全/Token 成本等 Agent 特定要素
3. **混合项目**用该模板产出时，完全无法表达单体、微服务和 Agent 三种风格如何并存和交互
4. **架构迁移**没有行业标准模式（如 Strangler Fig）作为设计选项

## 四、推荐改进方案

### 4.1 方案选择

**不要新增独立技能**。架构模式的选择和详细设计是 `系统架构设计文档` 模板的扩展，通过在模板中增加"架构风格"章节来区分。

理由：
- 架构设计的流程规范已在 `design-stage-execution` 中完整定义（17 类设计规范矩阵）
- 缺少的是**模板内容**（不同架构风格的设计要素差异），不是**流程规范**
- 四种架构风格的设计要素差异可以通过"按架构风格选择章节"的方式在同一模板中处理

### 4.2 模板改进建议

在 `project-document-templates` 的"系统架构设计文档"模板中，将当前线性结构改为**按架构风格分支**的结构：

| 设计目标与原则 | 必须 | 设计目标、设计原则、架构总览 |

### 4.3 架构风格决策框架（新增模板）

在 `project-document-templates` 的新模板中，增加一个**架构风格选择决策矩阵**：

| 评估维度 | 单体 | 微服务 | Agent | 混合 |
|:---------|:----:|:------:|:-----:|:----:|
| 用户规模 | ≤10 万 | ≥100 万 | 不限 | 部分大+部分小 |
| 团队规模 | ≤10 人 | ≥30 人 | ≥5 人 | ≥30 人 |
| 迭代频率 | ≥2 周/次 | ≤1 周/次 | 变化快 | 核心慢+边缘快 |
| 变更影响 | 牵一发而动全身 | 局部变更 | 思维链变更 | 核心稳定+边缘灵活 |
| 部署独立性 | 统一部署 | 独立部署 | 独立推理 | 混合部署 |
| 数据一致性 | 强一致 | 最终一致 | 语义一致 | 按域分层 |
| 技术复杂度 | 低 | 高 | 中 | 最高 |
| 学习成本 | 低 | 高 | 中（新领域）| 最高 |

**决策建议**：
- 用户 ≤ 10 万、团队 ≤ 10 人 → **单体起步**
- 用户 ≥ 100 万、团队 ≥ 30 人 → **微服务**
- 需要 LLM 驱动的认知类功能 → **在已有架构中嵌入 Agent**
- 旧系统单体 + 新需求需要微服务/AI → **混合（Strangler Fig 迁移）**

### 4.4 不修改 `design-stage-execution`

`design-stage-execution` 的规范矩阵已有"系统架构设计"行，覆盖"系统边界、模块、服务、上下游、技术选型、部署形态"，描述足够通用以适配所有架构风格。不需要修改。

`design-stage-execution` 的强制规则"不得用 API 文档替代系统架构"对所有架构类型同样适用。
