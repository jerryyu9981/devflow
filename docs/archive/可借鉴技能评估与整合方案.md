# 可借鉴技能评估与整合方案

> 基于对 Superpowers（14 个 Skill）和 Gstack（23 个特性）的逐项分析
> 版本：v1.0 | 2026-06-26

---

## 一、评估方法论

每个候选技能按 4 个维度打分：

| 维度 | 权重 | 说明 |
|:-----|:----:|:------
| **缺口大小** | 高 | 我们现有体系在此处的覆盖程度（分越大=越缺失）|
| **整合成本** | 高 | 融入现有架构需要的改动量 |
| **收益确定性** | 中 | 对工程质量的提升是否可预期 |
| **平台依赖性** | 中 | 是否依赖 TRAE 尚不具备的平台能力 |

## 二、Superpowers 候选技能评估（14 个）

### 2.1 ✅ 强烈建议借鉴（P0）

#### ① TDD Iron Rule：没有失败测试就不能写生产代码

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★★（大）—— 我们的"开发自测"是可选级的检查项，不是铁律 |
| 整合成本 | ★☆☆☆☆（低）—— +1 条强制规则到 coding-stage-execution |
| 收益确定性 | ★★★★★（高）—— Superpowers 社区验证，TDD 是工程化基础能力 |
| 平台依赖性 | ★☆☆☆☆（低）—— 纯规则定义，不依赖平台 |
| **综合** | **P0 / 极高性价比** |

**当前状态**：`coding-stage-execution` 的"开发自测"行只要求"自测命令已执行，失败项已处理或记录"

**建议融入方式**：在 coding-stage-execution 的强制规则中增加：

> **TDD 铁律**：生产代码必须在有对应失败测试的前提下编写。发现先写生产代码再补测试的情况，必须删除生产代码从测试开始重新实现。开发自测不能仅验证"代码能跑"，必须验证"功能正确"。

---

#### ② Systematic Debugging：四阶段系统化调试

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★★（大）—— 我们的 code-logic-review 是静态审查，没有逐层调试方法论 |
| 整合成本 | ★★☆☆☆（低-中）—— 可在 coding-stage 规范矩阵中增加一行调试指引 |
| 收益确定性 | ★★★★☆（高）—— 4 阶段法是业界验证过的方法论 |
| 平台依赖性 | ★☆☆☆☆（低）—— 纯方法论 |
| **综合** | **P0 / 高性价比** |

**Superpowers 的 4 阶段流程**：

```
Phase 1 根因调查：读错误信息→复现→查 diff
Phase 2 模式分析：找到能工作的类似代码做对比
Phase 3 假设验证：科学方法，一次只改一个变量
Phase 4 实施修复：先写失败测试，再修 bug
```

**关键规则**：连续 3 次修复都失败时，停下来质疑架构本身。

---

#### ③ Verification-Before-Completion：完成前强制验证

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★☆（中-大）—— 编码阶段 20 行规范矩阵里没有专门的"验证"行 |
| 整合成本 | ★☆☆☆☆（低）—— +1 条规则到 coding-stage-execution 的强制规则 |
| 收益确定性 | ★★★★★（高）—— 解决 AI 最常见的"我觉得能跑"问题 |
| 平台依赖性 | ★☆☆☆☆（低） |
| **综合** | **P0 / 极高性价比** |

**Superpowers 原文**：
> 没有新鲜的验证证据就不能声称完成。"应该能通过""我很有信心"都不行，必须跑命令、看输出、然后才能说结果。

---

### 2.2 ⚠️ 建议关注但非优先（P1）

#### ④ Brainstorming Hard Gate：设计确认前禁止写代码

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★☆☆（中）—— 我们的设计审计门禁（覆盖率≥95%）已起到类似作用 |
| 整合成本 | ★★★☆☆（中）—— 需要在 design-stage-execution 和 coding-stage-execution 之间增加更硬的衔接门禁 |
| 收益确定性 | ★★★★☆（高） |
| 平台依赖性 | ★☆☆☆☆（低） |
| **综合** | **P1 / 中等性价比** |

**不优先的原因**：我们已有需求架构对比审计（≥95%）和开发设计对比审计（≥90%），在流程上已经阻止了"跳过设计直接编码"。Brainstorming Gate 的本质功能已被覆盖。

---

### 2.3 ❌ 不适合借鉴

| 技能 | 原因 |
|:-----|:------|
| **Subagent-Driven Development** | 这是平台运行时能力（每个任务启动一个新 Agent），不是流程规则。TRAE 当前是单会话模式，不适合实施。留存观察 |
| **Dispatching Parallel Agents** | 同上，平台能力依赖。适合并行执行时有效，目前非必须 |
| **Receiving Code Review** | 教 AI 如何接收审查反馈（表演性回应等问题）—— 只有交互型 AI 才需要，我们的 code-logic-review 是结构化审查，不涉及此问题 |
| **Writing Skills** | 已在培训文档 6.3 节有完整说明，不重复 |
| **Using Git Worktrees** | Git 工作流管理——`code-version-backup-management` 和 `git-commit` 技能已覆盖 |

## 三、Gstack 候选技能评估（23 个特性）

### 3.1 ✅ 强烈建议借鉴（P0）

#### ⑤ Safety Guardrails：安全护栏（目录锁定 + 高危操作确认）

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★☆（中-大）—— 我们的 coding-stage-execution 只有一条"不得破坏环境边界"，没有限制 AI 修改文件范围的机制 |
| 整合成本 | ★★☆☆☆（低-中）—— 在 coding-stage-execution 的强制规则中补充文件范围保护规则 |
| 收益确定性 | ★★★★★（高）—— 大项目中 AI 误改文件是最常见的问题之一 |
| 平台依赖性 | ★★☆☆☆（低-中）—— 规则可定义，但真正锁定目录需要平台能力 |
| **综合** | **P0 / 高性价比** |

**Gstack 的做法**：
- `/careful`：AI 执行破坏性命令前强制告警
- `/freeze`：限制修改范围到指定目录
- `/guard`：同时开启两者

**建议融入方式**：在 coding-stage-execution 强制规则中增加：

> **文件范围保护**：编码实现时默认只允许修改本次任务涉及的文件。发现 AI 试图修改非本次任务范围的文件时，必须请求确认。所有文件修改必须在`设计开发追溯矩阵`的"涉及文件"列中有对应记录。

---

#### ⑥ Cross-Model Review：跨模型交叉审查

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★☆（中-大）—— 我们的 code-logic-review 只有单一模型的审查 |
| 整合成本 | ★★☆☆☆（低-中）—— 在 code-logic-review 中增加"跨模型验证"的推荐步骤 |
| 收益确定性 | ★★★★☆（高）—— 不同模型对同一段代码可能有不同的发现 |
| 平台依赖性 | ★★☆☆☆（中）—— 需要能调用另一个 AI 模型的能力 |
| **综合** | **P0 / 高性价比** |

**建议融入方式**：在 `code-logic-review` 技能中增加一条推荐做法：

> **跨模型交叉审查（推荐）**：关键模块的代码逻辑审查，建议使用与编码时不同的 AI 模型进行独立审查（如编码用 Claude，审查用 GPT/DeepSeek）。不同模型对同一问题的视角差异可能发现单一模型忽略的问题。

---

### 3.2 ⚠️ 建议关注但非优先（P1/P2）

#### ⑦ Persistent Headless Browser E2E（/qa）

| 维度 | 评估 |
|:-----|:------|
| 缺口大小 | ★★★★☆（中）—— 我们测试矩阵有 E2E 测试行，但缺乏自动化浏览器 E2E 的具体工具指引 |
| 整合成本 | ★★★★☆（高）—— 需要集成 Playwright + 持久化浏览器守护进程 |
| 收益确定性 | ★★★★★（高） |
| 平台依赖性 | ★★★★★（高）—— 需要运行时启动和管理无头浏览器 |
| **综合** | **P2 / 平台决策项** |

不优先的原因：这是一个基础设施决策而非流程规则改动。如果 TRAE 平台未来支持持久化无头浏览器，可以在 testing-stage-execution 的测试矩阵 E2E 行中补充工具推荐。

---

### 3.3 ❌ 不适合借鉴

| 特性 | 原因 |
|:-----|:------|
| **23 角色分工**（CEO/设计师/EM 等）| 我们的 role-management 以 Solo 模式为核心，23 角色适用于多人团队场景但 Solo 模式下过于冗余。保留参考价值 |
| **/autoplan** | 自动规划——我们的版本规划矩阵 + 需求规范矩阵共 35 行，比 Gstack 的 /autoplan 更严格完整 |
| **/ship 一键发布** | 发布流程已由 operations-stage-execution 的部署运维矩阵（19 行）完整覆盖 |
| **/retro 回顾** | 已由发布复盘报告和全流程闭环审计报告覆盖 |
| **Multi-Host 支持** | 平台战略决策，非流程规则 |
| **Garry Tan 60天60万行** | 运营数据验证，不涉及具体可借鉴的技能 |

## 四、整合路线

### 4.1 分三批实施

| 批次 | 技能 | 目标文件 | 改动量 |
|:----|:-----|:---------|:------|
| **批次 1（立即）** | TDD 铁律 | `coding-stage-execution` 强制规则 | +1 条 |
| **批次 1（立即）** | Verification-Before-Completion | `coding-stage-execution` 强制规则 | +1 条 |
| **批次 2（本轮）** | Systematic Debugging | `coding-stage-execution` 规范矩阵 | +1 行 |
| **批次 2（本轮）** | Safety Guardrails | `coding-stage-execution` 强制规则 | +1 条 |
| **批次 2（本轮）** | Cross-Model Review | `code-logic-review` 推荐做法 | +1 条 |
| **批次 3（后续）** | 无头浏览器 QA | `testing-stage-execution` 工具推荐 | +1 行 |

**合计**：约 +5 行改动，零架构变更。

### 4.2 不修改的决策

- **不改 L1 技能**（workflow / doc-management / role-management）— 三个方案的全流程管控都不如我们
- **不改 L2 阶段流程** — 6 个阶段的划分方式不变
- **不改编译层模式** — 这是我们的核心技术优势
- **不改文档体系** — 49 份文档 + 18 个模板是独占能力

### 4.3 修改后的效果

```
修改前（只靠内部流程规范）           修改后（借鉴 Superpowers+Gstack）
─────────────────────────           ─────────────────────────────
编码阶段 10 条强制规则             编码阶段 12 条强制规则（+TDD +验证 +护栏）
审查是单一模型                     推荐跨模型交叉验证
开发自测是"可选级"检查项           开发自测升级为 TDD 铁律
调试无方法论指引                    4 阶段系统化调试
```
