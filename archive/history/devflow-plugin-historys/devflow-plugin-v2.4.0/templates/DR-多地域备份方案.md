## 2. 多地域备份架构设计

### 2.1 三级架构概述

本方案采用主/从/冷备三级架构，在不同地域间实现数据备份和灾难恢复能力。

```
┌──────────────────────────────────────────────────────────┐
│                    多地域备份架构                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ┌─────────────┐     同步/半同步     ┌─────────────┐    │
│  │  主地域(Active) │ ───────────────> │  从地域(Standby) │    │
│  │  {地域名称}    │                   │  {地域名称}    │    │
│  │  角色：读写    │                   │  角色：只读    │    │
│  └─────────────┘                   └─────────────┘    │
│         │                                │             │
│         │ 异步                           │ 异步        │
│         ▼                                ▼             │
│  ┌─────────────────────────────────────────────────┐  │
│  │              冷备地域(Cold Standby)                 │  │
│  │              {地域名称}                             │  │
│  │              角色：仅备份存储，无在线服务             │  │
│  └─────────────────────────────────────────────────┘  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 2.2 地域角色定义

| 地域角色 | 定义 | 部署内容 | 数据状态 | 切换方式 | RTO | RPO |
|---------|------|---------|---------|---------|-----|-----|

## 3. 跨地域数据同步策略

### 3.1 同步方式对比

| 同步方式 | 原理 | 优势 | 劣势 | 适用场景 | 数据丢失风险 |
|---------|------|------|------|---------|:----------:|
| 同步复制 | 主节点等待所有从节点确认后才返回成功 | 数据一致性最强，零数据丢失 | 写入延迟高，可用性降低 | 金融交易、支付等强一致性场景 | 零 |
| 半同步复制 | 主节点等待至少一个从节点确认后返回成功 | 兼顾一致性和性能 | 仍有少量数据丢失风险 | 大多数生产环境 | 极低 |
| 异步复制 | 主节点写入后立即返回，后台异步复制到从节点 | 性能最优，对主节点影响最小 | 数据丢失风险较高 | 可接受少量数据丢失的场景 | 中 |

### 3.2 同步策略选择矩阵

| 数据类型 | 一致性要求 | 推荐同步方式 | 主→从延迟 | 主→冷备延迟 | 说明 |
|---------|:---------:|:----------:|:--------:|:----------:|------|
| 交易数据 | 强一致 | 同步复制 | < 10ms | - | 核心交易数据，零丢失 |
| 用户数据 | 最终一致 | 半同步复制 | < 50ms | < 1小时 | 用户个人信息 |
| 业务数据 | 最终一致 | 异步复制 | < 100ms | < 4小时 | 日志、报表等 |
| 配置数据 | 强一致 | 同步复制 | < 10ms | < 30分钟 | 系统配置和元数据 |
| 媒体文件 | 最终一致 | 异步复制 | < 5秒 | < 24小时 | 图片、视频等大文件 |

### 3.3 数据同步组件配置

| 组件 | 同步工具 | 同步方式 | 同步频率 | 冲突处理 | 监控 |
|------|---------|:-------:|---------|---------|------|
| 关系数据库 | {如 MySQL Replication / PG Streaming Replication} | {同步/半同步/异步} | 实时 | {策略} | 复制延迟监控 |
| NoSQL 数据库 | {如 MongoDB Replica Set / DynamoDB Global Table} | {同步/异步} | 实时 | {策略} | 同步延迟监控 |
| 对象存储 | {如 S3 Cross-Region Replication / OSS 跨区域复制} | 异步 | 近实时 | {策略} | 复制状态监控 |
| 消息队列 | {如 Kafka MirrorMaker / MQ 跨地域同步} | 异步 | 实时 | {策略} | 消息堆积监控 |
| 源代码 | Git Mirror（见 code-version-backup-management） | 异步 | 推送时触发 | - | Hook 执行状态 |

## 4. 地域故障切换流程

### 4.1 主备切换（主地域 → 从地域）

当主地域发生故障时，将从地域提升为主地域，接替所有服务。

#### 4.1.1 切换前检查

| 序号 | 检查项 | 检查命令/方法 | 预期结果 | 通过 |
|------|-------|-------------|---------|:----:|
| CHK-001 | 从地域数据库数据同步状态 | `{检查命令}` | 复制延迟 < {阈值} | {Y/N} |
| CHK-002 | 从地域服务健康状态 | `{健康检查URL}` | 所有服务健康 | {Y/N} |
| CHK-003 | DNS 切换准备就绪 | 检查 DNS 配置 | 切换记录已预配置 | {Y/N} |
| CHK-004 | 负载均衡器配置就绪 | 检查 LB 规则 | 流量转发规则已配置 | {Y/N} |
| CHK-005 | 客户端连接字符串可切换 | 检查配置管理 | 连接配置已预置 | {Y/N} |

#### 4.1.2 切换执行步骤

| 步骤编号 | 操作 | 负责人 | 预计耗时 | 回滚方案 |
|---------|------|-------|---------|---------|
| SW-001 | 确认主地域故障，宣布启动切换 | 总指挥 | 立即 | 取消切换，修复主地域 |
| SW-002 | 将从数据库提升为主（停止复制，设为可读写） | 数据负责人 | {5分钟} | 重新建立复制关系 |
| SW-003 | 更新 DNS 指向从地域 | 网络工程师 | {2-5分钟} | 回滚 DNS 记录 |
| SW-004 | 更新负载均衡器后端地址 | 运维工程师 | {2分钟} | 回滚 LB 配置 |
| SW-005 | 通知所有服务更新连接配置 | 技术负责人 | {5分钟} | 回滚服务配置 |
| SW-006 | 验证从地域服务正常响应 | 技术负责人 | {5分钟} | 执行回滚 |
| SW-007 | 发布切换完成公告 | 通信负责人 | 立即 | - |
| SW-008 | 持续监控从地域运行状态 | 运维人员 | 持续24小时 | - |

#### 4.1.3 切换后数据一致性验证

| 序号 | 验证项 | 验证方法 | 预期结果 |
|------|-------|---------|---------|
| VAL-001 | 数据库记录数对比 | 对比主备表记录数 | 偏差 < {阈值} |
| VAL-002 | 关键业务数据抽样验证 | 抽样检查关键订单/用户数据 | 数据完整一致 |
| VAL-003 | 自增序列/ID 连续性 | 检查自增ID是否有冲突 | 无冲突 |
| VAL-004 | 缓存数据一致性 | 检查缓存命中率 | 命中率恢复正常水平 |

### 4.2 多活切换（高级场景）

当项目采用多活架构时，地域间的切换更为复杂。

#### 4.2.1 多活架构前提条件

| 条件 | 说明 | 实现方式 |
|------|------|---------|
| 数据分片 | 数据按地域分片或全局唯一ID | 分片键设计 / 全局ID生成器（如 Snowflake） |
| 冲突解决 | 多地域同时写入时的冲突处理机制 | 向量时钟 / CRDT / 最后写入获胜 |
| 流量调度 | 按地域就近路由，支持动态调整 | DNS 负载均衡 / 全局负载均衡 |
| 灰度切换 | 支持逐步将流量从一个地域迁移到另一个地域 | 权重调整 + 健康检查 |

### 4.3 切换回退流程

当原主地域恢复后，需要将服务切回原主地域。

| 步骤编号 | 操作 | 负责人 | 预计耗时 | 说明 |
|---------|------|-------|---------|------|
| RB-001 | 确认原主地域完全恢复正常 | 技术负责人 | 1小时 | 所有硬件、网络、服务正常 |
| RB-002 | 建立从当前主到原主的数据同步 | 数据负责人 | {30分钟} | 反向同步，追平数据 |
| RB-003 | 验证数据一致性 | 数据负责人 | {30分钟} | 数据校验通过 |
| RB-004 | 选择业务低峰期执行回切 | 总指挥 | - | 避免业务影响 |
| RB-005 | 执行切换流程（同主备切换） | 技术团队 | {15分钟} | 将流量切回原主地域 |
| RB-006 | 验证回切后服务正常 | 技术负责人 | {10分钟} | 所有验证项通过 |

## 5. 数据一致性保障机制

### 5.1 一致性级别定义

| 一致性级别 | 定义 | 实现方式 | 适用场景 | 性能影响 |
|:---------:|------|---------|---------|:-------:|
| 强一致 | 所有节点在同一时刻看到完全相同的数据 | 同步复制 + 分布式锁 | 金融交易、库存扣减 | 高 |
| 因果一致 | 保证有因果关系操作的顺序 | 因果一致性协议 | 社交动态、消息回复 | 中 |
| 最终一致 | 在有限时间内所有节点数据收敛一致 | 异步复制 + 冲突解决 | 日志、报表、缓存 | 低 |

### 5.2 校验机制

| 校验类型 | 频率 | 方法 | 工具 | 触发告警条件 |
|---------|------|------|------|-----------|
| 实时校验 | 每次写入 | 写入确认 + 校验和 | 数据库原生校验 | 校验和不匹配 |
| 增量校验 | 每小时 | 对比最近变更的数据行 | 自定义校验脚本 | 数据不一致 |
| 全量校验 | 每周 | 全表扫描对比 | 数据校验工具 | 数据不一致 |
| 抽样校验 | 每日 | 随机抽样数据对比 | 自动化脚本 | 抽样不一致率 > 0 |

### 5.3 冲突处理策略

| 冲突类型 | 检测方式 | 解决策略 | 实现方式 |
|---------|---------|---------|---------|
| 写-写冲突（同记录） | 版本号/时间戳对比 | 最后写入获胜（LWW） | 记录级时间戳 |
| 写-写冲突（不同字段） | 字段级变更检测 | 字段级合并 | 操作日志回放 |
| 删除-写冲突 | 删除标记 + 写入时间对比 | 写入优先（覆盖删除） | 软删除 + 恢复标记 |
| 主键冲突 | 自增ID碰撞 | 全局唯一ID生成 | Snowflake / UUID |

### 5.4 数据修复流程

```
1. 检测不一致 → 校验脚本发现数据差异
2. 评估影响 → 确定受影响的数据范围和业务影响
3. 制定修复方案 → 选择合适的修复策略（全量覆盖 / 增量修复 / 手动修复）
4. 执行修复 → 在维护窗口执行数据修复操作
5. 验证修复 → 全量校验确认数据一致性
6. 复盘记录 → 记录不一致原因，优化同步策略
```
