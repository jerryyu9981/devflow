# 需求设计追溯矩阵模板

### 模板：需求设计追溯矩阵

- **对应文档名**：`{项目名}-需求设计追溯矩阵-v{版本号}.md`
- **存放路径**：作为 `doc\design\{项目名}-设计评审记录-v{版本号}.md` 的强制子章节，独立输出时使用本命名
- **作用**：在设计阶段建立需求到设计模块的映射，用于需求架构对比审计（覆盖率 >= 95%）
- **填写时机**：架构设计完成后、设计评审前建立，作为设计评审记录的核心章节
- **填写责任角色**：AA（Agent架构师）/ FA（前端架构师）
- **核心追溯链**：需求ID → 设计文档章节 → 设计模块 → 覆盖状态
- **强制规则**：P0/P1 需求必须 100% 有设计覆盖
- **最小章节结构**：

#### 1. 文档元信息（必须）

| 属性 | 值 |
|------|-----|
| 版本 | v{版本号} |
| 对应需求文档 | {项目名}-开发需求文档-v{版本号}.md |
| 对应设计文档 | {项目名}-系统架构设计文档-v{版本号}.md |
| 创建日期 | yyyy-MM-dd |
| 创建人 | AA/FA-{项目名}-{环境} |

#### 2. 映射表（必须）

核心字段定义：

| 字段 | 格式要求 | 示例 | 说明 |
|------|---------|------|------|
| 追溯ID | DT-{序号} | DT-001 | 唯一编号 |
| 需求ID | 需求追溯矩阵中的需求编号 | FR-001 | 精确对应需求追溯矩阵中的需求ID |
| 需求描述 | 简要说明 | 用户注册功能 | 一句话需求要点 |
| 设计文档章节 | 架构设计文档中的章节号 | 3.2 用户模块设计 | 精确到二级或三级标题 |
| 涉及设计模块 | 系统架构中的模块名 | user-auth-service | 对应架构设计中的模块划分 |
| 覆盖类型 | FULL/PARTIAL/NOT-COVERED/NA | FULL | FULL=完全覆盖；PARTIAL=部分覆盖；NOT-COVERED=未覆盖；NA=不适用 |
| 覆盖方式 | 如何满足该需求 | 提供register()API，包含输入校验/密码加密/邮箱唯一性检查 | 简要说明设计中的实现方式 |
| 设计偏差 | 与需求的差异说明 | 需求要求短信验证码，设计暂用邮箱验证 | 标记偏差以在审计中评估 |
| 状态 | COVERED/DEVIATION/UNCOVERED | COVERED | COVERED=已覆盖；DEVIATION=有偏差；UNCOVERED=未覆盖 |

#### 3. 填写示例

```
| 追溯ID | 需求ID | 需求描述 | 设计文档章节 | 涉及设计模块 | 覆盖类型 | 覆盖方式 | 设计偏差 | 状态 |
|--------|--------|---------|------------|------------|---------|---------|---------|------|
| DT-001 | FR-001 | 用户注册功能 | 3.2 用户模块设计 | user-auth-service | FULL | register()API，邮箱密码输入，bcrypt加密 | 无 | COVERED |
| DT-002 | FR-002 | 注册欢迎邮件 | 3.2 用户模块设计 | user-auth-service | PARTIAL | 注册事件触发通知，异步邮件服务延期 | 异步邮件延迟到v2.2 | DEVIATION |
| DT-003 | FR-010 | 实名认证 | 3.4 认证模块设计 | user-verify-service | FULL | 身份证OCR+活体检测接口 | 无 | COVERED |
| DT-004 | FR-011 | 实名信息加密 | 3.4 认证模块设计 | user-verify-service | FULL | AES-256加密存储身份证号 | 无 | COVERED |
| DT-005 | NFR-003 | 登录限流 | 3.6 安全设计 | api-gateway | FULL | 网关层RateLimiter中间件 | 无 | COVERED |
```

#### 4. 覆盖率统计（必须）

| 统计项 | 值 |
|--------|-----|
| 需求总数 | {数量} |
| COVERED | {数量（百分比）} |
| DEVIATION | {数量（百分比）} |
| UNCOVERED | {数量（百分比）} |
| 覆盖率（COVERED / 总数*100%） | {百分比 >= 95%} |

> 覆盖率 = COVERED / (FULL + PARTIAL) * 100%。覆盖率 >= 95% 时方可进入设计评审和需求架构对比审计。

#### 5. 偏差与未覆盖说明（必须）

| 需求ID | 偏差/未覆盖原因 | 影响评估 | 处理方式 |
|--------|---------------|---------|---------|
| FR-002 | 异步邮件服务延期到v2.2 | 用户注册后不会立即收到邮件，不影响注册主流程 | 在测试移交说明中标注为已知限制，在需求评审中确认延期 |

#### 6. 注意事项（必须）

- **审计输入**：本矩阵是 Step 2 尾端需求架构对比审计的基准输入，审计时检查覆盖率 >= 95%
- **审计产出**：审计结果写入 `{项目名}-需求架构对比审计报告-v{版本号}.md`
- **未覆盖处理**：UNCOVERED 的需求项需在审计前补充设计或由 PM 决策标记为延期
- **偏差处理**：DEVIATION 的项需评估对需求满足度的影响，必要时应更新需求文档或补充设计
