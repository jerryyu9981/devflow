## 一、问题现象

### 1.1 一句话概括

> **Step 3 的"完成"是文档层面的完成，不是代码质量层面的完成。**
>
> DevLogReport 写得很完善、代码逻辑审查结论是"通过"、静态检查记录齐全——但代码里积累了大量技术债务。

### 1.2 典型表现

| 层面 | 文档中的样子 | 实际代码中的样子 |
|---|---|---|
| **DevLogReport** | ✅ 结构完整，各章节齐全，技术债有记录 | — |
| **静态质量检查** | ✅ 有执行记录，P0/P1 全通过 | P2/P3 问题大量累积 |
| **代码逻辑审查** | ✅ 结论"通过"或"有条件通过" | 可维护性维度审查宽松 |
| **技术债务记录** | ✅ 每版本都有记录到 DevLogReport | 只记录不偿还，越积越多 |
| **功能交付** | ✅ 功能按需求实现了 | 实现质量差，后续维护成本高 |

### 1.3 为什么说这是"假完成"？

Step 3 的完成标准（coding-stage-execution §完成标准）有 12 条，但核心门槛只有一条：

> **无未解决的 P0/P1 问题。**

这意味着：
- P2 级别的技术债务 → 不阻塞
- P3 级别的可维护性问题 → 不阻塞
- TODO/FIXME 标记 → 不阻塞
- 重复代码、高复杂度 → 不阻塞（只要没到 P1 阈值）
- 架构偏离、设计走样 → 记录下来就行，不阻塞

**结果：每个版本都"完成"了，但每个版本都留下了一堆"以后再还"的债。**

## 二、根因分析

### 2.1 根因一：完成标准的结构性缺陷

**当前完成标准的重心**：

```
P0/P1 问题全部关闭  ←  这是硬门槛，没通过就是没完成
    ↓
P2/P3 问题记录在案  ←  这是软要求，记录了就算完成
    ↓
技术债务写入 DevLogReport  ←  有记录就达标
```

**问题**：技术债务天然是 P2/P3 的，所以天然不阻塞 Step 3 完成。规范只要求"记录"，不要求"偿还"，也不设债务上限。

**类比**：就像考试只要求"不挂科"（P0/P1），但不管考了多少分。每学期都及格，但成绩一年比一年差。

### 2.2 根因二：技术债务只进不出的单向机制

当前规范中的技术债务管理流程：

```
编码中发现技术债 → 记录到 DevLogReport → Step 3 完成 → 进入 Step 4
                                                            ↑
                                             没有任何步骤要求还债！
```

coding-stage-execution §技术债务跟踪 写了 5 条规则，但其中：
- ✅ 记录新增债务（有）
- ✅ 分类（有）
- ⚠️ 偿还规则（只有一句话："评估是否在本版本内偿还"，没有强制执行）
- ✅ 自测时检查（有，但只是检查有没有记录）
- ✅ 三技能配合（有，但都是 P2/P3 级）

**核心缺失**：没有"债务上限"、没有"还债比例要求"、没有"累积到一定程度就阻塞新版本"的机制。

### 2.3 根因三：代码审查的可维护性维度太软

code-logic-review 的 11 个审查维度中，"可维护性"排在最后一位（第 11 维）。

审查优先级（code-logic-review §审查原则）：
> "先找阻塞测试/上线的问题，再找可维护性改进。"

这意味着：
1. 先查需求覆盖、设计一致、业务流程、API 契约、数据一致、权限安全——这些都是 P0/P1
2. 最后才看可维护性——这是 P2/P3
3. 如果前面的都过了，可维护性有点问题也只是"记录风险"，不阻塞通过

**结果**：可维护性审查成了"走过场"——有这个环节，但实际不影响结论。

### 2.4 根因四：LLM 的天然倾向——先求能用，再求（不）求好

LLM 写代码的典型模式：

1. 优先实现功能（满足需求）
2. 能跑通就行
3. 代码质量、可维护性、优雅程度——如果不明确要求，就不会主动做
4. 技术债务？先记下来，"以后再优化"

加上审查的 LLM 也是同样的倾向：
- "功能实现了吗？实现了。"
- "有 P0/P1 问题吗？没有。"
- "那通过吧。"

**两个人的标准都一样低 → 互相放水 → 债务累积。**

### 2.5 根因五：历史债务无人认领

每个版本的技术债都是"本版本新增的"，但：
- 上一版本留下的债 → 没人记得
- 上上版本留下的债 → 更没人管
- 累积了 5 个版本的债 → 已经变成"代码就是这样的"

DevLogReport 只记录了本版本新增的债，但没有一个全局的技术债务总表，也没有定期回顾和清理机制。

## 三、治理方案

### 3.1 方案设计原则

1. **不搞运动式治理** — 不能说"这个版本专门还债"，这样业务就停了
2. **嵌入现有流程** — 在 Step 3 现有框架内增加约束，不另起炉灶
3. **量化、可验证** — 不能说"提高质量"，要说"债务增长率 ≤ X%"
4. **分级管控** — P0/P1 继续硬阻塞，P2/P3 设软约束，超过阈值才升级

### 3.2 方案一：技术债务增长率红线（P0，立即可用）

**核心规则**：每个版本的**新增技术债务不得超过本版本变更代码量的 X%**，超过则 Step 3 不通过。

**具体设计**：

| 指标 | 定义 | 红线 |
|---|---|---|
| **新增 TODO/FIXME 数量** | 本版本新增的 TODO、FIXME、HACK、XXX 标记 | 新增 ≤ 5 个（或按代码量比例） |
| **代码复杂度增量** | 新增/修改函数的圈复杂度、认知复杂度 | 高复杂度函数新增 ≤ 3 个 |
| **重复代码增量** | 新增的重复代码块 | 新增重复率 ≤ 3% |
| **架构偏离度** | 新增代码中违反既有架构/分层约定的部分 | 零容忍（P1） |

**执行位置**：coding-stage-execution §3.4 静态质量检查 + §3.7 技术债务审计

**通过条件**：
- 所有红线指标均在阈值内 → 通过
- 超过红线但有合理理由（紧急修复、临时方案有明确偿还计划）→ 有条件通过，需在 DevLogReport 中明确偿还计划和时间
- 超过红线且无合理理由 → 不通过，必须优化后重新审查

### 3.3 方案二："还债配额"机制（P1，每个版本强制还债）

**核心规则**：每个版本必须偿还一定比例的历史技术债务，否则 Step 3 不通过。

**具体设计**：

| 规则 | 说明 |
|---|---|
| **还债比例** | 每个版本至少偿还 **本版本预估工作量的 15~20%** 的历史债务 |
| **还债来源** | 从候选需求池的技术债类需求中挑选，或从 DevLogReport 历史债务中认领 |
| **验证方式** | DevLogReport 中必须有"本版本偿还债务清单"章节，列出偿还了哪些债、怎么验证的 |
| **豁免条件** | P0 级紧急修复版本可以豁免，但必须在下一个正常版本补还 |

**类比**：就像信用卡还款——每个月必须还最低还款额，不能一直只借不还。

### 3.4 方案三：代码审查"可维护性"权重升级（P1）

**当前问题**：可维护性是第 11 维，排在最后，实际执行时容易放水。

**改进方案**：

1. **调整审查顺序**：把"可维护性"从最后一位移到第 6 位（中间位置），明确它不是"有空再看"的
2. **增加"可维护性否决项"**：以下情况即使功能正确也不能通过：
   - 单个函数超过 200 行且无合理理由
   - 复制粘贴超过 3 处的相似代码
   - 关键模块无注释、无文档
   - 魔数/硬编码字符串超过 5 个且未提取为常量
3. **审查结论中必须有可维护性专项评价**：不能只说"通过"，必须说明可维护性水平（好/中/差）和主要问题

### 3.5 方案四：全局技术债务台账 + 季度回顾（P2，长期治理）

**核心机制**：

1. **建立全局技术债务台账**：
   - 不只是每个版本的 DevLogReport 里零散记录
   - 专门有一份 `doc/tech-debt/技术债务总表.md`
   - 每条债务有：编号、来源版本、严重级别、预估偿还工作量、状态（待处理/进行中/已偿还/已接受）

2. **季度回顾机制**：
   - 每季度做一次技术债务审计
   - 统计债务总量变化趋势
   - 识别"最值得还的债"（收益/成本比最高的）
   - 纳入下个季度的版本规划

3. **债务老化升级**：
   - P3 债务超过 3 个版本未处理 → 升级为 P2
   - P2 债务超过 3 个版本未处理 → 升级为 P1
   - 升级为 P1 后就会阻塞 Step 3

### 3.6 方案五：证据真实性强化（P2，防假证据）

针对"LLM 写假的测试/审查报告"的风险：

| 措施 | 说明 |
|---|---|
| **实际输出片段要求** | 静态检查和自测结果不能只写"通过"，必须包含实际命令和输出片段（至少 10 行关键输出） |
| **可复现要求** | 所有命令必须是可复现的——审查者可以照着同样的命令跑出同样的结果 |
| **交叉验证** | 静态检查结果 ↔ 自测结果 ↔ DevLogReport 记录，三者必须互相印证 |
| **随机抽查机制** | Step 4 测试阶段随机抽取 1~2 个自测用例实际运行，验证是否真的通过 |

## 四、推荐组合与实施路径

### 4.1 推荐组合

| 优先级 | 方案 | 作用 | 实施成本 |
|---|---|---|---|
| **P0** | 方案一：债务增长率红线 | 防止新增债务失控 | 低 |
| **P1** | 方案二：还债配额 | 强制逐步还债 | 中 |
| **P1** | 方案三：可维护性权重升级 | 提高审查门槛 | 低 |
| **P2** | 方案四：全局台账 + 季度回顾 | 长期治理 | 中 |
| **P2** | 方案五：证据真实性强化 | 防假证据 | 中 |

### 4.2 实施路径

**第一阶段（立即执行）**：方案一 + 方案三
- 在 coding-stage-execution 中增加技术债务增长率红线
- 在 code-logic-review 中升级可维护性维度的权重和否决项
- 成本：约 0.5 人天
- 效果：立即遏制新增债务的速度

**第二阶段（下一个版本开始）**：方案二
- 每个版本强制分配 15~20% 工作量还债
- DevLogReport 增加"本版本偿还债务清单"章节
- 成本：约 0.3 人天（规范修改）+ 每个版本实际还债工作量
- 效果：债务总量开始下降

**第三阶段（下季度起）**：方案四 + 方案五
- 建立全局技术债务台账
- 季度回顾机制
- 证据真实性强化
- 成本：约 1 人天（初始建立）+ 每季度 0.5 人天（回顾）
- 效果：长期可持续的债务治理体系

## 五、对当前项目的建议

既然已经发现了大量历史技术债务，建议按以下步骤处理：

### 第一步：摸清底数（1~2 天）

1. 做一次全面的技术债务扫描（静态检查工具 + 人工审查）
2. 建立技术债务总表，按 P0/P1/P2/P3 分级
3. 统计总量和分布（哪些模块欠债最多、什么类型的债最多）

### 第二步：分类处置

| 债务级别 | 处置方式 |
|---|---|
| **P0/P1 债务** | 立即修复，不能拖 |
| **P2 高收益债务** | 在下个版本中优先偿还（收益/成本比高的） |
| **P2 低收益债务** | 排入还债配额，逐步消化 |
| **P3 债务** | 记录在案，接受现状，等有合适机会再处理 |

### 第三步：建立机制

把方案一、二、三落地到 DevFlow 规范中，确保以后的版本不会再"假完成"。

## 六、总结

### 6.1 问题本质

Step 3 "假完成"的本质不是规范缺失——技术债务跟踪、可维护性审查、DevLogReport 这些规范都有。问题在于：

> **规范只要求"记录"，不要求"解决"；只卡 P0/P1，不管 P2/P3。**

结果就是：文档越来越完善，代码质量越来越差。

### 6.2 核心对策

1. **给新增债务设红线** — 超过就不让过
2. **强制每个版本还一点债** — 不能只借不还
3. **把可维护性审查从"软"变"硬"** — 不能功能对了就过
4. **建立全局台账和长期治理机制** — 不能一笔糊涂账

### 6.3 一句话总结

> **Step 3 的"完成"不应该是"功能做出来了"，而应该是"功能做出来了，而且代码质量没有变差（最好还有所提升）。"**
