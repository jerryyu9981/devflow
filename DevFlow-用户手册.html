DevFlow 概述

1.1 什么是 DevFlow

DevFlow 是一套可插拔的软件开发工程规范框架（Skills-as-Code 架构），专为 AI 辅助编程场景设计。它将软件工程的核心环节整合为标准化的 6 阶段流程（Step 0~5），通过需求追溯链（RT-ID→DT-ID→TD-ID→TT-ID）和审计门禁确保每一行代码都可追溯到具体需求、每个阶段有明确的质量检查。

设计哲学

DevFlow 不替代任何开发工具或框架。它是在 AI 对话层之上叠加的一层工程治理层——把 AI 从"随性聊天"变成"标准化工程流水线"。每个阶段结束时都有审计门禁，不合格就返工，质量在流程中逐步累积，而不是最后集中修补。

1.2 核心概念

6 阶段流程
Step 0~5：规划→需求→设计→编码→测试→部署
追溯链体系

审计门禁
每阶段结束必须审计，P0/P1 必须闭环

文件结构一致性

1.5 四条约束链

DevFlow 的核心不是工具，而是四条约束链——它们共同构成了让 AI 自主遵循工程规范的治理机制。AI 会忘记做过什么、会跳过步骤、会声称完成了但实际没有，这四条链让每一段代码都有据可查、有门可守、有债可追。

🔗 门禁链
每个阶段的进出都有门禁要求，不可或缺。门禁不过不进不出。
🔍 追溯链
RT-ID→DT-ID→TD-ID→TT-ID 四层递进。每行代码都能追溯到需求，每个测试都关联设计。
📋 债务链
在各个阶段对技术债务的全生命周期进行维护，确保开发过程不遗漏。
✅ 审计链
audit-agent 独立审计师重新执行验证命令，对比"声称"与"实际"输出。发现造假→全量作废重审。
工程治理 vs 工具

DevFlow 不替代 IDE、不替代编译器、不替代 CI/CD。它是在 AI 对话层之上叠加的一层工程治理层——让 AI 自主遵循规范，而不是靠人盯着每一步。

安装指南

2.1 前置条件

条件要求说明
操作系统Windows 10+ / macOS / Linux脚本提供 .ps1/.bat（Windows）和 .sh（macOS/Linux）
ShellPowerShell 5.1+ 或 Bash 4+不支持 CMD
AI 平台TRAE Work / IDE / Claude Code / Cursor技能安装到对应平台的技能目录
Git可选但推荐用于备份和版本管理
PowerShell 执行策略

Windows 默认可能禁止运行脚本：Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

2.2 获取插件

方法一：Git 克隆
git clone https://github.com/jerryyu9981/devflow.git && cd devflow-plugin

方法二：手动获取 — 从同事或压缩包获取插件文件夹。

2.3 Windows 安装

  1. 打开 PowerShell — Win+R → powershell
  2. 进入插件目录 — cd D:\路径\devflow-plugin
  3. 运行安装脚本 — .\install.ps1 或双击 install.bat
  4. 输入项目路径 — 输入你的项目根目录（不是插件目录）
  5. 配置项目信息 — 项目名称、Git 仓库地址（可选）、备份仓库地址（可选）
  6. 完成 — 重启 TRAE，输入 / 即可看到 DevFlow 技能

2.4 macOS/Linux 安装

  1. chmod +x install.sh
  2. ./install.sh
  3. 后续交互与 Windows 相同

2.5 验证安装

验证清单
  • 配置文件 — 项目根目录下有 .devflow/config.json
  • 状态文件 — .devflow/state.json
  • 技能列表 — 重启 TRAE 后在 / 技能列表中能看到 devflow 技能
  • 注册验证 — .\validate-registry.ps1 → 28 skills, 0 errors
  • 功能验证 — 输入"初始化 DevFlow"，能正常返回初始化报告

2.6 更新版本

  1. 获取新版文件 — Git pull 或重新解压
  2. 备份配置 — 备份 .devflow/config.json 和 .devflow/state.json
  3. 运行更新 — .\update.ps1 -Action Sync
  4. 验证 — 检查 devflow-config.json 的 devflowVersion

脚本自动检测新旧版本差异、备份旧版、执行增量更新。支持 -Target IDE|Work|All 参数控制安装目标。

2.7 卸载

① 删除项目中 .devflow/ 目录 ② 从全局技能目录删除 DevFlow 技能文件

3

项目初始化

3.1 首次初始化

在 TRAE 中输入"初始化 DevFlow"或调用 devflow-init 技能。它会自动：

  1. 扫描项目目录，检查已有文档和代码结构
  2. 推断当前所处阶段（新项目从 Step 0 开始，已有项目从中间切入）
  3. 创建 .devflow/config.json 和 .devflow/state.json
  4. 输出初始化报告，包含项目信息和下一步建议
中途引入

不必从头开始。devflow-init 会自动检测现有文档推断当前阶段，从已有阶段切入。

3.2 配置文件

.devflow/config.json：项目全局配置。字段：project（项目名）、projectVersion（当前版本）、branchStrategy（分支策略）、remote.origin（主仓库）、remote.backup（备份仓库）。

3.3 状态文件

.devflow/state.json：记录运行状态。字段：project、version、currentPhase、completedPhases、auditResults。建议由 PM 统一管理，加入 Git 版本控制。

3.4 版本号单一来源

DevFlow 的版本号以 version.json 为唯一权威来源。发布时自动同步到 devflow-config.json 的 devflowVersion 和 .devflow/config.json 的 projectVersion。三处必须一致，不一致视为发布失败。

6 阶段开发流程

Step 0 规划→↓ Step 1 需求→↓ Step 2 设计→↓ Step 3 编码→↓ Step 4 测试→↓ Step 5 上线

4.0 Step 0 — 版本规划

技能：version-planning-stage-execution | 触发：输入"开始版本规划"

子步骤：0.0a 跨版本债务审查 → 0.0 收集候选需求 → 0.1 技术可行性粗筛 → 0.2 版本目标与范围决策 → 0.3 创建 Backlog → 0.4 Phase 拆分 + 风险评估 → 0.5 版本规划评审

产出：单版本规划文档 / Backlog / Phase 计划 / 评审记录

通过标准

候选需求池已更新 + 目标可衡量 + Backlog 形成 + 优先级已确认 + Phase 已拆分 + 依赖/风险已记录 + 评审通过 + 产出物存在性验证通过

4.1 Step 1 — 需求分析

技能：requirements-stage-execution | 触发：输入"开始需求分析"

子步骤：1.0 入场检查 → 1.1 来源归档 → 1.2 角色分析 → 1.3 目标/场景/故事 → 1.4 流程/功能 → 1.5 非功能/数据/权限/UI/接口 → 1.6 约束/验收/优先级 → 1.7 追溯矩阵/基线 → 1.8 评审 → 1.9 评估审计 → 1.10 设计移交

关键产出：开发需求文档 / 用户需求说明书 / UIUX 需求 / 需求追溯矩阵（RT-ID）/ 需求基线及设计移交

强制规则

① 不得扩大 Step 0 范围 ② 所有需求必须有来源 ③ P0/P1 必须有验收标准 ④ 必须建立需求追溯矩阵 ⑤ 需求评审未通过不得进入 Step 2

4.2 Step 2 — 架构设计

技能：design-stage-execution | 触发：输入"开始设计"

轨道：🎯 整体（始终）+ ⚙️ 后端（始终）+ 🎨 前端（按需）+ 🔗 第三方（按需）

子步骤：2.0 入场+轨道选择 → 2.1 需求-设计追溯（DT-ID）→ 2.2 系统架构 → 2.3 技术选型+ADR → 2.4~2.6 详细设计 → 2.7 专项设计 → 2.8 覆盖检查 → 2.9 API 契约对齐 → 2.10 评审 → 2.11 审计 → 2.12 移交

覆盖率门禁

P0/P1 需求必须有明确设计覆盖，总覆盖率 ≥ 95%。剩余 ≤ 5% 必须标记为"已知设计缺口"。

4.3 Step 3 — 编码开发

技能：coding-stage-execution | 触发：输入"开始编码"

子步骤：3.0 入场 → 3.1 任务拆解 → 3.2 TD-ID 追溯矩阵（含 Subtask CheckList）→ 3.3a TDD 编码 → 3.4a 静态质量检查 → 3.5a 实际运行验证 → 3.6a 自测 → 3.7a 代码逻辑审查 → 3.8 修复 → 3.9 DevLogReport → 3.10 审计移交

三层质量门禁（强制顺序）
  1. 静态质量检查（3.4）— 12 类检查（语法/Lint/类型/构建/符号/参数/返回值/导入导出/API/环境变量/数据字段/状态枚举）+ 技术债务增长率检查
  2. 实际运行验证（3.5）— L1 构建 → L2 启动 → L3 冒烟，必须有实际输出片段
  3. 代码逻辑审查（3.7）— 14 维审查（含命名与结构一致性），P0/P1 必须闭环
TDD 铁律

测试先于生产代码：RED（写失败测试）→ GREEN（写可通过的代码）→ REFACTOR（重构）。所有 feat/fix 提交必须包含对应测试。

4.4 Step 4 — 测试验证

技能：testing-stage-execution | 触发：输入"开始测试"

子步骤：4.0 入场+自测证据抽查 → 4.1 计划+用例（TT-ID）→ 4.2 环境验证 → 4.3a API/4.3b 组件/4.3c 第三方 → 4.4a 后端集成/4.4b 前端集成 → 4.5 E2E → 4.6 回归+覆盖率 → 4.7 专项测试 → 4.8 UAT → 4.9 缺陷闭环 → 4.10 报告 → 4.11 审计移交

强制测试矩阵

除非明确标记"不适用"，不得跳过：API/集成/E2E/Mock/回归/覆盖率/合规/安全/性能/可访问性/UAT。跳过项必须在报告中说明原因。

4.5 Step 5 — 部署运维

技能：operations-stage-execution | 触发：输入"开始部署"

子步骤：5.0 入场 → 5.1 发布计划+版本确认 → 5.2 环境/DB → 5.3 缓存/消息 → 5.4 部署执行 → 5.5 上线验证 → 5.6 监控/日志/告警 → 5.7 性能/安全 → 5.8 回滚预案 → 5.9 运维移交 → 5.10 发布复盘 → 5.11 全流程闭环审计

发布强制规则

① 不得无回滚上线 ② 不得无监控上线 ③ 部署成功≠业务可用 ④ 不得泄露密钥 ⑤ P0/P1 上线问题必须停止发布或回滚 ⑥ 回滚后 15 分钟内完成验证 ⑦ 版本号自动更新为原子步骤，不可跳过

追溯链体系

追溯链确保每行代码都能追溯到需求，是 DevFlow 的核心机制。

5.1 四层追溯 ID

ID产生阶段格式含义
RT-IDStep 1RT-{版本号}-{序号}Requirement Traceability，唯一标识需求
DT-IDStep 2DT-{版本号}-{序号}Design Traceability，标识设计项，引用 RT-ID
TD-IDStep 3TD-{版本号}-{序号}Development Traceability，标识编码任务，引用 DT-ID
TT-IDStep 4TT-{版本号}-{序号}Test Traceability，标识测试用例，关联 RT-ID+TD-ID

5.2 追溯链流转

RT-001: 用户可以通过邮箱注册
↓
DT-012: 注册 API 接口DT-013: 用户表 email 字段
↓
TD-008: 注册接口实现TD-009: 数据库迁移脚本
↓
TT-005: 注册功能测试

5.3 强制规则

追溯 ID 使用规范
  • 所有 P0/P1 需求的测试用例必须至少关联一个 TD-ID
  • 追溯矩阵的"Backlog ID"列强制填写 V260-XXX 格式
  • P0/P1 需求必须 100% 可追溯
  • Git commit footer 必须引用 RT-ID

配置与维护

7.1 Git 分支策略

策略配置值适用场景
Git Flow"git-flow"有计划发布周期的中大型项目，默认推荐
GitHub Flow"github-flow"持续部署的小型项目或 SaaS
Trunk-Based"trunk-based"高频发布、强 CI/CD 的成熟团队

7.2 技术债务管理

  • 全局债务总表 — DevFlow-技术债务总表.md，15 字段标准格式，跨版本追踪
  • 老化升级 — P3>2版本→P2, P2>2→P1, P1>2→P0
  • 还债配额 — 每版本 ≥ 15%，连续 2 版 <15% 触发专项评审
  • 优先级 — 安全(P0) > 架构(P1) > 测试(P2) > 代码整洁(P3)
  • 风险归集门禁 — 6 个 L2 技能含风险归集检查章节，P1+ 自动流入债务总表
  • 债务增长率门禁 — 新增 TODO ≤5 / 高复杂度函数 ≤3 / 重复率 ≤2%

7.3 备份策略

类型频率保留
Git MirrorTag 创建时永久
Bundle 快照每周最近 4 个
数据库 Dump每天90 天

文档规范

8.1 命名规则

格式：{项目名}-{文档类型}-v{版本号}.md

类型前缀路径
版本规划V-doc/version/releases/v{版本号}/
需求分析R-doc/requirements/
架构设计D-doc/design/
开发编码C-doc/development/
测试验证T-doc/testing/
部署运维O-doc/release/
审计—doc/audit/

8.2 产出物存在性验证

每个阶段结束前必须通过 LS/Glob 列出目标目录验证所有产出文件实际存在。空输出（声称完成但文件不存在）不得通过。验证结果记录在阶段评审/审计文档中。

8.3 风险归集检查章节

所有阶段文档的"输出要求"之后必须包含标准化的风险归集检查模板。未填写此章节的版本不得标记为"已发布"。包含 4 项检查：P1+ 风险归集状态、未归集风险 ID 及原因、归集日期、技术债务总表版本。

常见问题

Q1：安装后技能列表为空？

检查技能目录 %USERPROFILE%\.trae-cn\skills\ 是否有 .md 文件。重启 TRAE。如果还没有，执行 .\update.ps1 -Action Sync 强制同步。

Q2：项目做了一半才引入 DevFlow？

运行 devflow-init，自动扫描并推断当前阶段，从中间切入即可，不需要从头开始。

Q3：需求变更后追溯链如何更新？

修改需求文档 → 更新 RT-ID 描述 → 标注变更影响范围 → 重新评估受影响的 DT-ID/TD-ID → 必要时回退对应阶段 → 更新所有引用

Q4：能跳过某些阶段只使用部分功能吗？

可以。DevFlow 完全可插拔。例如只用编码阶段的质量检查，调用对应技能即可，不需要走完整流程。

Q5：团队协作时 state.json 会有冲突吗？

建议由 PM 或 Tech Lead 统一管理 state.json，其他成员只读。阶段切换通过 devflow-phase-manager 统一执行。

Q6：安装时提示 PowerShell 执行策略受限？

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

Q7：v2.10.0 相比旧版本有什么变化？

6 笔技术债务全部偿还，新增文件结构一致性保障、风险归集门禁落地、模板从 9 补到 24 个、季度审计机制、首次性能基线数据。向后完全兼容 v2.9.x。

Q8：devflow-config.json 的 skills 数组和 layers 有什么关系？

devflow-config.json 是唯一权威配置源。skills 数组定义了 28 个技能的完整注册信息（名称、来源、层级、安装目标），layers 按层级分组供编排引用。两者必须一致，不一致由 validate-registry.ps1 检测。

Q9：如何查看当前版本的变更统计？

每个版本发布时生成 Release Note（DevFlow-Release-Note-v{版本号}.md），包含变更统计和兼容性说明。Changelog 汇总在 doc/release/README.md。

Q10：CI/CD 流水线如何集成？

Step 5 可参考 cicd-pipeline-management 技能定义的标准流水线（检出→构建→质量门禁→部署→验证）。质量门禁包括单元测试覆盖率、安全扫描和性能基准对比。
