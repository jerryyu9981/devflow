## 定位

本技能是项目文档内容模板的参考标准。它基于 DCO、DPS、DHAP 三个项目已生成的实际文档结构，提炼共性结构，补充缺失章节，形成高频文档的最小内容结构模板。

本技能不替代 `project-document-management` 的命名和存储规范，只定义文档内部应该包含哪些章节。

## 触发条件

- 各阶段输出文档时参考对应模板
- 文档评审时对照模板检查完整性
- 新项目初始化时参考模板建立文档骨架

## 模板使用原则

1. **最小必须**：模板中标记"必须"的章节不可省略，标记"可选"的按需添加
2. **兼容扩展**：项目可以在模板基础上增加更多章节，不受限制
3. **风格兼容**：支持中文编号（一/二/三）和阿拉伯数字（1/2/3）两种章节编号风格
4. **元信息统一**：所有文档开头必须包含基本信息表格（项目名、版本号、状态、日期、负责人/作者）
5. **修订历史**：重要文档（规划文档、架构文档、需求文档）建议包含修订历史表

## 高频文档模板

### 模板：单版本规划文档

- **对应文档名**：`{项目名}-单版本规划文档-v{版本号}.md`
- **存放路径**：`doc\version\releases\v{版本号}\`
- **参考来源**：DPS v2.6.0 单版本规划文档、DCO v2.1.0 版本规划文档、DHAP v3.0.0 单版本规划文档
- **最小章节结构**：

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 文档元信息 | 必须 | 项目名、版本号、版本主题、状态、创建日期、最后更新、文档负责人 |
| 修订历史 | 可选 | 版本、日期、修改人、修改内容 |
| 版本概述/版本定位 | 必须 | 版本背景、版本目标（业务目标、技术目标、成功指标） |
| 版本范围 | 必须 | 包含范围、不包含范围、延期/排除项 |
| 优先级排序 | 必须 | 优先级矩阵或排序表 |
| Phase拆分 | 必须 | 各Phase的目标、需求和交付物 |
| 关键依赖/资源与依赖 | 必须 | 内部依赖、外部依赖 |
| 风险与约束 | 必须 | 风险清单、约束条件 |
| 高层验收目标 | 必须 | 核心验收标准 |
| 发布策略草案 | 可选 | 发布时间窗口、发布方式 |

### 模板：开发需求文档

- **对应文档名**：`{项目名}-开发需求文档-v{版本号}.md`
- **存放路径**：`doc\requirements\`
- **参考来源**：DPS v2.6.0 开发需求文档、DCO v2.1.1 开发需求文档、DHAP v1.0.0 开发需求文档
- **最小章节结构**：

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 文档元信息 | 必须 | 文档编号、版本、状态、日期、作者 |
| 文档概述/需求概述 | 必须 | 版本背景、需求范围概述 |
| 功能需求 | 必须 | 按模块/功能点组织，每个功能点包含需求ID、描述、优先级、验收标准 |
| 非功能需求 | 必须 | 性能、安全、可用性、可维护性等 |
| 接口需求 | 有接口时必须 | 接口列表、接口规范 |
| 数据需求 | 有数据模型时必须 | 数据模型、数据迁移需求 |
| 安全需求 | 有安全要求时必须 | 安全策略、合规要求 |
| 约束与假设/风险与约束 | 必须 | 技术约束、业务假设、风险项 |
| 术语表 | 可选 | 专业术语解释 |

### 模板：系统架构设计文档

- **对应文档名**：`{项目名}-系统架构设计文档-v{版本号}.md`
- **存放路径**：`doc\design\`
- **参考来源**：DPS v2.6.0 系统架构设计文档、DCO v2.1.1 系统架构设计文档、DHAP v1.0.0 系统架构设计文档
- **作用**：描述系统的重大设计决策和总体结构。模板按架构风格分支组织——先确定架构风格（单体/微服务/Agent/混合），再按对应分支补充设计章节
- **填写原则**：
  - 先阅读"架构风格决策"章节选择风格，再填写对应附加章节
  - 不需要的附加章节（如单体项目不写微服务章节）可以省略
  - 架构风格变更时（如从单体迁移到微服务），必须更新此文档并记录变更理由
- **最小章节结构**：

#### 通用章节（所有架构类型必须）

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 文档元信息 | 必须 | 文档编号、版本、状态、日期、作者、架构风格标注 |
| 设计目标与原则 | 必须 | 业务目标、设计原则、约束条件、架构决策记录（ADR）|
| **架构风格决策** | 必须 | 选择单体/微服务/Agent/混合并说明理由；见文末决策矩阵 |
| 模块总览 | 必须 | 模块划分图、每个模块的职责和边界、模块间依赖关系 |
| 技术选型 | 必须 | 语言/框架/数据库/中间件/运行时选型及每项选型的依据说明 |
| API 设计 | 有 API 时必须 | 外部 API（RESTful）+ 内部 API（gRPC/事件）定义、请求/响应格式 |
| 安全架构 | 可选 | 认证授权、数据加密、安全策略、密钥管理 |
| 可观测性 | 必须 | 日志格式/指标类型/链路追踪/Dashboard 规划；参考 observability-standards |

#### 单体架构附加章节

适用于：项目规模小、团队人员少、迭代频率低的场景。

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 分层策略 | 必须 | 表现层/业务层/数据层/基础设施层的职责划分和单向依赖方向 |
| 模块分包 | 必须 | 包结构设计（按业务域或按层）、模块间引用规则、禁止循环依赖 |
| 构建与部署 | 必须 | 多模块构建策略（Maven/Gradle）、启动优化、单体打包部署 |

#### 微服务架构附加章节

适用于：用户规模大、团队独立、需要独立部署和独立扩展的场景。

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 服务拆分 | 必须 | DDD 限界上下文分析、服务粒度决策、拆分边界和依赖关系图；禁止循环依赖（依赖 <= 3 层）|
| 服务通信 | 必须 | 内部服务通信协议（gRPC + Protobuf）、外部暴露（RESTful）、事件驱动（消息队列）；序列化和契约管理 |
| 服务治理 | 必须 | 注册发现（K8s Service/Nacos）、配置中心（Nacos/K8s ConfigMap）、API 网关（路由/限流/认证）、熔断降级（阈值/降级策略/舱壁隔离）、负载均衡策略 |
| 数据一致性 | 必须 | 分布式事务策略选择（Saga/TCC/事务消息）、每个服务的数据存储方案、最终一致性保证措施 |
| 部署与发布 | 必须 | 容器化方案（Docker + K8s Deployment/Service/Ingress）、灰度发布/蓝绿部署（Istio VirtualService）、HPA 弹性伸缩策略 |
| 故障模式 | 必须 | 级联失败分析（Cascading Failure）、故障隔离策略（Bulkhead）、重试退避策略（Exponential Backoff）|

#### Agent 架构附加章节

适用于：需要 LLM 驱动的认知推理、工具调用、工作流自动化的场景。

| 章节 | 必要性 | 说明 |
|------|--------|------|
| Agent 认知模式 | 必须 | 选型：ReAct（推理-行动循环）/ Plan-and-Execute（先计划再执行）/ Reflection（自我反思）/ Multi-step 等；说明选择的理由 |
| Agent 协作模式 | 涉及多 Agent 时必须 | Google 8 种模式：Sequential（顺序链）/ Broadcast（广播）/ Orchestrator（编排器）/ Aggregator（聚合器）/ Cascade（级联）/ Loop（循环）/ Gate（人工门禁）/ Hybrid（混合）|
| LLM 配置 | 必须 | 模型选择（GPT-5/Claude/Llama/DeepSeek 等及选型理由）、温度参数、Top-P、Token 预算上限 |
| 工具系统 | 必须 | 工具定义方式（@tool / MCP）、工具参数绑定模式、工具安全（注入防护/权限边界/敏感信息过滤）、工具列表和说明 |
| 记忆系统 | 可选 | 短期记忆（滚动上下文窗口）、长期记忆（向量数据库/知识图谱）、检索增强策略 |
| Agent 评测框架 | 必须 | 评测指标（工具调用精准率/参数准确率/任务成功率）、评测数据集、边界测试用例 |
| 成本控制 | 必须 | 模型路由策略（简单任务用小模型、复杂任务用大模型）、Token 预算监控、LLM 调用缓存策略 |

#### 混合架构附加章节

适用于：旧系统改造 / 单体逐步迁移 / 微服务和 Agent 并存的场景。

| 章节 | 必要性 | 说明 |
|------|--------|------|
| 混合策略 | 必须 | 单体/微服务/Agent 三种风格的共存方式、各自的职责边界和交互关系 |
| 渐进迁移 | 涉及单体拆分为微服务时必须 | Strangler Fig（绞杀者）模式、迁移优先级排序、过渡期双写策略、回退方案 |
| 异构通信 | 必须 | 单体内部方法调用 + 微服务 gRPC + Agent LLM 调用三种通信模式的统一治理和转换规则 |
| 统一可观测性 | 必须 | 单体日志 + 微服务链路追踪 + Agent 思维链的统一采集和分析方案 |

#### 架构风格决策矩阵

##### 选择框架

| 评估维度 | 单体 | 微服务 | Agent | 混合 |
|---------|:----:|:------:|:-----:|:----:|
| 用户规模 | <= 10 万 | >= 100 万 | 不限 | 部分大+部分小 |
| 团队规模 | <= 10 人 | >= 30 人 | >= 5 人 | >= 30 人 |
| 迭代频率 | >= 2 周/次 | <= 1 周/次 | 变化快 | 核心慢+边缘快 |
| 变更影响 | 局部改动影响整个应用 | 局部变更，影响隔离 | 思维链变更影响推理质量 | 核心稳定+边缘灵活 |
| 部署单元 | 统一部署包 | 独立服务各自部署 | 独立推理实例 | 混合部署策略 |
| 数据一致性 | 强一致性（本地事务）| 最终一致性（分布式）| 语义一致性（LLM 输出）| 按域分层保障 |
| 技术复杂度 | 低 | 高 | 中（新领域）| 最高 |
| 学习成本 | 低 | 高 | 中 | 最高 |

##### 决策建议

1. **初创期或小型项目**：用户数 <= 10 万、团队 <= 10 人、迭代周期 >= 2 周 → 选择**单体**。可先用单体快速交付，后续按需拆分。
2. **中大型互联网项目**：用户数 >= 100 万、团队 >= 30 人、需要独立部署和独立扩展 → 选择**微服务**。配合 Kubernetes + Istio 实现服务治理。
3. **需要 LLM 驱动的认知能力**：需要在现有系统中嵌入 AI Agent 功能 → 在已有架构（单体或微服务）基础上**嵌入 Agent**。Agent 作为独立模块/服务运行，通过 API 与传统架构交互。
4. **旧系统改造或渐进迁移**：已有单体需要逐步拆分、或需要在单一系统中同时使用多种架构 → 选择**混合**。核心业务保持单体，边缘服务微服务化或 Agent 化，采用 Strangler Fig 模式逐步迁移。

#### 设计注意事项（所有架构类型通用）

- **技术选型必须说明理由**：不仅仅是"选了什么"，还要说明"为什么选这个而不是那个"（如考量闭源风险/社区活跃度/团队掌握度/性能基准）
- **API 变更时必须同步更新架构文档**：API 是系统的契约，变更后必须在本文档中记录
- **架构决策记录（ADR）**：关键设计决策应在文档中记录决策、备选方案和选择理由
- **可观测性不可省略**：无论何种架构类型，都必须说明日志/指标/追踪方案
### 模板：需求追溯矩阵

- **对应文档名**：`{项目名}-需求追溯矩阵-v{版本号}.md`
- **存放路径**：`doc\requirements\`
- **作用**：在需求阶段建立从版本目标到验收标准的完整追溯链，确保每个需求都可追踪其来源和目标
- **填写时机**：需求分析过程中逐步建立，需求评审前必须完整
- **填写责任角色**：RA（需求分析师）
- **核心追溯链**：版本目标 → 本版本Backlog项 → 需求项 → 验收标准
- **强制规则**：P0/P1 需求必须 100% 可追溯
- **最小章节结构**：

#### 1. 文档元信息（必须）

| 属性 | 值 |
|------|-----|
| 版本 | v{版本号} |
| 对应版本 | {项目名}-单版本规划文档-v{版本号}.md |
| 创建日期 | yyyy-MM-dd |
| 创建人 | RA-{项目名}-{环境} |

#### 2. 追溯映射表（必须）

核心字段定义：

| 字段 | 格式要求 | 示例 | 说明 |
|------|---------|------|------|
| 追溯ID | RT-{序号} | RT-001 | 唯一编号，按追溯链顺序编号 |
| 版本目标 | 版本规划文档中的目标描述 | 支持用户自助注册 | 对应单版本规划文档中的版本目标 |
| Backlog项 | 本版本Backlog中的条目编号 | B-003 用户注册 | 对应本版本Backlog中的条目 |
| 需求ID | 需求文档中的功能编号 | FR-001 | 在需求分析过程中按功能点顺序分配的ID，与开发需求文档中的编号保持一致 |
| 需求描述 | 简要说明需求内容 | 用户可使用邮箱+密码注册账号 | 一句话清晰描述 |
| 验收标准 | 可验证的通过条件 | 注册成功后跳转主页；重复邮箱返回409；密码长度8-64位校验 | 从用户故事的Acceptance Criteria或功能需求细化中提取，需求评审时确认 |

| 来源 | 需求来源类型 | 用户反馈 | user/business/ops-data/prod-issue/competitive/compliance/security/tech-debt/tech-evolution/internal-improvement |
| 需求池项 | 候选需求池中的条目编号 | CP-003 用户注册 | 对应候选需求池中的条目编号和标题；不为 N/A 时，来源自动继承候选需求池中该条目的原始来源；来源为候选池外的新增需求时标注 N/A |
| 技术债务ID | 技术债务清单中的债务编号 | TD-2026-005 | 对应技术债务清单中的债务ID；不为 N/A 时，来源自动为 tech-debt；不来自技术债时标注 N/A |

#### 4. 追溯链完整性检查表（必须）

| 检查项 | 通过标准 | 检查结果 |
|--------|---------|---------|
| 所有版本目标都有对应的Backlog项 | 版本规划文档中的每个目标至少对应1个Backlog项 | 通过/不通过 |
| 所有P0/P1 Backlog项都有对应的需求ID | P0/P1覆盖率达到100% | 通过/不通过 |
| 所有需求都有对应的验收标准 | 每项需求至少有1条验收标准 | 通过/不通过 |
| 需求评审后无未追溯的需求变更 | 评审后新增的需求已补充追溯 | 通过/不通过 |

#### 5. 注意事项（必须）

- **未追溯项说明**：版本目标、Backlog项或需求中未能建立追溯链的项在此说明原因
- **追溯断裂处理**：发现追溯断裂（如需求无对应的版本目标），记录在此并在需求评审中提出
- **审计输入**：本矩阵是 Step 1 评估报告的需求完整性审计输入，审计时检查 P0/P1 需求是否 100% 可追溯

### 模板：需求设计追溯矩阵

- **对应文档名**：`{项目名}-需求设计追溯矩阵-v{版本号}.md`
- **存放路径**：作为 `doc\design\{项目名}-设计评审记录-v{版本号}.md` 的强制子章节，独立输出时使用本命名
- **作用**：在设计阶段建立需求到设计模块的映射，用于需求架构对比审计（覆盖率 >= 95%）
- **填写时机**：架构设计完成后、设计评审前建立，作为设计评审记录的核心章节
- **填写责任角色**：AA（Agent架构师）/ FA（前端架构师）
- **核心追溯链**：需求ID → 设计文档章节 → 设计模块 → 覆盖状态
- **强制规则**：P0/P1 需求必须 100% 有设计覆盖
- **最小章节结构**：

#### 1. 文档元信息（必须）

| 属性 | 值 |
|------|-----|
| 版本 | v{版本号} |
| 对应需求文档 | {项目名}-开发需求文档-v{版本号}.md |
| 对应设计文档 | {项目名}-系统架构设计文档-v{版本号}.md |
| 创建日期 | yyyy-MM-dd |
| 创建人 | AA/FA-{项目名}-{环境} |

#### 2. 映射表（必须）

核心字段定义：

| 字段 | 格式要求 | 示例 | 说明 |
|------|---------|------|------|
| 追溯ID | DT-{序号} | DT-001 | 唯一编号 |
| 需求ID | 需求追溯矩阵中的需求编号 | FR-001 | 精确对应需求追溯矩阵中的需求ID |
| 需求描述 | 简要说明 | 用户注册功能 | 一句话需求要点 |
| 设计文档章节 | 架构设计文档中的章节号 | 3.2 用户模块设计 | 精确到二级或三级标题 |
| 涉及设计模块 | 系统架构中的模块名 | user-auth-service | 对应架构设计中的模块划分 |
| 覆盖类型 | FULL/PARTIAL/NOT-COVERED/NA | FULL | FULL=完全覆盖；PARTIAL=部分覆盖；NOT-COVERED=未覆盖；NA=不适用 |
| 覆盖方式 | 如何满足该需求 | 提供register()API，包含输入校验/密码加密/邮箱唯一性检查 | 简要说明设计中的实现方式 |
| 设计偏差 | 与需求的差异说明 | 需求要求短信验证码，设计暂用邮箱验证 | 标记偏差以在审计中评估 |
| 状态 | COVERED/DEVIATION/UNCOVERED | COVERED | COVERED=已覆盖；DEVIATION=有偏差；UNCOVERED=未覆盖 |

#### 3. 填写示例

```
| 追溯ID | 需求ID | 需求描述 | 设计文档章节 | 涉及设计模块 | 覆盖类型 | 覆盖方式 | 设计偏差 | 状态 |
|--------|--------|---------|------------|------------|---------|---------|---------|------|
| DT-001 | FR-001 | 用户注册功能 | 3.2 用户模块设计 | user-auth-service | FULL | register()API，邮箱密码输入，bcrypt加密 | 无 | COVERED |
| DT-002 | FR-002 | 注册欢迎邮件 | 3.2 用户模块设计 | user-auth-service | PARTIAL | 注册事件触发通知，异步邮件服务延期 | 异步邮件延迟到v2.2 | DEVIATION |
| DT-003 | FR-010 | 实名认证 | 3.4 认证模块设计 | user-verify-service | FULL | 身份证OCR+活体检测接口 | 无 | COVERED |
| DT-004 | FR-011 | 实名信息加密 | 3.4 认证模块设计 | user-verify-service | FULL | AES-256加密存储身份证号 | 无 | COVERED |
| DT-005 | NFR-003 | 登录限流 | 3.6 安全设计 | api-gateway | FULL | 网关层RateLimiter中间件 | 无 | COVERED |
```

#### 4. 覆盖率统计（必须）

| 统计项 | 值 |
|--------|-----|
| 需求总数 | {数量} |
| COVERED | {数量（百分比）} |
| DEVIATION | {数量（百分比）} |
| UNCOVERED | {数量（百分比）} |
| 覆盖率（COVERED / 总数*100%） | {百分比 >= 95%} |

> 覆盖率 = COVERED / (FULL + PARTIAL) * 100%。覆盖率 >= 95% 时方可进入设计评审和需求架构对比审计。

#### 5. 偏差与未覆盖说明（必须）

| 需求ID | 偏差/未覆盖原因 | 影响评估 | 处理方式 |
|--------|---------------|---------|---------|
| FR-002 | 异步邮件服务延期到v2.2 | 用户注册后不会立即收到邮件，不影响注册主流程 | 在测试移交说明中标注为已知限制，在需求评审中确认延期 |

#### 6. 注意事项（必须）

- **审计输入**：本矩阵是 Step 2 尾端需求架构对比审计的基准输入，审计时检查覆盖率 >= 95%
- **审计产出**：审计结果写入 `{项目名}-需求架构对比审计报告-v{版本号}.md`
- **未覆盖处理**：UNCOVERED 的需求项需在审计前补充设计或由 PM 决策标记为延期
- **偏差处理**：DEVIATION 的项需评估对需求满足度的影响，必要时应更新需求文档或补充设计

### 模板：设计开发追溯矩阵

- **对应文档名**：`{项目名}-设计开发追溯矩阵-v{版本号}.md`
- **存放路径**：`doc\development\`
- **作用**：编码前由开发者根据设计文档创建，作为编码实现的逐项指引；Step 3 尾端开发设计对比审计以此为基准检查偏差
- **填写时机**：编码开始前创建设计项到文件的映射，编码过程中逐项标记状态，编码完成后汇总供审计使用
- **最小章节结构**：

#### 1. 文档元信息（必须）

| 属性 | 值 |
|------|-----|
| 版本 | v{版本号} |
| 对应设计文档 | {项目名}-系统/Agent/前端架构设计文档-v{版本号}.md |
| 创建日期 | yyyy-MM-dd |
| 创建人 | 角色-项目名-环境 |

#### 2. 追溯映射表（必须）

核心字段定义：

| 字段 | 格式要求 | 示例 | 说明 |
|------|---------|------|------|
| 追溯ID | TD-{序号} | TD-001 | 唯一编号，按设计项顺序编号 |
| 设计项 | 设计文档中的章节/决策名称 | 用户注册接口设计 | 精确对应设计文档中的标题或决策点 |
| 涉及模块 | 模块名 | user-auth | 系统架构中的模块名 |
| 涉及文件 | 文件路径（相对项目根目录） | server/src/auth/register.ts | 一个设计项可映射多个文件；多个文件用分号分隔 |
| 变更类型 | ADD/MOD/DEL/REF/NFC | ADD | ADD=新增文件；MOD=修改现有文件；DEL=删除文件；REF=重构（不改变行为）；NFC=非功能变更（配置/依赖/性能）|
| 实现策略 | 简要说明实现方法 | Passport.js本地策略，密码bcrypt加密，JWT返回 | 让审计者知道你是怎么实现的 |
| 审计条件 | 验收时检查什么 | 注册成功返回token；密码加密存储；重复用户名返回409 | 每项1-3个关键检查点 |
| 状态 | PENDING/IN_PROGRESS/DONE/VERIFIED/BLOCKED | PENDING | 见下文状态机定义 |

#### 3. 状态机定义

```
PENDING（待开始）
  | 开始编码
IN_PROGRESS（编码中）
  | 本地自测通过
DONE（编码完成）
  | code-logic-review 确认
VERIFIED（审查通过）
  ^ 发现需要返工
  |
  |                    |
BLOCKED（阻塞） ---> 问题解决 ---> PENDING 或 IN_PROGRESS
  | 确认不需要修复
CANCELLED（取消）
```

#### 4. 映射粒度规则

1. **一个设计项可对应多个文件**：例如"用户注册接口"可能映射 register.ts + validator.ts + types/user.ts，在涉及文件列中用分号分隔
2. **一个文件可在多个设计项中出现**：例如 types.ts 被多个设计项修改是正常的，说明该文件是核心依赖
3. **无代码映射的设计项**：如"数据库设计"可直接映射到 migration 文件或标注 N/A（代码级不适用）
4. **编码中发现但设计未覆盖的映射**：补充到注意事项章节，标注为"编码发现-新增映射"，在审计时作为偏差说明

#### 5. 填写示例

```
| 追溯ID | 设计项 | 涉及模块 | 涉及文件 | 变更类型 | 实现策略 | 审计条件 | 状态 |
|--------|--------|---------|---------|---------|---------|---------|------|
| TD-001 | 用户注册API | user-auth | server/auth/register.ts | ADD | 接受username/password，bcrypt加密，返回JWT | 注册成功返回token；重复用户名返回409 | DONE |
| TD-002 | 注册输入校验 | user-auth | server/auth/validator.ts; server/types/auth.ts | ADD | zod schema校验username+password | 非法输入返回422 | DONE |
| TD-003 | 登录API | user-auth | server/auth/login.ts | MOD | 密码比对后返回JWT | 登录成功返回token；密码错误返回401 | IN_PROGRESS |
| TD-004 | 密码加密存储 | user-auth | server/auth/user.model.ts | MOD | prisma新增password_hash字段 | 数据库不存明文密码 | VERIFIED |
| TD-005 | JWT配置 | auth-config | server/config/jwt.ts; server/middleware/auth.ts | ADD | HS256算法，过期时间配置化 | JWT签名一致；过期返回401 | PENDING |
```

#### 6. 编码状态跟踪（必须）

| 追溯ID | 设计项 | 状态 | 负责人 | 开始日期 | 完成日期 | Pull Request | 备注 |
|--------|--------|------|--------|---------|---------|-------------|------|
| TD-001 | 用户注册API | DONE | AD-CoPlayer-Dev | 2026-06-20 | 2026-06-21 | PR #42 | - |
| TD-002 | 注册输入校验 | DONE | AD-CoPlayer-Dev | 2026-06-20 | 2026-06-21 | PR #42 | - |
| TD-003 | 登录API | IN_PROGRESS | AD-CoPlayer-Dev | 2026-06-21 | - | - | 依赖TD-005 |
| TD-004 | 密码加密存储 | VERIFIED | AD-CoPlayer-Dev | 2026-06-20 | 2026-06-21 | PR #42 | 审查通过 |
| TD-005 | JWT配置 | PENDING | AD-CoPlayer-Dev | - | - | - | 阻塞中 |

#### 7. 注意事项（必须）

- **设计偏差记录**：编码过程中发现设计文档未覆盖的边界情况，在此记录
- **新增映射**：编码中发现但设计文档未预见的映射项
- **阻塞原因**：状态为 BLOCKED 的项在此说明阻塞原因和解决方案
- **尾端审计输入**：本矩阵是 Step 3 尾端开发设计对比审计的基准输入，审计时逐项检查矩阵中 DONE/VERIFIED 的项是否已按实现策略完成---
