# Requirements Stage Execution（Step 1 需求阶段执行规范）

## 定位

本技能用于软件开发流程中的 Step 1：需求分析阶段。它发生在 Step 0 版本规划通过之后、Step 2 架构与设计之前，负责把已批准的版本范围、本版本 Backlog、Phase 计划和高层验收目标细化为可设计、可开发、可测试、可审计的需求基线。

它是 Step 1 的主控技能。它不替代版本规划，也不替代设计；它负责组织需求入场检查、需求收集、用户与角色分析、业务流程、用户故事、功能需求、非功能需求、数据需求、权限与安全需求、UI/UX 需求、接口与集成需求、验收标准、需求追溯、需求评审和设计移交。

## 触发条件

当用户提出以下需求时，调用本技能：

- Step 0 版本规划通过后开始需求分析
- 编写 PRD、需求文档、用户故事、验收标准或需求追溯矩阵
- 将本版本 Backlog 细化成正式需求
- 梳理用户角色、业务流程、功能需求、非功能需求、数据需求、权限需求、接口需求
- 组织需求评审、需求基线确认或进入设计阶段前的需求移交
- 判断需求阶段是否完整、是否可以进入设计
- 处理需求范围变更、需求冲突或需求优先级调整

## 阶段位置

```text
Step 0 版本规划
→ Step 1 需求分析
→ Step 2 架构与设计
→ Step 3 开发 / 编码
→ Step 4 测试
→ Step 5 部署与运维
```

本技能负责：

```text
Step 1 需求分析
├── 需求入场检查
├── 需求来源归档
├── 干系人与用户角色分析
├── 业务目标和用户目标
├── 用户场景和用户故事
├── 业务流程和业务规则
├── 功能需求
├── 非功能需求
├── 数据需求
├── 权限与安全需求
├── UI/UX 与原型需求
├── 接口与集成需求
├── 约束、边界和排除项
├── 验收标准
├── 优先级确认
├── 需求追溯矩阵
├── 需求评审
└── 设计移交
```

## 入场门禁

进入 Step 1 前必须满足：

1. Step 0 版本规划已批准。
2. 当前版本目标、范围、不包含范围、本版本 Backlog、Phase 计划和高层验收目标已明确。
3. P0/P1 候选需求已具备来源、价值和初步优先级。
4. 关键干系人、审批人和需求负责人已明确。
5. 不存在未确认的重大版本范围争议。

如不满足，应回退 Step 0，不得直接进入正式需求分析。

## 需求规范矩阵

正式需求阶段必须按以下矩阵执行。若某项不适用，必须在需求评审记录中说明原因。

| 需求类别 | 必须执行内容 | 通过标准 | 强制产出 / 证据 |
|---|---|---|---|
| 需求入场检查 | 确认单版本规划、本版本 Backlog、Phase 计划、版本规划评审结论 | Step 0 输入齐备，可进入需求细化 | 需求入场检查记录 |
| 需求来源 | 记录用户反馈、业务输入、运营数据、线上问题、竞品分析、法规合规、技术债、安全审计、技术演进、内部改进 | 需求来源可追溯 | 需求来源清单 |
| 干系人与用户角色 | 明确业务方、用户、运营、开发、测试、运维、合规和审批人 | 角色、职责、审批关系清晰 | 干系人与用户角色表 |
| 业务目标 | 细化业务目标、用户目标、成功指标和版本目标映射 | 目标可衡量，可追溯到 Step 0 | 业务目标说明 |
| 用户场景 | 主场景、异常场景、边界场景、用户旅程 | P0/P1 场景完整 | 用户场景说明 |
| 用户故事 | 用户故事、价值说明、前置条件、后置结果 | 用户故事可被设计和测试使用 | 用户故事清单 |
| 业务流程 | 主流程、分支流程、失败流程、状态流转、业务规则 | 流程闭环，异常路径明确 | 业务流程说明 |
| 功能需求 | 功能项、输入、处理、输出、状态、权限、错误处理 | 功能需求可设计、可开发、可测试 | 功能需求清单 |
| 非功能需求 | 性能指标(SLA/SLO: P50/P99/吞吐量/并发数)、安全、兼容性、可用性、可维护性、可观测性 | 非功能指标可验证 | 非功能需求说明 |
| 数据需求 | 业务实体、字段、数据来源、生命周期、数据权限、留存规则 | 数据需求支持后续模型设计 | 数据需求说明 |
| 权限与安全需求 | 用户角色、权限边界、敏感操作、审计要求、合规要求 | 权限和安全边界明确 | 权限与安全需求说明 |
| UI/UX 需求 | 页面、交互、状态、表单、错误提示、无障碍要求 | 关键界面和交互需求清晰 | UI/UX 需求说明、原型草案 |
| 接口与集成需求 | 外部系统、上下游、输入输出、同步/异步、失败处理 | 集成边界和契约需求明确 | 接口与集成需求说明 |
| 约束和排除项 | 不做什么、版本边界、技术/时间/合规约束 | 无隐式扩项 | 范围边界说明 |
| 验收标准 | 每个 P0/P1 需求的验收条件、验证方式、UAT 标准 | 验收条件可测试 | 验收标准清单 |
| 优先级确认 | P0/P1/P2、Must/Should/Could、范围变更识别 | 优先级和版本范围一致 | 需求优先级表 |
| 需求追溯 | 版本目标 → Backlog → 需求 → 验收标准 | P0/P1 需求 100% 可追溯 | 需求追溯矩阵 |
| 需求评审 | 完整性、一致性、可设计性、可测试性、范围合规性评审 | P0/P1 问题闭环 | 需求评审记录 |
| 需求基线 | 标记进入设计阶段的需求版本、范围、变更规则 | 需求基线清晰，不可随意变更 | 需求基线说明 |
| 设计移交 | 向 Step 2 提供需求基线、追溯矩阵、验收标准和风险 | 可进入设计阶段 | 设计移交材料 |

## 强制规则

建议在非功能需求中明确性能目标：P50<目标ms / P99<目标ms / 预期并发数 / 预期日活 / 吞吐量目标

1. **不得扩大 Step 0 范围**1. **不得扩大 Step 0 范围**：新增需求必须回写候选需求池或触发单版本范围变更记录。
2. **需求追溯矩阵的"Backlog ID"列强制填写 V260-XXX 格式编号**，确保从需求可追溯回需求池项。
3. **不得跳过需求来源记录**：所有需求必须有来源、负责人和版本归属。
4. **不得用用户故事替代完整需求**：用户故事只是表达形式，不能替代业务规则、数据、权限、验收标准。
5. **不得用原型替代需求文档**：原型只说明交互，不完整覆盖业务规则、非功能、数据和接口需求。
6. **P0/P1 需求必须有验收标准**：无验收标准不得进入设计。
7. **必须建立需求追溯矩阵**：版本目标、Backlog、需求和验收标准必须可追溯。
8. **需求评审未通过不得进入 Step 2**。
9. **需求基线变更必须记录**：进入 Step 2 后变更需求，必须记录范围、影响、审批和下游同步结果。
10. **产出物真实性验证门禁**：所有声称已创建的产出文档，在阶段结束前必须通过文件系统验证实际存在。验证方法：使用 LS/Glob 列出目标目录中的文件，逐一核对产出清单。验证不通过不得进入下一阶段。验证结果须记录在阶段评审/审计文档中。

## 专项技能反向声明规则

所有被需求规范矩阵调用的专项技能，都必须承认 `requirements-stage-execution` 是 Step 1 的需求阶段主控技能。

专项技能在需求阶段被调用时必须遵守：

- 只负责自身专项领域，不直接宣布整个需求阶段完成。
- 需求来源、假设、约束、开放问题、决策和下游影响必须写入相关需求文档。
- 专项分析通过不能替代 Step 1 需求评审或需求审计。
- 发现 P0/P1 需求缺口时，必须在 Step 1 内修复并重新评审。

## 完成标准


Step 1 可完成的最低条件：

1. 所有 P0/P1 需求均有来源、场景、业务规则和验收标准。
2. 需求追溯矩阵覆盖版本目标、本版本 Backlog、需求和验收标准。
3. 范围边界、排除项和版本变更已记录。
4. 功能、非功能、数据、权限、安全、UI/UX、接口与集成需求已完成或明确不适用。
5. 需求评审已通过。
6. 需求基线已确认。
7. 设计移交材料已准备好。
8. 已明确允许进入 Step 2。
9. **产出物存在性验证**：阶段完成前必须通过 LS/Glob 列出目标目录，确认所有产出文件实际存在，空输出（声称完成但文件不存在）不得通过。

### 风险归集门禁

当前阶段执行完成后，发现 P1+ 风险/问题时必须：
1. 打开 `doc/version/global/{项目名}-技术债务总表.md`
2. 检查是否已有对应债务条目
3. 若无 → 按 15 字段标准格式新增条目
4. 在阶段移交说明中注明已归集的风险条目（TD-XXX）
5. 未完成归集的阶段不得移交下一阶段
6. **将修改后的 `{项目名}-技术债务总表.md` 列入本阶段输出文档清单，确保人工可审查增量变更**

## 内部工作流

Step 1 需求分析按以下 10 个子步骤顺序执行。

### 步骤序列

```text
1.0 入场检查 → 1.1 来源归档 → 1.2 角色分析 → 1.3 业务目标/用户场景/用户故事
→ 1.4 业务流程/功能需求 → 1.5 非功能/数据/权限/UI/接口
→ 1.6 约束排除项/验收标准/优先级 → 1.7 追溯矩阵/需求基线
→ 1.8 需求评审 → 1.9 需求评估审计 → 1.10 设计移交
```

### 1.0 入场检查
| 维度 | 内容 |
|------|------|
| **输入** | Step 0 输出：单版本规划、本版本 Backlog、Phase 计划、评审结论 |
| **活动** | 确认 Step 0 输入齐备；缺失关键输入 → 回退 Step 0 |
| **产出** | 入场检查记录 |
| **门禁** | 基础层（独立模式）：需求输入来源明确。扩展层（全流程模式）：Step 0 评审通过 + Backlog 齐备 |

### 1.1~1.2 基础分析
| 步骤 | 活动 | 产出 |
|------|------|------|
| 1.1 来源归档 | 需求来源归档 | 需求来源清单 |
| 1.2 角色分析 | 干系人与用户角色表 | 角色表 |

### 1.3~1.5 需求细化
| 步骤 | 活动 | 产出 |
|------|------|------|
| 1.3 目标/场景/故事 | 业务目标 → 用户场景 → 用户故事 | 各类需求说明文档 |
| 1.4 流程/功能 | 业务流程 → 功能需求 | 业务流程文档 + 功能需求 |
| 1.5 非功能/数据/权限/UI/接口 | 非功能需求 + 数据需求 + 权限需求 + UI/UX 需求 + 接口需求 | 各类需求说明文档 |

**强制规则**：不得扩大 Step 0 已批准的范围。

### 1.6 边界与验收
| 活动 | 产出 |
|------|------|
| 约束排除项定义 + 验收标准逐项确认 + 优先级确认 | 验收标准清单 + 范围边界说明 |

**强制规则**：P0/P1 必须有验收标准。

### 1.7 追溯矩阵 + 需求基线
| 活动 | 产出 |
|------|------|
| 建立需求追溯矩阵（RT-ID）；确认需求基线版本 | 需求追溯矩阵 + 需求基线说明 |

**强制规则**：P0/P1 需求 100% 可追溯。追溯矩阵必须包含"Backlog ID"列。

### 1.8 需求评审
| 活动 | 产出 | 门禁 |
|------|------|------|
| 完整性、一致性、可设计性、可测试性、范围合规性评审 | 需求评审记录 | P0/P1 问题闭环；不通过不可进入 1.9 |

### 1.9 需求评估审计
| 活动 | 产出 | 门禁 |
|------|------|------|
| 审计师执行：需求追溯矩阵 + 验收标准 + 基线检查 | 需求评估报告（放 doc/audit/assessment） | 审计不通过 → 回到 1.3~1.7 |

### 1.9b 变更一致性自检
| 活动 | 产出 |
|------|------|
| **① 检查所有需求文档文件头版本号与修订历史底部版本号一致 ② 确认所有新文件的路径与命名规范匹配 ③ 确认追溯矩阵 RT-ID 数等于需求总数。自检失败 → 修正后才能进入 1.10** | 自检记录（写入评价结论） |

### 1.10 设计移交
| 活动 | 产出 |
|------|------|
| 向 Step 2 提供需求基线、追溯矩阵、验收标准、风险清单；**调用 audit-agent --stage 1 --phase 1+2 验证 RT-ID 需求追溯矩阵完整性和 Step 1 产出物存在性，输出阶段审计报告到 doc/audit/review/** | 设计移交说明 |

**完成后**：通知 devflow-phase-manager 更新 state.json → 进入 Step 2。
