# 项目文档管理规范

为遵循五步开发流程的项目，提供一套强制性的标准化文档管理框架，确保项目全生命周期信息的可追溯性与一致性。

## 触发条件

当对话涉及以下场景时，自动调用此技能并提供精确指引：

- 项目文档的创建、查找、命名、存储
- 文档版本管理与修订历史更新
- 文档权限规则查询
- 项目阶段转换时的文档产出要求
- 审计报告或评估报告的存放路径或命名规范

## 1. 核心原则

- **强制性产出**：每个开发阶段必须产出规定的核心文档，不得遗漏。
- **统一结构**：在开发、测试、生产三个环境中，采用一致的顶层目录框架；各环境按阶段职责保留当前产出目录、只读基线副本目录和归档目录。
- **严格版本控制**：所有文档的任何修改都必须遵循版本管理规范，并同步更新修订历史。
- **清晰权责**：文档的创建、更新、读取权限与项目角色明确绑定。
- **单一事实源**：同一环境、同一版本的当前有效文档仅有一个主存放位置；跨环境基线副本、只读归档副本和兼容性导出副本必须标记来源、版本和只读状态，不得作为主事实源。
- **审计门禁**：每个阶段包含审计子步骤，审计通过后方可进入下一阶段。

## 2. 文档命名规范

所有文档使用 Markdown 格式，命名前缀统一为 `{项目名}-`。主命名格式与别名等效。单版本文档命名均包含版本号后缀 `-v{版本号}`，其中 `{版本号}` = `{主版本}.{次版本}.{修订号}`（如 v1.0.0）。全部版本长期文档为例外，不带单版本号，通过文档修订历史维护版本。

### 2.1 核心项目文档

本节是 Step 0-5 阶段产物的全量命名索引，包含部分审计/评估文档的主文件名。审计/评估文档的分类、路径和归档位置以 2.2 节为准；若两处描述冲突，以 2.2 节的审计路径规则为准。

> **设计文档说明**：设计类文档（系统架构设计、Agent架构设计、前端架构设计）支持[总体设计]和[版本设计]两种形态。
> - **总体设计**（不带版本号，如 `{项目名}-系统架构设计文档.md`）：长期维护，定义架构原则、技术选型、总体分层和核心约定。
> - **版本设计**（带 `-v{版本号}`，如 `{项目名}-系统架构设计文档-v2.1.1.md`）：继承总体架构约定，记录本版本的设计增量和变更。
> - 版本设计不得推翻总体设计的架构约定；总体设计更新不得影响已发布的版本设计。

## 3. 存储路径映射

规范中使用 `环境目录` 作为路径占位符。正式规范使用 `{项目根目录}` 表达项目实际根路径，以下路径为默认逻辑映射；`D:\Trae CN\myproject\...` 仅作为示例，不是强制物理路径。

| 环境 | 环境目录 |
|------|---------|
| 开发环境 | `{项目根目录}\Dev` |
| 测试环境 | `{项目根目录}\Test` |
| 生产环境 | `{项目根目录}\Pro` |

所有环境的项目文档，均统一存储在 `环境目录\项目名\doc` 目录下，并进一步按文档类型分子目录。三环境保持一致的顶层目录框架，但不要求每个环境列出完全相同的当前有效文件；开发环境保留开发中主文档，测试环境保留测试执行材料和只读基线副本，生产环境保留发布运维材料和最终归档副本。

### 4.4 阶段证据归属规则

各阶段生成的成果物与证据文件，按以下规则归属到对应环境的目录结构中。

### 4.5 文档内容模板参考

文档的内部章节结构、最小内容要求、推荐章节模板由 `project-document-templates` 技能定义。本技能只定义文档的命名、存储路径、版本控制和权限管理，不定义文档内部应该包含哪些章节。生成文档内容时调用 `project-document-templates` 技能中的对应模板。

阶段矩阵中的证据项分为两类：独立文档和主文档强制章节。

| 类型 | 规则 | 示例 |
|------|------|------|
| 独立文档 | 需要单独审批、跨角色移交、审计归档或长期复用的材料，必须按命名规范输出独立 Markdown 文件 | 测试报告、运维审计报告、部署执行报告、上线检查报告 |
| 主文档强制章节 | 只服务于当前阶段执行记录、无需单独审批但必须可追溯的材料，可并入阶段主文档；必要时也可独立输出 | 开发入场检查、实现计划、修复复审、测试跳过项说明、制品校验摘要 |

强制规则：

1. 阶段主控技能可决定某项证据是否独立输出，但不得省略该证据。
2. 审计报告类文档必须存放在 `doc\audit` 对应子目录，不得重复存放在阶段业务目录。
3. 主文档强制章节必须在主文档目录和内容要求中明确，不能因为没有独立文件而视为可省略。
4. 若阶段矩阵新增证据项，必须同步更新本文档的命名、路径、生命周期和权限矩阵。

## 6. 文档版本控制

### 版本号格式

```
主版本.次版本.修订号
  │     │    └── 修订：Bug修复、纠错
  │     └─────── 次版本：功能更新、里程碑
  └────────────── 主版本：重大变更、阶段批准
```

### 状态标记

| 标记 | 含义 |
|------|------|
| [Draft] | 编写中，尚未完成（草案） |
| [Review] | 待人工审批（评审中） |
| [Approved] | 人工已批准（已批准） |
| [Final] | 已完成并锁定（终版） |

### 强制要求

任何文档的内容更新，必须执行以下操作：

1. 递增版本号（遵循上述语义规则）
2. 更新状态标记
3. 在文档的"修订历史"章节中，明确记录：版本号、日期、修改人、修改摘要

### 版本化文件管理流程

文档内容更新时，按以下步骤管理版本化文件：

1. **归档当前版本**：将工作目录中的当前版本文件复制到对应子目录的 `archive\` 中
2. **创建新版本文件**：基于当前版本创建新文件，文件名使用递增后的版本号
3. **更新文档内容**：更新状态标记和修订历史章节
4. **清理工作目录**：删除工作目录中的旧版本文件，仅保留最新版本

说明：`archive\` 目录下的历史版本文件为只读，禁止修改。工作目录中仅保留当前最新版本。

### 文档就地归档规则

为保证每个文档子目录只保留当前有效版本、便于使用者聚焦，所有 `doc` 业务子目录（`version` / `requirements` / `design` / `development` / `test` / `operation` / `release` / `audit` 及其子目录）执行就地归档。

| 规则项 | 内容 |
|:-------|:-----|
| 归档位置 | 每个 doc 业务子目录**内部**维护 `archive\` 子目录，历史版本就地归档，不集中外移 |
| 归档对象 | 非当前版本的历史版本文件（含按版本号命名的单版本文档）|
| 保留对象 | ① 当前版本文件 ② 长期维护文档（不按版本号命名的全部版本文档，如版本规划总纲、版本迭代路线图、候选需求池、技术债务总表、Release-Note-All、README 等）|
| 归档时机 | 版本发布完成、进入下一版本规划时；阶段审计移交时确认归档完整性 |
| 归档操作 | 使用 `git mv` 移动文件以保留历史；归档文件只读，禁止修改 |
| audit 子目录 | `audit\assessment` / `audit\review` / `audit\verification` / `audit\comprehensive` 各自就地归档历史版本 |
| 验收标准 | 归档后，每个 doc 业务子目录工作区仅包含当前版本文件与长期维护文档，`archive\` 收纳全部历史版本 |

> 归档为一次性整理动作：历史遗留的跨版本文件批量移入各自 `archive\`；此后每个版本发布时按"版本化文件管理流程"增量归档。

## Coding Stage Integration

When this skill is used during the formal coding stage, coordinate with `coding-stage-execution`.

- Treat `coding-stage-execution` as the Step 3 coding-stage controller.
- Use this skill only for its specialty area; do not use it to declare the whole development stage complete.
- Record implementation decisions, changed files, static quality commands, self-test evidence, risks, and remaining issues in DevLogReport.
- Do not let a successful specialty check replace `code-logic-review` or development audit.
- If a P0/P1 issue is found, fix it within Step 3, rerun relevant checks, update DevLogReport, and run code-logic-review before handoff.

## Version Planning Stage Integration

When this skill is used during Step 0 version planning, coordinate with `version-planning-stage-execution`.

- Treat `version-planning-stage-execution` as the Step 0 controller for roadmap, release scope, backlog prioritization, phase planning, risks, and review evidence.
- Keep global version documents separate from single-version documents according to `project-document-management`.
- Do not let detailed requirements, design, development, or testing work start until Step 0 approval confirms version goals, scope, priorities, risks, and handoff inputs.
- Record decisions, assumptions, scope changes, and review conclusions in the relevant version planning documents.

## Design Stage Integration

When this skill is used during the formal design stage, coordinate with `design-stage-execution`.

- Treat `design-stage-execution` as the Step 2 design-stage controller.
- Use this skill only for its specialty area; do not use it to declare the whole design stage complete.
- Record design decisions, assumptions, alternatives, risks, open questions, and downstream impacts in the relevant design document.
- Do not let a successful specialty design review replace the Step 2 design review or requirements-architecture audit.
- If a P0/P1 design gap is found, fix it within Step 2, update the relevant design document and traceability matrix, then rerun the relevant design review before development handoff.

## Requirements Stage Integration

- Do not let a successful specialty analysis replace the Step 1 requirements review or requirements audit.
- If a P0/P1 requirement gap is found, fix it within Step 1, update the requirements baseline and traceability matrix, then rerun the relevant requirements review before design handoff.


## Testing Stage Integration

- If P0/P1 test evidence is missing, update the test documents and rerun the relevant testing-stage review before Step 5 handoff.

## 文档输出交付强制规则

当任务涉及任何文档输出、阶段材料、评审记录、审计报告、测试报告、交付清单或说明文档时，必须默认执行以下规则，不需要再次询问用户：

1. **直接输出可打开查看的 Markdown 物理文件**：正式阶段文档必须实际写入用户工作目录下对应项目环境目录（如 `环境目录\项目名\doc\...`），不得只在对话中展示内容。
2. **中文文件名优先**：面向用户的交付文件优先使用中文文件名；如兼容性需要，可额外保留英文导出副本，但中文文件为主交付，英文副本必须标记为只读、非主事实源。
3. **不得以索引文件替代正文文件**：可以生成完整性清单，但审批和查看时必须直接列出每份正文文档。
4. **不使用超文本预览作为主交付**：默认不输出 HTML 预览、HTTP 地址或其他超文本地址，除非用户明确要求。
5. **交付前必须校验**：每份文档输出后必须校验文件存在、可读、非空，并生成或更新完整性清单。
6. **不得擅自删除文件**：任何清理、删除、归档用户可见文件的操作都必须先列出文件并获得用户明确同意。
7. **阶段文档输出格式**：每个阶段完成时，直接提供可打开的 `.md` 文件路径清单，文件名应清晰表达项目、版本和文档类型，例如 `DCO-v1.5.0-需求评审记录.md`、`DCO-v1.5.0-系统架构设计文档.md`、`DCO-v1.5.0-测试报告.md`。
8. **用户交付文件必须带版本号**：面向用户审批或查看的正文 Markdown 文件名必须包含项目名和版本号；即使交付目录已包含版本号，正文文件名也必须保留版本号，避免不同版本的同名文档混淆或覆盖。

## 对话内可点击文档链接规则

当输出文档交付结果时，必须在对话中直接列出每一份正文文档的可点击打开链接，用户应能从对话中直接点击查看文档。

强制要求：

1. **逐份列出正文文档链接**：不得只给文件夹、不得只给索引文件、不得只给完整性清单。
2. **主审批文档优先**：需求文档、评审记录、评估/审计报告、测试报告、部署交付报告等主审批文档必须放在最前面。
3. **中文标题 + 可点击链接**：链接标题使用中文文档名，例如“打开开发需求文档”“打开需求评审记录”。
4. **保留物理文件交付**：链接目标必须指向已经写入用户工作目录的实际 Markdown 文件。
5. **链接前先校验**：列出链接前必须确认文件存在、可读、非空。
6. **不以网址预览替代**：除非用户明确要求，不使用 HTTP/HTML 预览地址作为主交付。
7. **不以目录替代文档**：可以补充目录路径，但不能替代逐份文档链接。

## 变更统计与影响文件清单规则

当完成任一阶段、代码修改、脚本修改、配置修改、测试补充、文档交付或审计交付时，必须在对话交付结果中同步给出变更统计和影响文件清单，不需要用户再次提醒。

强制要求：

1. **区分统计类别**：至少区分生产/脚本/配置代码、测试代码、文档产物、校验清单；不得把历史遗留未提交文件混入本次统计。
2. **给出增删改统计**：对代码、脚本、配置类变更，优先使用 `git diff --numstat` 或等效方式统计新增行、删除行、净变化；新增文件需单独标注。
3. **列出具体影响文件**：必须逐项列出受影响文件路径、文件类型、变更性质（新增/修改/删除）、新增行、删除行和主要影响说明。
4. **列出测试与验证结果**：必须列出本次新增或修改的测试文件、测试用例数量、执行命令、通过/失败/跳过数量，以及未执行项和原因。
5. **列出文档交付统计**：涉及阶段文档时，必须列出正文文档数量、每份文档行数或字节数、完整性清单状态，并继续提供逐份可点击正文文档链接。
6. **说明范围边界**：若工作区存在既有未提交、未跟踪或历史文件，必须明确本次统计只覆盖本轮实际修改/生成的文件。
7. **写入阶段文档**：上述统计应同步写入对应阶段的 `DevLogReport`、测试报告、部署交付清单或阶段评审记录，作为审批依据。
