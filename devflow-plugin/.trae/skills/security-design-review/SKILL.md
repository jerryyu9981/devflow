# Security Design Review（安全设计评审）

## 定位

本技能在 Step 2 架构设计阶段执行安全设计评审，实现安全左移。它提供威胁建模方法论、安全架构评审清单、数据分类分级标准和安全需求追溯矩阵模板，确保系统在设计阶段就考虑并内建安全措施。

本技能不替代正式的安全测试和安全审计，也不替代编码阶段的安全编码规范（由 `secure-coding-practices` 负责）。它负责在设计阶段识别威胁、评估风险、制定安全架构决策，将安全需求追溯到具体威胁和架构决策。

推荐位置：

```text
Step 2 架构设计 → 威胁建模 → 安全架构评审 → 数据分类分级 → 安全需求追溯 → 设计文档输出
```

## 触发条件

当以下场景发生时，应调用本技能：

- Step 2 设计阶段启动时
- 新系统或新模块的架构设计时
- 处理敏感数据（用户隐私、金融数据、健康数据等）时
- 对外暴露 API 或 Web 端点时
- 集成第三方系统、第三方 SDK 或外部服务时
- 系统安全等级为 P0 或 P1 时
- 涉及认证、授权、加密等安全功能的设计时
- 跨信任边界的系统交互设计时

## 威胁建模方法论

### STRIDE 模型

STRIDE 是微软提出的威胁分类模型，将威胁分为六类。每类威胁对应不同的安全属性破坏。

| 威胁类型 | 安全属性 | 识别方法 | 缓解策略 | 示例 |
|---|---|---|---|---|
| Spoofing（欺骗） | 身份认证 | 审查所有身份验证入口、令牌管理、会话机制 | MFA、强密码策略、JWT 签名验证、会话绑定 | 攻击者伪造管理员令牌访问后台接口 |
| Tampering（篡改） | 完整性 | 审查数据在传输和存储过程中是否可被修改 | TLS 加密传输、数字签名、HMAC 校验、输入验证 | 攻击者篡改订单金额参数提交请求 |
| Repudiation（抵赖） | 不可抵赖性 | 审查关键操作是否有审计记录和追溯能力 | 操作日志、签名日志、时间戳、操作链追踪 | 用户否认执行过敏感操作且无法证明 |
| Information Disclosure（信息泄露） | 机密性 | 审查数据存储、传输、日志、错误信息中的暴露面 | 加密存储、TLS 传输、数据脱敏、最小权限 | 日志中打印完整密码或 API 密钥 |
| Denial of Service（拒绝服务） | 可用性 | 审查资源消耗型操作、无限制请求、单点故障 | 限流、熔断、资源配额、弹性伸缩、防护 WAF | 攻击者通过大量请求耗尽服务器资源 |
| Elevation of Privilege（权限提升） | 授权 | 审查权限校验逻辑、角色划分、越权风险 | RBAC/ABAC、权限最小化、越权检查、沙箱隔离 | 普通用户通过参数篡改获取管理员权限 |

### DREAD 风险评估模型

DREAD 用于对识别出的威胁进行量化风险评估，每个维度评分 1-10 分。

| 维度 | 含义 | 评分标准 |
|---|---|---|
| Damage（损害潜力） | 威胁利用成功后造成的损失程度 | 1= negligible，5= significant，10=catastrophic |
| Reproducibility（可重现性） | 威胁被重复利用的难易程度 | 1= very hard，5= needs effort，10= trivial |
| Exploitability（可利用性） | 攻击者利用该威胁的技术门槛 | 1= expert + special tools，5= knowledgeable，10= script kiddie |
| Affected Users（影响用户数） | 受影响用户或系统的比例 | 1= very few，5= some users，10= all users |
| Discoverability（可发现性） | 威胁被攻击者发现的难易程度 | 1= very hard，5= documented，10= obvious |

风险等级划分：

| 总分范围 | 风险等级 | 处理要求 |
|---|---|---|
| 30-50 | 高（High） | 必须在当前版本修复或缓解 |
| 15-29 | 中（Medium） | 应在当前版本修复，可接受风险残留 |
| 5-14 | 低（Low） | 记录并跟踪，可在后续版本处理 |

### 威胁建模流程步骤

以下是完整的威胁建模流程：

1. **确定资产**：识别系统中需要保护的核心资产（数据、服务、基础设施、业务流程）
2. **绘制数据流图**：用 DFD 描述系统的数据流向、处理节点、数据存储和信任边界
3. **识别信任边界**：确定系统内外、组件之间的信任边界线
4. **逐元素应用 STRIDE**：对每个数据流、处理过程、数据存储和外部实体逐一检查六类威胁
5. **评估风险（DREAD）**：对每个识别出的威胁进行 DREAD 评分和风险等级划分
6. **制定缓解措施**：针对高/中风险威胁制定具体的缓解策略和安全控制
7. **文档化**：将威胁模型、风险评估和缓解措施记录到设计文档中
8. **评审和更新**：由安全负责人评审，系统变更时更新威胁模型

## 安全架构评审清单

以下安全架构评审清单覆盖七个核心安全域：

### 身份认证

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 多因子认证（MFA） | 敏感操作和后台管理必须启用 MFA | 必须 |
| 单点登录（SSO） | 企业内部系统应支持 SSO 集成 | 推荐 |
| OAuth 2.0 / OIDC | 对外服务应使用标准协议，禁止自研认证协议 | 必须 |
| JWT 安全 | 使用 RS256/ES256 签名，设置合理过期时间，禁止算法混淆攻击 | 必须 |
| 密码策略 | 强密码（8 位以上、大小写+数字+特殊字符）、禁止常见弱密码 | 必须 |
| 登录保护 | 连续失败锁定、验证码、IP 限速 | 必须 |

### 授权模型

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| RBAC/ABAC | 根据业务复杂度选择 RBAC（角色）或 ABAC（属性）授权模型 | 必须 |
| 权限最小化 | 用户和角色只授予完成工作所需的最小权限集 | 必须 |
| 越权检查 | 每个请求必须校验当前用户对目标资源的访问权限 | 必须 |
| 权限分离 | 敏感操作（如支付、删除）应要求二次确认或更高权限 | 推荐 |
| 权限继承 | 清晰定义角色继承关系，避免权限膨胀 | 推荐 |

### 数据保护

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 传输加密 | 使用 TLS 1.2+（推荐 TLS 1.3），禁止 HTTP 明文传输 | 必须 |
| 存储加密 | 敏感数据必须加密存储，使用 AES-256 或同等算法 | 必须 |
| 密钥管理 | 使用专业密钥管理服务（如 HashiCorp Vault、KMS），禁止硬编码密钥 | 必须 |
| 字段加密 | 信用卡号、身份证号、密码等敏感字段单独加密 | 必须 |
| 密钥轮换 | 定期轮换加密密钥，支持密钥版本管理 | 推荐 |

### 输入验证

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 白名单验证 | 使用白名单（允许的值）而非黑名单进行输入验证 | 必须 |
| 参数化查询 | 所有数据库查询使用参数化查询或 ORM，禁止 SQL 拼接 | 必须 |
| 输出编码 | 根据上下文（HTML/URL/JavaScript/CSS）进行适当的输出编码 | 必须 |
| 文件上传 | 限制文件类型、大小，存储路径使用随机文件名，禁止执行上传文件 | 必须 |
| API 输入 | 每个接口定义参数类型、长度、格式约束，在框架层统一校验 | 必须 |

### 会话管理

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 安全 Cookie | 设置 HttpOnly、Secure、SameSite=Strict/Lax 属性 | 必须 |
| 会话超时 | 设置合理的会话过期时间，闲置会话自动失效 | 必须 |
| 并发控制 | 限制同一账号的并发会话数，或提供会话管理能力 | 推荐 |
| 会话固定 | 登录成功后重新生成会话标识 | 必须 |
| 登出清理 | 登出后立即使会话失效，清除服务端和客户端状态 | 必须 |

### 日志审计

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 操作日志 | 记录关键业务操作（创建/修改/删除）、操作人、时间、IP | 必须 |
| 安全事件日志 | 登录成功/失败、权限变更、敏感数据访问等安全事件单独记录 | 必须 |
| 日志脱敏 | 日志中的敏感信息（密码、密钥、身份证号）必须脱敏处理 | 必须 |
| 日志完整性 | 安全日志应具备防篡改能力（如写入独立存储、只追加） | 推荐 |
| 日志保留 | 安全日志保留周期至少 180 天，满足合规要求 | 必须 |

### 依赖安全

| 检查项 | 要求 | P0/P1 系统 |
|---|---|---|
| 已知漏洞扫描 | 集成自动化漏洞扫描工具（npm audit、pip audit、govulncheck 等） | 必须 |
| 许可证合规 | 检查依赖许可证与项目许可证的兼容性 | 推荐 |
| 供应链安全 | 使用锁定文件（lockfile），验证包签名，使用可信镜像源 | 必须 |
| 版本固定 | 生产依赖必须锁定版本，禁止使用范围版本（^、~）于生产环境 | 必须 |
| 定期更新 | 建立依赖更新机制，定期检查和升级有安全补丁的依赖 | 推荐 |

## 数据分类和保护等级

### 数据分类标准

数据按敏感程度分为四个等级：

| 等级 | 名称 | 定义 | 示例 |
|---|---|---|---|
| L1 | 公开 | 对外公开发布的数据，无泄露风险 | 产品介绍、公开文档、营销内容 |
| L2 | 内部 | 仅限企业内部使用，泄露会造成轻微影响 | 内部流程文档、组织架构、非敏感业务数据 |
| L3 | 机密 | 限制访问范围，泄露会造成重大影响 | 用户个人信息、订单数据、财务报表、内部 API 文档 |
| L4 | 绝密 | 极少数人可访问，泄露会造成灾难性影响 | 核心算法、加密密钥、用户密码、支付密钥 |

### 各等级保护要求

| 保护措施 | L1 公开 | L2 内部 | L3 机密 | L4 绝密 |
|---|---|---|---|---|
| 传输加密 | 可选 | 推荐 | 必须 | 必须（TLS 1.3） |
| 存储加密 | 不需要 | 可选 | 必须（AES-256） | 必须（AES-256 + HSM） |
| 访问控制 | 无限制 | 基于角色 | 基于角色 + 记录审计 | 最小权限 + 审批 + 审计 |
| 日志审计 | 不记录访问 | 记录访问日志 | 记录访问和操作日志 | 记录完整操作链 + 防篡改 |
| 备份要求 | 标准备份 | 标准备份 | 加密备份 + 异地存储 | 加密备份 + 异地 + 物理隔离 |
| 共享限制 | 无限制 | 内部共享需审批 | 共享需负责人审批 | 禁止共享 |
| 销毁方式 | 标准删除 | 安全删除 | 安全删除 + 验证 | 物理销毁 + 验证报告 |

### 数据生命周期安全要求

数据从创建到销毁的每个阶段都有对应的安全要求：

| 阶段 | 安全要求 |
|---|---|
| 创建/采集 | 明确数据分类等级，获得用户授权（如涉及个人信息），最小化采集范围 |
| 存储 | 按等级加密存储，合理选择数据库和文件系统，定期检查存储访问权限 |
| 使用 | 按需授权访问，使用中脱敏展示（如手机号保留后四位），操作日志审计 |
| 共享/传输 | 外部共享需审批和协议，传输使用加密通道，数据脱敏或匿名化后共享 |
| 归档 | 超出使用期但需保留的数据加密归档，降低访问频率和权限 |
| 销毁 | 到达保留期后安全销毁，L3/L4 需验证销毁结果，销毁记录留存备查 |

## 安全需求追溯矩阵模板

安全需求追溯矩阵将安全需求追溯到威胁模型和架构决策，确保每个安全需求都有明确的来源和实现方案。

以下是追溯矩阵模板：

| 需求编号 | 安全需求 | 威胁来源（STRIDE） | 风险等级（DREAD） | 架构决策/缓解措施 | 设计文档章节 | 负责人 | 状态 |
|---|---|---|---|---|---|---|---|
| SR-001 | 用户密码必须使用 bcrypt 哈希存储 | Information Disclosure | 高（32） | 数据库设计：password 字段存储 bcrypt hash | 数据库设计 3.2 | 张三 | 已实现 |
| SR-002 | 所有 API 接口必须验证 JWT 令牌 | Spoofing | 高（35） | API 网关统一校验 JWT，白名单路由除外 | 架构设计 4.1 | 李四 | 已实现 |
| SR-003 | 订单金额接口参数必须服务端校验 | Tampering | 高（28） | 订单服务校验金额范围，不信任客户端传入 | 订单服务设计 2.3 | 王五 | 设计中 |
| SR-004 | 管理操作必须记录审计日志 | Repudiation | 中（22） | AOP 拦截管理操作，写入审计日志表 | 日志设计 3.1 | 赵六 | 已实现 |
| SR-005 | API 限流每用户 100 次/分钟 | Denial of Service | 中（25） | 网关层令牌桶限流，按用户维度 | 网关设计 5.2 | 张三 | 设计中 |
| SR-006 | 普通用户不能访问管理后台接口 | Elevation of Privilege | 高（30） | RBAC 权限校验，管理接口限制 admin 角色 | 授权设计 4.3 | 李四 | 已实现 |

## 反模式

以下是在安全设计评审中应避免的做法：

- **不做威胁建模**：跳过威胁建模直接进入开发，安全风险在设计阶段就被忽略，修复成本指数级增长
- **安全后置**：将安全措施推迟到开发完成甚至上线后，而非在设计阶段内建安全
- **忽视第三方风险**：集成第三方 SDK、API 或服务时不评估其安全风险，不审查其安全实践
- **过度依赖网络边界**：认为防火墙和内网隔离足以保证安全，忽视内部威胁和深度防御
- **忽略数据分类**：不区分数据敏感等级，所有数据采用相同保护措施
- **安全需求无追溯**：安全需求与威胁模型、架构决策之间缺乏追溯关系，无法验证覆盖度
- **一次性安全设计**：认为系统设计完成后安全工作就结束了，不随系统演进更新威胁模型
- **忽视合规要求**：不考虑行业法规（GDPR、等保、PCI-DSS 等）对系统设计的影响

## 强制规则

以下规则必须严格遵守：

1. P0 系统必须执行完整的威胁建模流程（STRIDE + DREAD），并输出威胁模型文档
2. 处理敏感数据（L3/L4）的系统必须执行数据分类分级，并在设计文档中明确标注
3. 对外暴露的 API 必须设计认证和授权机制，禁止无认证的公开接口（文档类除外）
4. 安全需求追溯矩阵必须覆盖所有高、中风险威胁的缓解措施
5. 涉及密码学功能的设计必须使用标准算法和经过验证的库，禁止自研加密算法
6. 安全架构评审清单中标记为"必须"的检查项必须全部通过才能进入开发阶段
7. 威胁模型和追溯矩阵必须在系统架构发生重大变更时同步更新
