# backend-coverage（后端设计覆盖率检查）

## When To Use

本技能用于在 Step 2（架构与设计阶段）对**后端设计**进行系统化覆盖检查，防止以下问题流入开发阶段：

- API 接口文档缺少异常响应、边界条件、版本兼容性或降级策略
- 数据库设计与 API 契约、前端展示需求不一致，导致联调返工
- 业务状态流转缺少可视化文档，异常分支未覆盖
- 鉴权、权限、敏感字段等安全设计未系统化梳理
- 设计阶段未预埋后端测试关注点

**触发场景**：
- 用户要求"检查后端设计是否完整"
- 需要"API 契约覆盖检查"或"接口完整性验证"
- 需要"数据模型对齐检查"
- 需要"业务状态机覆盖检查"
- 需要"安全设计检查"
- 设计评审前需要系统化的后端设计验证

## Core Workflow

执行以下五个步骤，按顺序进行，不得跳过：

### Step 1: API 契约覆盖检查

验证 API 接口设计文档是否完整覆盖了所有需求场景。

**检查维度**：

| 检查项 | 说明 | 强制要求 |
|---|---|---|
| 路径与方法 | 每个 API 的路径、HTTP 方法、版本号 | 强制 |
| 请求参数 | 参数名、类型、是否必填、默认值、校验规则 | 强制 |
| 响应结构 | 成功响应的字段、类型、示例 | 强制 |
| 异常响应 | 所有可能的错误码、错误信息、HTTP 状态码 | P0 API 强制 |
| 边界条件 | 分页、排序、最大返回条数、超时时间 | P0 API 强制 |
| 版本兼容 | 接口版本变更策略、废弃字段处理 | 涉及版本升级时强制 |
| 降级策略 | 服务不可用时的降级行为、缓存兜底、默认值 | P0 API 建议 |
| 鉴权方式 | 认证方式（Token/OAuth/API Key）、权限粒度 | 强制 |

**执行动作**：
1. 读取 API 接口设计文档
2. 对每个 P0 API 逐条检查上述 8 个维度
3. 对 P1 API 检查核心维度（请求参数、响应结构、异常响应、鉴权）
4. 记录缺失项和修复计划

**通过标准**：
- P0 API：所有检查项 100% 覆盖
- P1 API：请求参数、响应结构、异常响应、鉴权方式必须覆盖

**强制产出**：`{项目名}-API契约覆盖检查表-v{版本号}.md`

---

### Step 2: 数据模型对齐检查

验证数据库设计、API 契约、前端展示三者之间的一致性。

**对齐维度**：

| 对齐对象 | 检查内容 | 示例 |
|---|---|---|
| 数据库 ↔ API 响应 | 字段名、类型、约束是否与 API 响应一致 | DB `user_name` vs API `username`（不一致） |
| API 响应 ↔ 前端展示 | API 响应字段是否被前端使用，是否有前端需要但 API 未提供的字段 | 前端需要 `userAvatar`，API 只返回 `userId` |
| 枚举值一致性 | 数据库状态码、API 状态码、前端状态映射是否一致 | DB: 0=待支付, 1=已支付; API: pending/paid; 前端: 待支付/已支付 |
| 必填/可选一致性 | 数据库 NOT NULL 约束、API 必填标记、前端表单必填标记 | DB 允许 NULL，但 API 标记为 required |
| 数据格式一致性 | 日期格式、金额精度、字符串编码等 | DB: DECIMAL(10,2); API: 字符串 "19.99"; 前端: 数字 19.99 |

**执行动作**：
1. 读取数据库设计文档、API 接口设计文档、前端页面清单
2. 对 P0 数据流建立三方映射表
3. 检查字段名、类型、枚举值、必填规则、数据格式的一致性
4. 记录不一致项和统一方案

**通过标准**：
- P0 数据流：数据库 ↔ API ↔ 前端 三者字段映射 100% 一致
- P1 数据流：核心字段映射一致，非核心字段不一致有记录和修复计划
- 枚举值不一致必须在设计阶段统一

**强制产出**：`{项目名}-数据模型对齐检查表-v{版本号}.md`

---

### Step 3: 业务状态机覆盖检查

将核心业务实体的状态流转可视化，确保所有状态转换路径（包括异常分支）均有设计。

**必须覆盖的内容**：

| 检查项 | 说明 | 强制要求 |
|---|---|---|
| 状态定义 | 所有可能的状态值及含义 | 强制 |
| 初始状态 | 实体创建时的默认状态 | 强制 |
| 终止状态 | 哪些状态是终态（不可再转换） | 强制 |
| 正常转换 | 所有合法的状态转换路径 | 强制 |
| 异常转换 | 什么情况下会触发状态回退或异常跳转 | P0 业务强制 |
| 超时处理 | 状态在特定时间后未变化如何处理 | 涉及时效业务时强制 |
| 并发冲突 | 同一实体被多个操作同时修改时的状态一致性 | 涉及并发时强制 |

**执行动作**：
1. 识别需求文档中的 P0/P1 核心业务实体（如订单、用户、任务等）
2. 为每个实体定义完整的状态列表
3. 列出所有正常转换路径和异常转换路径
4. 覆盖超时处理和并发冲突场景

**通过标准**：
- P0 业务实体：所有状态转换路径 100% 覆盖，异常分支 >= 80%
- P1 业务实体：正常转换路径 100% 覆盖，异常分支 >= 50%

**强制产出**：`{项目名}-业务状态机文档-v{版本号}.md`

---

### Step 4: 安全与权限设计检查

系统化梳理系统的鉴权机制、数据权限控制和敏感数据处理策略。

**检查维度**：

| 检查项 | 说明 | 强制要求 |
|---|---|---|
| 鉴权方式 | Token/OAuth/API Key/Session 的选择和实现 | 强制 |
| 权限粒度 | RBAC/ABAC 模型、角色定义、权限边界 | 涉及多角色时强制 |
| 数据权限 | 用户只能访问自己的数据还是可访问他人数据 | 强制 |
| 敏感字段 | 密码、身份证、银行卡、手机号等敏感信息的存储和传输 | 强制 |
| 输入校验 | SQL 注入、XSS、CSRF、文件上传等攻击防护 | 强制 |
| 审计日志 | 关键操作的日志记录（谁、何时、做了什么） | P0 操作强制 |
| 加密策略 | 传输加密（TLS）、存储加密（AES）、密钥管理 | 强制 |

**执行动作**：
1. 读取安全设计说明和 API 接口设计文档
2. 逐条检查上述 7 个维度
3. 识别高风险缺口（如未定义鉴权、敏感字段明文存储等）
4. 记录修复计划

**通过标准**：
- 所有强制检查项 100% 通过
- 安全设计检查不通过不得进入编码阶段

**强制产出**：`{项目名}-安全设计检查表-v{版本号}.md`

---

### Step 5: 后端设计-测试预映射 + 覆盖报告

从后端设计文档中提取测试关注点，形成最终覆盖检查报告。

**执行动作**：
1. 从 API 契约覆盖检查表、数据模型对齐检查表、状态机文档、安全设计检查表中提取测试关注点
2. 按功能测试 / 性能测试 / 安全测试 / 异常测试 / 并发测试 分类
3. 标注优先级和预估测试方法
4. 汇总所有检查结果，形成覆盖报告

**后端设计-测试预映射表必须包含**：

| 需求ID | API ID | 测试类型 | 测试关注点 | 优先级 | 预估测试方法 |
|---|---|---|---|---|---|
| REQ-001 | API-001 | 功能测试 | 支持手机号、邮箱、微信三种登录方式 | P0 | 正例测试 |
| REQ-001 | API-001 | 安全测试 | 密码错误 5 次后锁定 15 分钟 | P0 | 边界值测试 |
| REQ-002 | API-003 | 性能测试 | 仪表盘统计接口响应时间 <= 500ms | P1 | 压力测试 |

**覆盖报告必须包含**：
1. 检查概览（API 总数、已覆盖数、数据流对齐率、状态机覆盖率、安全检查项通过率）
2. 问题清单（按严重度排序：严重/中等/轻微）
3. 修复计划（责任人、截止时间）
4. 风险评估（哪些遗漏可能流入开发阶段）
5. 是否允许进入设计评审的结论

**通过标准（全部满足方可进入设计评审）**：
- [ ] P0 API 所有检查项 100% 覆盖
- [ ] P0 数据流三者映射 100% 一致
- [ ] P0 业务实体状态机所有正常转换路径 100% 覆盖，异常分支 >= 80%
- [ ] 安全设计所有强制检查项 100% 通过
- [ ] 后端设计-测试预映射表已提交并获测试代表签字

**强制产出**：
- `{项目名}-后端设计-测试预映射表-v{版本号}.md`
- `{项目名}-后端覆盖检查报告-v{版本号}.md`

## Integration With DevFlow

### Step 2 设计阶段集成

当本技能在 Step 2 设计阶段被调用时：
- 以 `design-stage-execution` 为阶段控制器
- 本技能只负责后端设计覆盖检查这一专项领域
- 不替代 `api-design`、`sql-database`、`security-best-practices` 等专项设计技能
- 不替代设计评审或需求-架构审计
- 发现的 P0/P1 设计缺口必须在 Step 2 内修复，更新相关设计文档后重新检查

### 协作技能

| 场景 | 应调用技能 |
|---|---|
| 需要设计/修改 API | `api-design` |
| 需要设计/修改数据库 | `sql-database`、`mongodb` |
| 需要安全设计建议 | `security-best-practices` |
| 需要前后端 API 契约对齐 | `api-contract-management` |
| 需要测试视角审阅 | `testing-stage-execution` |

### 与前端覆盖检查的关系

```text
Step 2 设计阶段
├── 前端覆盖检查 → prototype-coverage（独立技能）
├── 后端覆盖检查 → backend-coverage（本技能）
└── 前后端对齐检查 → api-contract-management
```

`backend-coverage` 与 `prototype-coverage` 是**同级对称**的专项技能，均由 `design-stage-execution` 在设计评审前协调调用。

## Example Invocation

### 示例 1: 执行完整的后端覆盖检查

用户指令："请检查当前项目的后端设计覆盖率"

执行流程：
1. 读取 API 接口设计文档、数据库设计文档、需求文档
2. 执行 Step 1-5 的完整检查流程
3. 输出后端覆盖检查报告，指出 API 缺失、数据不一致、状态机遗漏、安全缺口
4. 给出修复建议和优先级排序

### 示例 2: 仅执行 API 契约覆盖检查

用户指令："检查订单相关的 API 是否完整"

执行流程：
1. 读取订单模块的 API 设计文档
2. 对订单相关 API 执行 Step 1（API 契约覆盖检查）
3. 输出 API 契约覆盖检查表，指出缺失的异常响应和边界条件
4. 给出修复建议

### 示例 3: 数据模型对齐检查

用户指令："检查数据库字段和 API 返回是否一致"

执行流程：
1. 读取数据库设计文档和 API 接口设计文档
2. 执行 Step 2（数据模型对齐检查）
3. 输出数据模型对齐检查表，指出字段名、类型、枚举值不一致项
4. 给出统一方案建议
