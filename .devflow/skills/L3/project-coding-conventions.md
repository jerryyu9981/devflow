# project-coding-conventions（项目编码约定）

## 定位

本技能是项目级编码约定的唯一事实来源（Single Source of Truth），被 `coding-stage-execution` 在 Step 3 编码实现阶段调用。所有编码实现必须同时满足本技能的约定和 `code-static-quality-check`、`code-logic-review` 的检查要求。

本技能不重复定义通用编码规范（如语言特定的格式化规则），而是聚焦于项目级别的架构约束、跨模块一致性规则和团队协作约定。语言级别的格式化由各语言的 linter/formatter 负责。

## 触发条件

- Step 3 编码实现阶段开始时自动触发
- 编码实现过程中遇到约定未覆盖的场景时按需查阅
- 代码评审发现编码风格不一致时引用本技能作为判定标准

## 约束范围

> **编码阶段三技能关系**：本技能与 code-static-quality-check（静态质量检查）、code-logic-review（代码逻辑审查）共同组成 Step 3 编码阶段的质量保障体系。三者使用不同的命名前缀以反映职责范围：project-coding-conventions（project- 前缀）为项目级跨阶段约定，code-static-quality-check 和 code-logic-review（code- 前缀）为编码子阶段专项门禁。三技能在编码阶段串联执行：编码实现 → project-coding-conventions（编码标准）→ code-static-quality-check（静态质量）→ 开发自测 → code-logic-review（逻辑审查）→ 修复复审 → DevLogReport → 开发审计。

本技能覆盖的约定范围：

本技能覆盖以下约定范围：

- **后端分层架构约束**：Controller/Service/Repository 各层职责与禁止事项
- **错误处理规范**：统一错误码体系、错误响应格式、异常分类处理
- **日志规范**：日志级别使用规则、必须记录的字段、禁止记录的内容
- **API 设计约定**：统一响应格式、分页参数、错误码段、版本头
- **注释与文档规则**：公共 API 注释、复杂算法注释、TODO 格式、废弃标记
- **数据库操作规则**：SQL 编写规则、数据库性能规则、事务范围、迁移规范
- **前端编码规则**：组件文件结构、状态管理选择、路由守卫、表单校验
- **并发与异步安全规则**：共享状态保护、竞态条件避免
- **配置管理规则**：环境变量命名、配置文件结构、禁止硬编码
- **依赖管理规则**：依赖引入规范、依赖审计要求、锁文件管理、废弃依赖清理
- **命名模板**：API 路径、数据库表名、环境变量前缀、配置键命名空间

## 后端分层架构约束

| 层级 | 职责 | 允许的操作 | 禁止的操作 |
|------|------|-----------|-----------|
| Controller/Router | 请求接收、参数校验、响应封装、调用 Service | 参数校验、HTTP 状态码设置、调用单个 Service | 直接操作数据库、包含业务逻辑、直接返回原始异常 |
| Service | 业务逻辑编排、事务管理、调用 Repository | 业务规则计算、事务边界管理、调用多个 Repository | 直接操作 HTTP 请求/响应、包含 SQL 语句 |
| Repository/DAO | 数据访问、SQL 执行、ORM 操作 | 单表 CRUD、参数化查询、分页查询 | 包含业务逻辑、调用其他 Repository、直接返回 Domain 对象以外的东西 |

### 补充规则

- **禁止跨层调用**：Controller 不得直接调用 Repository，必须经过 Service 层
- **禁止循环依赖**：Service A 不得依赖 Service B 同时 Service B 依赖 Service A；如需双向通信，通过事件机制解耦
- **每层必须有独立单元测试**：Controller 层测试请求/响应映射，Service 层测试业务逻辑，Repository 层数测试数据访问

## 错误处理规范

### 异常分类

| 类别 | 说明 | 处理方式 | 示例 |
|------|------|---------|------|
| 业务异常 | 用户输入不合法或业务规则不满足 | 返回对应业务错误码和友好提示 | 余额不足、参数格式错误 |
| 系统异常 | 内部错误、依赖服务不可用 | 记录 ERROR 日志，返回通用系统错误码，不暴露内部细节 | 数据库连接失败、空指针 |
| 第三方异常 | 外部服务返回错误或超时 | 记录 WARN 日志，返回降级响应或重试 | 支付网关超时、短信发送失败 |

### 统一错误响应格式

```json
{
  "code": "BIZ_001",
  "message": "用户输入的邮箱格式不正确",
  "details": [
    {"field": "email", "reason": "不符合邮箱格式要求"}
  ],
  "traceId": "abc-123-def"
}
```

### 错误码命名规则

- 格式：`{类别}_{三位编号}`
- 类别前缀：BIZ（业务）、SYS（系统）、AUTH（鉴权）、PERM（权限）、RATE（限流）、DB（数据库）、EXT（外部依赖）
- 编号范围：001-999
- 示例：BIZ_001、SYS_001、AUTH_001

## 日志规范

### 日志级别使用规则

| 级别 | 使用场景 | 示例 |
|------|---------|------|
| DEBUG | 开发调试信息，生产环境关闭 | 变量值、中间计算结果、循环计数 |
| INFO | 关键业务节点、状态变更 | 用户注册成功、订单创建、支付完成 |
| WARN | 可恢复的异常、降级操作 | 第三方服务超时后重试成功、缓存未命中回源 |
| ERROR | 不可恢复的错误、需要人工介入 | 数据库连接失败、支付网关返回未知错误 |

### 必须记录的字段

每条日志必须包含（通过结构化日志或上下文注入）：

- **traceId**：请求追踪 ID
- **timestamp**：时间戳（精确到毫秒）
- **level**：日志级别
- **module**：模块名（如 `auth.service`、`order.controller`）
- **message**：人类可读的描述
- **关键业务字段**：userId、orderId、requestId 等（按场景选取）

### 禁止记录的内容

- 密码、令牌、密钥等敏感信息（任何级别都不允许）
- 完整的请求体（超过 1KB 时只记录摘要）
- 完整的响应体（同上）
- 用户个人隐私数据（身份证号、手机号需脱敏）

## API 设计约定

> **优先级说明**：本项目级 API 约定优先于 pi-design 技能的通用指导。所有 Step 3 编码实现必须遵循本约定；pi-design 技能作为设计阶段的 API 模式参考，编码阶段的 API 格式以本约定为准。

### 统一响应格式

成功响应：

```json
{
  "code": 0,
  "message": "success",
  "data": { "...": "..." },
  "traceId": "abc-123-def"
}
```

分页响应：

```json
{
  "code": 0,
  "message": "success",
  "data": { "...": "..." },
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 100,
    "totalPages": 5
  },
  "traceId": "abc-123-def"
}
```

### 路径命名规则

- 使用小写 kebab-case：`/api/v1/user-profiles`
- 资源名用复数名词：`/users`、`/orders`
- 子资源用路径表示：`/users/{userId}/orders`
- 操作用 HTTP 方法区分，不在路径中使用动词

### 分页参数

- `page`：页码（从 1 开始）
- `pageSize`：每页条数（默认 20，最大 100）
- `sortBy`：排序字段（可选）
- `sortOrder`：排序方向 asc/desc（可选）

### 版本管理

- URL 路径版本：`/api/v1/`、`/api/v2/`
- 版本号只增不减
- 旧版本至少维护 6 个月

## 注释与文档规则

### 强制注释场景

| 场景 | 注释要求 | 示例 |
|------|---------|------|
| 公共 API（对外暴露的函数/类/接口） | 必须包含功能说明、参数说明、返回值说明、异常说明 | JSDoc / docstring |
| 复杂算法 | 必须说明算法思路、时间复杂度、空间复杂度 | `// 使用滑动窗口，O(n)时间复杂度` |
| 业务规则 | 必须引用需求文档编号 | `// 需求 DCO-REQ-2026-001: 余额不足时禁止下单` |
| 临时方案/TODO | 必须标记负责人和预期解决时间 | `// TODO(zhangsan): 2026-07-01前重构为策略模式` |
| 废弃代码 | 必须标记废弃原因和替代方案 | `// DEPRECATED: 使用 UserService.create() 替代，将在 v3.0 移除` |

### 禁止的注释

- 无意义的注释：`// 获取用户`（代码 `getUser()` 本身已经说明）
- 注释掉的代码块（应删除，由 Git 管理历史）
- 与代码不一致的注释

## 数据库操作规则

### SQL 编写规则

- 必须使用参数化查询，禁止字符串拼接 SQL
- 禁止 `SELECT *`，必须明确列出所需字段
- 大表查询必须有索引提示或 WHERE 条件
- 禁止在 WHERE 子句中对索引列使用函数
- UPDATE/DELETE 必须有 WHERE 条件（禁止全表操作）

### 数据库性能规则

| 场景 | 检查项 | 禁止行为 |
|---|--------|---------|
| 查询性能 | EXPLAIN计划检查、索引覆盖、N+1查询检测 | 禁止无索引全表扫描上线 |
| 批量操作 | 使用批量INSERT/UPDATE、分批提交 | 禁止逐条INSERT大量数据 |
| 连接管理 | 连接池大小配置合理、查询超时设置 | 禁止长连接无超时 |
| 慢查询 | 开启慢查询日志、定期审查 | 禁止不审查慢查询上线 |

### 事务规则

- 事务范围必须最小化，只包含必须原子操作的业务逻辑
- 禁止在事务中调用外部服务（HTTP 请求、文件 IO）
- 事务超时设置：默认 30 秒，长事务需单独评估
- 只读操作不得使用事务

### 数据库迁移规则

- 每个迁移文件必须有 up 和 down 方法
- 禁止修改已执行的迁移文件
- 大表变更必须分批执行
- 迁移前必须备份数据
- 新增字段必须有默认值或允许 NULL

## 前端编码规则

### 组件文件结构

每个组件目录包含：

```
ComponentName/
├── index.tsx          # 组件入口
├── ComponentName.tsx  # 组件实现
├── ComponentName.module.css  # 样式（或 .scss）
├── types.ts           # 类型定义
├── useComponentName.ts  # 自定义 Hook（如有）
└── __tests__/         # 测试文件
```

### 状态管理选择标准

| 场景 | 推荐方案 | 说明 |
|------|---------|------|
| 组件内部 UI 状态 | useState/useReducer | 表单输入、展开折叠等 |
| 跨组件共享状态 | Context + useReducer | 主题、语言、用户信息 |
| 服务端状态 | React Query / SWR | API 数据获取和缓存 |
| 复杂全局状态 | Zustand / Redux | 跨页面共享、持久化需求 |

### 路由守卫规范

- 需要鉴权的页面必须在路由层统一处理
- 禁止在组件内部做鉴权判断
- 未授权访问统一跳转到登录页

### 表单校验标准

- 前端校验：即时反馈，提升用户体验
- 后端校验：必须独立执行，不依赖前端校验
- 校验规则必须与需求文档中的验收标准一致

## 并发与异步安全规则

### 共享状态保护

- 禁止在多个 goroutine/线程/async 函数间共享可变状态而不加锁
- 全局变量必须有明确的初始化和清理机制
- 缓存必须有 TTL 和容量上限

### 竞态条件预防

- 数据库操作必须使用乐观锁或悲观锁
- 支付等关键操作必须有幂等性保证
- 定时任务必须有分布式锁

## 配置管理规则

### 环境变量命名

- 格式：`{项目名}_{模块}_{键名}`，全部大写
- 示例：`DCO_DB_HOST`、`DCO_REDIS_PORT`、`DPS_API_TIMEOUT`
- 禁止在代码中硬编码任何环境相关值

### 配置文件结构

- 使用分层配置：default.yml -> {env}.yml -> 环境变量覆盖
- 敏感配置（密钥、密码）必须通过环境变量或密钥管理服务注入
- 配置变更必须记录到 DevLogReport

## 编码阶段反向声明

本技能被 `coding-stage-execution` 内联引用（内联内容：API 响应格式、错误码、三层约束、并发、配置、数据库性能规则）。修改本技能时，需同步检查 `coding-stage-execution` 中的内联速查表。

|
| 新增运行时依赖 | 评估必要性、许可证兼容性、已知漏洞、维护活跃度 | 禁止引入无维护的依赖、禁止引入与项目许可证不兼容的依赖 |
| 新增开发依赖 | 评估必要性、版本匹配 | 禁止引入非必要的构建/测试工具链 |
| 依赖升级 | 变更日志检查、API 兼容性检查、回归范围评估 | 禁止跨大版本升级不做影响分析 |
| 依赖移除 | 检查代码中是否仍有引用、更新 import/require | 禁止只改 package.json 不移除引用代码 |

### 依赖审计要求
1. **每次版本迭代**必须执行依赖审计（`npm audit`/`pip audit`/`go list -u -m all`）。
2. **Critical 漏洞**：发现即阻塞，必须立即修复或寻找替代依赖。
3. **High 漏洞**：本版本内修复，无法在本版本修复的须说明理由。
4. **许可证合规**：新增依赖必须检查许可证是否与项目兼容，禁止使用 GPL 类强传染性许可证（除非项目明确选择 GPL）。
5. **废弃依赖清理**：发现已废弃或不再维护的依赖，记录到技术债务清单并安排替换计划。

### 依赖锁定
1. 必须提交锁文件（`package-lock.json`/`poetry.lock`/`go.sum`）到版本控制。
2. 禁止手动修改锁文件，必须通过包管理器更新。
3. CI/CD 流水线中必须验证锁文件与 package.json 一致。

## 命名模板

### API 路径模板

`/api/v{版本号}/{资源名复数}`

### 数据库表名模板

`{模块缩写}_{业务实体名}`，全部小写下划线分隔

示例：`dco_sync_record`、`dhap_user_profile`

### 环境变量前缀

`{模块}.{子模块}.{键名}`，如 `db.pool.maxConnections`

## 与其他技能的关系

### 被调用关系

- `coding-stage-execution`：在编码实现阶段调用本技能作为编码标准
- `code-static-quality-check`：静态检查中引用本技能的命名规则和格式规则
- `code-logic-review`：逻辑审查中引用本技能的错误处理和日志规范

### 不替代关系

- 不替代 `security-best-practices`：安全编码的详细规则由该技能负责
- 不替代 `coplayer-naming-conventions` 和 `universal-naming-conventions`：通用命名规范由该技能负责，本技能只定义项目级命名模板
- 不替代 `api-design`：API 设计模式由该技能负责，本技能只定义项目级约定
- 不替代 `react-skills` / `vue-skills`：框架特定最佳实践由该技能负责
